## 1. 规范目标

本规范解决以下问题：

| 问题 | 说明 |
|------|------|
| **避免所有模板都强行加入 Few-shot** | 有些模板 Zero-Shot 就够用，加了示例浪费 token 且不必要 |
| **避免该用 Few-shot 时没有示例** | 输出格式不稳定、需要固定风格的模板，没有示例会导致结果不可控 |
| **避免示例过多导致模板臃肿** | 塞了 5-10 个示例的模板难以维护，应迁移到案例库 |
| **Zero-Shot / Few-shot / 案例库边界不清** | 不知道什么情况该用哪种，容易过度使用或遗漏 |
| **未来模板创建缺乏判断依据** | 每次新建模板都要重新纠结「要不要加示例」 |

**核心定位**：在 T-CONFIG-003（选策略）之后、T-CONFIG-002（写示例）之前，专门解决「要不要启用 Few-shot」的问题。

## 2. 适用范围

### 强制适用

本规范强制适用于以下场景的 Few-shot 启用判断：

| 类型 | 说明 |
|------|------|
| **文本提示词模板** | `prompt-kb/02-text-prompts/templates/` 下所有模板创建或审查时 |
| **Prompt Chaining 模板** | 多步骤 Pipeline 模板中各步骤是否需要示例的判断 |
| **带参考资料输入的模板** | 包含防幻觉机制的模板中示例的启用判断 |
| **OpenClaw 工作流模板** | 单 Agent / 多 Agent 工作流中交接格式、审核格式的示例判断 |
| **图像提示词模板** | `prompt-kb/03-image-prompts/` 下模板的示例启用判断（只做判断，不定义具体格式） |
| **视频提示词模板** | `prompt-kb/04-video-prompts/` 下模板的示例启用判断（只做判断，不定义具体格式） |
| **多 Agent 协作模板** | Agent 间交接格式、审核评分格式是否需要示例的判断 |

### 不强制适用

| 类型 | 原因 |
|------|------|
| **学习笔记** | 属于知识沉淀，不属于模板工程范畴 |
| **案例复盘** | 已归档的实战案例（`06-case-studies/`），本身就是案例库内容 |
| **资源索引** | 纯链接/目录列表，无示例需求 |
| **临时草稿** | 尚未定稿，不适合过早规范 |

## 3. 与现有规范的关系

Prompt-KB 规范体系在 Few-shot 相关的判断上分为三个层次：

| 规范 | 编号 | 负责什么 | 决策顺序 |
|------|------|----------|----------|
| **T-CONFIG-003** | 策略判断规范 | 「这个任务适合什么策略？」（Zero-Shot / Few-Shot / Prompt Chaining / ...） | **第 1 步** |
| **T-CONFIG-004（本规范）** | Few-shot 适用条件规范 | 「这个任务是否应该启用 Few-shot？」（是 / 否 / 迁移案例库） | **第 2 步** |
| **T-CONFIG-002** | Few-shot 示例规范 | 「Few-shot 示例应该怎么写？」（数量 / 格式 / 类型 / 验收） | **第 3 步** |

**判断流程：**
1. 先用 **T-CONFIG-003** 判断整体策略；
2. 如果策略中涉及 Few-shot，再用 **本规范** 判断是否真的需要启用；
3. 如果确认需要 Few-shot，最后用 **T-CONFIG-002** 写示例。

**关键原则：**
- 如果本规范判断**不需要** Few-shot，**不要为了完整性强行加示例**；
- 如果本规范判断**需要** Few-shot，参考 T-CONFIG-002 确定数量和格式；
- 如果本规范判断**示例超过 3 个**，迁移到案例库（`06-case-studies/`）。

## 4. Few-shot 决策总表

以下总表覆盖 16 种常见任务情况，给出是否使用 Few-shot 的判断及更适合的方案。

| # | 任务情况 | 是否使用 Few-shot | 更适合的方案 | 原因 |
|---|----------|-------------------|-------------|------|
| 1 | 任务简单、输入清楚 | ❌ 不需要 | Zero-Shot + 占位符格式示例 | 模型 Zero-Shot 能力足够，加示例浪费 token |
| 2 | 输出格式不稳定 | ✅ 需要 | 1-2 个 Few-shot 示例 | Few-shot 是最直接的格式锁定手段 |
| 3 | 需要固定文风 | ✅ 需要 | 1 个 Few-shot 示例（展示风格） | 模型需要看到目标语气、措辞、专业度 |
| 4 | 需要固定结构 | ✅ 需要 | 1 个 Few-shot 示例（展示结构） | 表格/报告/卡片等结构化输出需要格式基准 |
| 5 | 用户不知道怎么填 | ✅ 需要 | 1 个 Few-shot 示例（填写示范） | 示例是最好的使用说明，比纯文字说明更直观 |
| 6 | 经常出现信息不足 | ✅ 需要 | 2 个 Few-shot 示例（正常 + 信息不足） | 信息不足处理方式无法从指令中自然学到 |
| 7 | 有边界情况或风险场景 | ✅ 需要 | 2-3 个 Few-shot 示例（含边界输入） | 需要展示正确的拒绝方式和兜底策略 |
| 8 | 需要风格迁移 | ✅ 需要 | 1-2 个 Few-shot 示例（展示目标风格） | 风格迁移是 Few-shot 的经典应用场景 |
| 9 | 需要分类判断 | ✅ 需要 | 1-3 个 Few-shot 示例（覆盖各分类） | 示例能传达分类边界和判断标准 |
| 10 | 需要多步骤任务 | ⚠️ 按步骤判断 | Prompt Chaining + 在容易出错的步骤放示例 | 不需要每步都加，只加在最容易出错的步骤 |
| 11 | 需要参考资料 | ❌ 通常不需要 | Zero-Shot + 参考资料区（T-CONFIG-001 §5） | 参考资料机制比示例更能防止幻觉 |
| 12 | 示例超过 3 个 | ❌ 不要塞进模板 | 迁移到案例库（`06-case-studies/`） | 超过 3 个示例会让模板臃肿，且 token 性价比低 |
| 13 | 需要展示大量真实案例 | ❌ 不要塞进模板 | 案例库 + 模板中引用案例库 | 案例库是专门沉淀真实案例的地方 |
| 14 | 图像提示词生成 | ⚠️ 按需 | 1 个示例（展示画面描述方式） | 帮助用户学习如何描述主体/风格/构图/光线 |
| 15 | 视频提示词生成 | ⚠️ 按需 | 1 个示例（展示分镜/镜头描述方式） | 帮助用户学习如何描述时间顺序和镜头运动 |
| 16 | OpenClaw 工作流执行 | ⚠️ 按需 | 在交接/审核/工具调用处放示例 | 锁定 Agent 间交互格式，但不需要全局塞示例 |

## 5. 应该使用 Few-shot 的情况

### 5.1 输出格式经常不稳定

**场景**：同样的提示词多次运行，输出结构不一致（有时用列表、有时用段落、有时漏字段）。

**为什么 Few-shot 有帮助**：
- 示例直接展示了目标格式，比文字描述「请用表格输出」有效得多；
- 模型会模仿示例的结构、字段顺序、分隔符风格；
- 多次运行验证输出格式稳定性后，如果 Zero-Shot 已经稳定，可以移除示例。

**简短示例**：

```
任务：将客户评价转为结构化数据。

示例：
输入：这款积木拼装顺滑，零件精度很高，孩子很喜欢，就是包装有点简陋。
输出：
| 维度 | 评价 | 情感 |
|------|------|------|
| 拼装体验 | 顺滑、零件精度高 | 正面 |
| 包装 | 简陋 | 负面 |
| 整体 | 孩子很喜欢 | 正面 |
```

### 5.2 需要固定风格

**场景**：品牌营销文案、客服话术、专业报告、个人博客等，需要保持一致的语气、措辞和详细程度。

**为什么 Few-shot 有帮助**：
- 风格是难以用规则文字描述的东西——「专业但亲切」「简洁但有温度」这种描述模型很难准确理解；
- 示例能直接展示目标风格的具体表现（用什么词、多长的句子、什么样的结构）；
- 1 个高质量的风格示例通常就够了。

**适合的场景**：
- 品牌营销文案（语气统一）
- 客服回复模板（话术标准）
- 专业报告（术语和措辞一致性）
- 个人知识库笔记（保持个人写作风格）

### 5.3 需要固定结构

**场景**：报告、表格、卡片、评估表、复盘模板等，输出必须按特定结构呈现。

**为什么 Few-shot 有帮助**：
- 结构化输出的字段顺序、嵌套层级、缩进方式，用文字描述不如直接展示；
- 示例同时锁定了「有什么字段」和「字段怎么排」两个维度；
- 配合 T-CONFIG-001 §7.2 的占位符格式示例，双重锁定效果更好。

### 5.4 用户不知道怎么填

**场景**：模板有多个占位符（`{品类}`、`{时间范围}`、`{指标}`），用户第一次使用时不知道该填什么。

**为什么 Few-shot 有帮助**：
- 示例是最好的「使用说明」——用户直接看示例就知道该怎么填；
- 比「请填写品类名称」这种文字说明更直观；
- 推荐用真实业务数据的填写示范，不要用抽象描述。

### 5.5 有信息不足场景

**场景**：用户输入经常缺失关键信息（如只说「帮我分析一下」但没说分析什么），模型需要正确处理而不是编造。

**为什么 Few-shot 有帮助**：
- 信息不足的处理方式（`[待确认]` 标记、提问澄清、合理假设 + 标注）无法从指令中自然学到；
- 示例能展示「发现信息缺失 → 标记 → 给出兜底建议」的完整链路；
- 推荐 2 个示例：正常输入 + 信息不足输入。

### 5.6 有边界或拒绝场景

**场景**：模板有明确的不适用场景（如「不做销量预测」「不支持医疗诊断」），需要展示正确的拒绝方式。

**为什么 Few-shot 有帮助**：
- 边界输入的拒绝行为需要同时做到：明确拒绝 + 说明原因 + 给出替代方案；
- 模型默认行为是「尽量回答」，不教它拒绝的话会勉强处理超范围需求；
- 推荐 2-3 个示例：正常输入 + 边界/超范围输入（必要时加信息不足输入）。

### 5.7 需要分类或判断标准

**场景**：分类任务、评分任务、评估任务等，模型需要学习判断边界。

**为什么 Few-shot 有帮助**：
- 分类/评分的标准往往是模糊的（如「正面评价」vs「中性评价」的边界在哪里）；
- 示例能展示「这个算正面、那个算中性」的具体判断；
- 每个分类至少 1 个示例，推荐覆盖所有主要分类。

## 6. 不应该使用 Few-shot 的情况

### 6.1 任务非常简单

**场景**：一句话改写、普通总结、简单问答、翻译一句话等。

**原因**：
- 现代 AI 模型 Zero-Shot 能力已经足够处理简单任务；
- 加示例只会增加 token 消耗，不会提升输出质量；
- 如果 Zero-Shot 输出已经稳定，完全不需要 Few-shot。

**替代方案**：Zero-Shot + 占位符格式示例（如果有格式要求的话）。

### 6.2 用户希望自由发挥

**场景**：创意写作、头脑风暴、文案灵感、设计方案等。

**原因**：
- 示例有强烈的「锚定效应」，模型会倾向于模仿示例的内容、结构和风格；
- 用户希望的是多样化输出，而非和示例一样的标准化输出；
- 1 个极端具体的示例可能让模型 10 次输出都围绕示例的主题。

**替代方案**：Zero-Shot + 宽松约束（只约束基本方向，不约束格式和风格）。

### 6.3 模板已经足够清晰

**场景**：T-CONFIG-001 §7.2 的占位符格式示例已经展示了输出格式，模板指令已经很具体。

**原因**：
- 占位符格式示例（如 `| 品类 | 销量 | 环比 |`）已经起到了格式锁定作用；
- 如果 Zero-Shot + 占位符格式示例的输出已经稳定，不需要再加完整 Few-shot 示例；
- 遵循「先用最简方案，不满意再升级」的原则。

### 6.4 示例会污染输出

**场景**：示例中的具体主题、风格、事实可能被模型误当成当前任务内容。

**原因**：
- 模型可能直接复制示例中的具体措辞、数据或主题；
- 例如示例中用了「慢回弹玩具」作为品类，模型可能在新任务中也默认用「慢回弹玩具」；
- 示例越具体，污染风险越高。

**替代方案**：
- 不给示例，用占位符格式示例代替；
- 如果必须给示例，使用非常抽象/通用的内容（如用「产品 A」而非具体品类名）。

### 6.5 输入差异太大

**场景**：开放式问答、多领域通用任务、通用翻译等，输入的变化范围远超示例能覆盖的。

**原因**：
- 2-3 个示例只能覆盖部分情况，反而可能降低泛化能力；
- 模型在「没见过的输入类型」上的表现可能因为锚定效应而变差；
- 示例覆盖不了时，不如不加。

**替代方案**：Zero-Shot + 约束条件（列出必须遵守的规则，而非给出具体示例）。

### 6.6 示例过多导致模板臃肿

**场景**：需要 4+ 个示例才能覆盖所有分类/场景/边界。

**原因**：
- 每增加 1 个示例，prompt 长度增加 100-300 字，token 消耗线性增长；
- 超过 3 个示例的模板难以阅读和维护；
- 过多示例的边际收益递减（第 4 个示例的价值远低于第 1 个）。

**替代方案**：在模板正文中保留最关键的 1-3 个示例，多余示例迁移到案例库（`06-case-studies/`），在模板中附上「更多示例见案例库」的引用。

## 7. Zero-Shot / Few-shot / 案例库边界

### 7.1 三者定位

| 做法 | 定位 | 适用场景 | 放在哪里 |
|------|------|----------|----------|
| **Zero-Shot** | 「不做示例」 | 简单、清楚、低风险任务 | 直接写任务指令 |
| **Few-shot** | 「做 1-3 个示例」 | 需要锁定格式、风格、边界的任务 | 模板 `### 示例` 章节 |
| **案例库** | 「做大量案例沉淀」 | 需要参考多个真实案例、长期复盘、分类训练 | `06-case-studies/` 目录 |

### 7.2 判断表

| 需求 | 推荐做法 | 原因 |
|------|----------|------|
| 只需要快速完成任务 | Zero-Shot | 简单任务直接做，不需要额外准备 |
| 需要稳定输出格式 | 1 个 Few-shot | 示例是最直接的格式锁定手段 |
| 需要展示信息不足处理 | 2 个 Few-shot | 正常 + 信息不足，两种都要 |
| 需要展示拒绝/边界处理 | 2-3 个 Few-shot | 正常 + 边界，必要时加信息不足 |
| 需要覆盖多个分类 | 每类 1 个 Few-shot（不超过 3 个） | 每个分类至少 1 个示例 |
| 示例超过 3 个 | 案例库 | 模板正文不超过 3 个示例 |
| 需要参考多个真实案例 | 案例库 | 案例库是沉淀真实案例的地方 |
| 需要长期复盘 | 案例库 | 复盘结果应归档到案例库 |
| 模板需要新手快速上手 | 1 个最小 Few-shot 示例 | 1 个示例足够展示用法 |
| 任务完全开放、需要创意 | Zero-Shot | 示例会限制思维广度 |

### 7.3 边界迁移规则

```
Zero-Shot → Few-shot → 案例库

迁移条件：
  Zero-Shot → Few-shot：输出格式不稳定 / 需要固定风格 / 用户不会填
  Few-shot → 案例库：  示例数量 > 3 个 / 需要大量真实案例 / 需要长期复盘

不可逆回：
  一旦确定需要 Few-shot，不要退回 Zero-Shot（除非验证发现示例确实无帮助）
  一旦迁移到案例库，不要把案例库内容搬回模板正文
```

## 8. Few-shot 数量判断

### 8.1 数量规则

| 数量 | 适用场景 | 说明 |
|------|----------|------|
| **0 个** | 任务简单，模板 + 占位符格式示例已经足够清楚 | Zero-Shot + 占位符格式示例 |
| **1 个** | 默认推荐，用于锁定输出格式或填写示范 | 最常见的选择，满足大多数模板需求 |
| **2 个** | 需要展示「正常 + 信息不足」或「正常 + 边界」的对比 | 两种输入类型的处理方式不同 |
| **3 个** | 需要展示「正常 + 信息不足 + 边界」的完整覆盖 | Prompt-KB 推荐上限 |
| **> 3 个** | 迁移到案例库 | 不建议塞进模板正文 |

### 8.2 各数量的选择逻辑

- **0 个**：先试 Zero-Shot，如果输出格式稳定、风格一致，就不需要加；
- **1 个**：默认起点，用于展示「输出长什么样」或「怎么填模板」；
- **2 个**：当有明确的信息不足处理或边界拒绝需求时；
- **3 个**：当同时需要覆盖正常、信息不足和边界三种情况时（完整 Pipeline 模板）；
- **超过 3 个**：停止，将多余示例迁移到案例库。

### 8.3 重要提醒

- 普通模板正文**不建议超过 3 个示例**；
- 如果需要 3-5 个以上示例来覆盖分类或场景，应考虑改成案例库或专门的评估集；
- T-CONFIG-002 §6.1 给出了更详细的数量规范，本规范的判断结果应与 T-CONFIG-002 对齐。

## 9. Prompt Chaining 中的 Few-shot 使用

### 9.1 基本原则

**Prompt Chaining 不一定每一步都需要 Few-shot。**

每一步是否需要示例，取决于该步骤的输出是否稳定。只有输出不稳定的步骤才需要示例。

### 9.2 各步骤的判断

| 步骤 | 典型输出 | 是否需要 Few-shot | 推荐示例类型 |
|------|----------|-------------------|-------------|
| **Step 1 需求澄清** | 已知信息 + 待确认问题 + 初步方向 | ⚠️ 可选 | 1 个填写示范（帮助用户理解怎么填原始需求） |
| **Step 2 框架设计** | 分阶段表格（阶段名/目标/关键动作） | ⚠️ 按需 | 如果框架格式不稳定，1 个结构示例 |
| **Step 3 内容生成** | 最终计划/报告/分析的完整内容 | ⚠️ 按需 | 如果风格或格式要求高，1 个完整输出示例 |

### 9.3 实践建议

- **不要每一步都塞 3 个示例**——这是最常见的过度使用；
- **示例应放在最容易出错的步骤**——哪步输出最不稳定，就在哪步放示例；
- **优先锁定 Step 2 的格式**——框架设计往往是输出波动最大的环节；
- **Step 1 的示例价值在于「填写示范」**——帮用户理解怎么描述需求。

### 9.4 T-TEXT-001 的当前状态

T-TEXT-001 v0.4（模糊需求转计划 Pipeline）**不需要强制增加更多 Few-shot 示例**。

原因：
- T-TEXT-001 三步的输出格式已经通过占位符格式示例锁定；
- 参考资料 + `[待确认]` 标记机制已经提供了足够的信息不足处理能力；
- 如果未来发现某一步的输出确实不稳定，可以针对性添加 1 个示例。

## 10. 图像 / 视频提示词中的 Few-shot 判断

⚠️ **本规范只制定判断原则，不创建具体图像/视频提示词模板。** 具体示例格式留给 `03-image-prompts/` 和 `04-video-prompts/` 模块。

### 10.1 图像提示词

适合使用 Few-shot 的情况：

| 场景 | 说明 | 推荐示例类型 |
|------|------|-------------|
| 用户不知道如何描述画面 | 不知道该写什么风格、什么构图 | 1 个画面描述示例 |
| 需要固定风格 | 水彩/油画/赛博朋克等固定风格 | 1 个风格描述示例 |
| 需要学习描述方式 | 不知道怎么描述主体/场景/构图/光线 | 1 个完整描述示例 |
| 需要展示负面提示词 | 不知道该排除什么 | 1 个含负面提示词的示例 |

不需要使用 Few-shot 的情况：
- 用户已经能准确描述画面需求；
- 每次生成风格完全不同；
- 任务是「自由创作」而非「风格统一」。

### 10.2 视频提示词

适合使用 Few-shot 的情况：

| 场景 | 说明 | 推荐示例类型 |
|------|------|-------------|
| 用户不知道如何描述镜头运动 | 不知道该用「推进」「俯拍」「跟随」等 | 1 个镜头描述示例 |
| 需要固定分镜格式 | 多个视频需要统一的分镜结构 | 1 个分镜表格示例 |
| 需要展示时间顺序 | 不知道怎么描述时间轴上的变化 | 1 个时间轴描述示例 |
| 需要展示动作变化和节奏 | 不知道怎么描述主体在时间段内的动作 | 1 个动作描述示例 |

不需要使用 Few-shot 的情况：
- 用户已经是视频专业人员，能准确描述分镜；
- 视频风格每次都不同；
- 任务是「自由创作」而非「格式统一」。

### 10.3 与 T-CONFIG-002 的关系

- T-CONFIG-002 §2 已明确：图像/视频提示词的输入→输出逻辑与文本模板不同，本规范只提供通用判断原则；
- 具体的图像/视频 Few-shot 示例格式，将在 `03-image-prompts/` 和 `04-video-prompts/` 模块建设时单独定义。

## 11. OpenClaw 工作流中的 Few-shot 判断

### 11.1 基本原则

**普通单 Agent 工作流不一定需要 Few-shot。** 只在交互格式不稳定的环节使用。

### 11.2 适合使用 Few-shot 的环节

| 环节 | 说明 | 推荐示例类型 |
|------|------|-------------|
| Agent 间交接格式 | 多 Agent 协作时，一个 Agent 的输出是下一个 Agent 的输入 | 1 个交接示例（锁定格式） |
| 审核 Agent 的评分格式 | 审核需要统一的评分维度和输出结构 | 1 个评分示例（锁定维度和格式） |
| 工具调用前后的输入输出 | 模型需要知道调用工具时传什么参数、拿到结果后怎么处理 | 1 个工具调用示例 |
| human-in-the-loop 确认格式 | 需要人工确认时，展示确认信息的格式 | 1 个确认格式示例 |

### 11.3 不适合使用 Few-shot 的环节

| 环节 | 原因 |
|------|------|
| 简单的单步执行 | Agent 本身有能力处理，不需要示例 |
| 权限确认的实质内容 | 示例不能替代真实权限确认——确认环节必须基于实际操作内容 |
| 动态生成的输出 | 每次内容完全不同，示例覆盖不了 |
| 工具内部的执行逻辑 | 工具调用逻辑应在 OpenClaw 配置中声明，不在提示词示例中展示 |

### 11.4 重要提醒

- **不要让示例替代真实权限确认**——示例展示的是「格式」，不是「权限判断逻辑」；
- human-in-the-loop 的确认必须基于实际操作内容和当前上下文，不能照搬示例中的确认文本；
- 工作流示例推荐数量：每个需要锁定的环节 1 个即可，整个工作流不超过 3 个示例。

## 12. Few-shot 启用决策树

从模板创建/审查开始，逐步判断是否需要 Few-shot：

```
开始 Few-shot 决策
  │
  ├─ ① 任务是否简单清楚？
  │   ├─ 是（输入清楚、一步完成、低风险）→ 优先 Zero-Shot → 验证输出稳定性
  │   │   ├─ 输出稳定 → 不用 Few-shot ✅
  │   │   └─ 输出不稳定 → 继续判断 ②
  │   └─ 否 → 继续判断 ②
  │
  ├─ ② 输出格式是否稳定？
  │   ├─ 是（Zero-Shot 每次输出结构一致）→ 不用 Few-shot ✅
  │   └─ 否 → 继续判断 ③
  │
  ├─ ③ 是否需要固定风格/文风？
  │   ├─ 是 → 使用 1 个 Few-shot（风格锁定） → 跳到 ⑧
  │   └─ 否 → 继续判断 ④
  │
  ├─ ④ 是否需要固定结构（表格/报告/卡片）？
  │   ├─ 是 → 使用 1 个 Few-shot（结构锁定） → 跳到 ⑧
  │   └─ 否 → 继续判断 ⑤
  │
  ├─ ⑤ 用户是否不知道怎么填模板？
  │   ├─ 是 → 使用 1 个 Few-shot（填写示范） → 跳到 ⑧
  │   └─ 否 → 继续判断 ⑥
  │
  ├─ ⑥ 是否有信息不足或边界场景？
  │   ├─ 仅信息不足 → 使用 2 个 Few-shot（正常 + 信息不足） → 跳到 ⑧
  │   ├─ 仅边界/拒绝 → 使用 2 个 Few-shot（正常 + 边界） → 跳到 ⑧
  │   ├─ 两者都有 → 使用 3 个 Few-shot（正常 + 信息不足 + 边界） → 跳到 ⑧
  │   └─ 都没有 → 继续判断 ⑦
  │
  ├─ ⑦ 是否需要分类或判断标准？
  │   ├─ 是 → 每类 1 个 Few-shot（不超过 3 个） → 跳到 ⑧
  │   └─ 否 → 不用 Few-shot ✅
  │
  └─ ⑧ 最终检查
      ├─ 示例是否会污染输出？
      │   ├─ 是 → 考虑用更抽象的示例内容，或不用 Few-shot
      │   └─ 否 → 继续
      ├─ 示例是否超过 3 个？
      │   ├─ 是 → 保留最关键的 3 个，其余迁移到案例库
      │   └─ 否 → 最终选择确定 ✅
```

**最终选择汇总：**
- **不用 Few-shot**：任务简单 + 输出稳定 + 无格式/风格/边界需求
- **使用 1 个**：需要格式锁定 / 风格锁定 / 结构锁定 / 填写示范
- **使用 2 个**：需要展示正常 + 异常（信息不足或边界）
- **使用 3 个**：需要完整覆盖（正常 + 信息不足 + 边界）
- **迁移到案例库**：示例超过 3 个，或需要大量真实案例

## 13. 可复制判断提示词

以下是一个可以直接复制使用的提示词。

**用途**：当你创建新模板时，让 AI 判断是否需要 Few-shot。

```markdown
### 任务
帮我判断以下模板是否需要启用 Few-shot。

### 模板描述
{粘贴模板的任务描述、目标输出、目标用户等信息}

### 判断维度
请逐一回答以下问题，并给出最终建议：

1. **任务复杂度**：这个模板的任务是简单清楚还是比较复杂？
2. **输出稳定性**：Zero-Shot 的输出格式是否稳定？
3. **是否需要固定风格**：输出是否有特定的语气、措辞、专业度要求？
4. **是否需要固定结构**：输出是否有固定的表格/报告/卡片结构？
5. **用户填写难度**：用户是否可能不知道怎么填写模板的占位符？
6. **是否有信息不足场景**：用户输入是否经常缺失关键信息？
7. **是否有边界或拒绝场景**：模板是否有明确的不适用场景？
8. **示例污染风险**：示例内容是否可能被模型误当成当前任务？
9. **是否需要分类/判断标准**：输出是否涉及分类、评分或评估？

### 输出格式
| 维度 | 判断结果 | 原因 |
|------|----------|------|
| 是否需要 Few-shot | {是/否} | {原因} |
| 推荐示例数量 | {0/1/2/3} | {原因} |
| 推荐示例类型 | {正常/信息不足/边界/风格/结构/填写示范} | {原因} |
| 示例应放在哪个步骤 | {步骤名或章节名} | {原因} |
| 是否应迁移到案例库 | {是/否} | {原因} |
| 示例污染风险 | {低/中/高} | {评估} |
| 是否需要参考 T-CONFIG-002 | {是/否} | {原因} |
```

## 14. 常见误判

| # | 误判模式 | 典型表现 | 修正建议 |
|---|----------|----------|----------|
| 1 | **所有模板都加示例** | 不管任务简单还是复杂，每个模板都塞 1-3 个示例 | 用 §12 决策树判断，简单任务优先 Zero-Shot |
| 2 | **完全不加示例** | 认为现代模型不需要示例，所有模板都是纯 Zero-Shot | 检查输出稳定性；格式不稳定时加示例 |
| 3 | **示例太多** | 一个模板塞了 5-10 个示例，prompt 长度爆表 | 控制在 1-3 个，多余迁移到案例库 |
| 4 | **示例过长** | 每个示例 500+ 字，比模板指令还长 | 单个示例控制在 300 字以内（参考 T-CONFIG-002 §9.4） |
| 5 | **示例和任务不相关** | 模板是分析销售数据，示例却用了「翻译英文」 | 示例必须和模板任务类型一致 |
| 6 | **示例替代了规则说明** | 用 10 个示例代替 3 条规则 | 规则用文字写清楚，示例只用于格式锁定 |
| 7 | **示例污染输出** | 模型直接复制示例中的品类名、数据、措辞 | 使用更抽象的示例内容，或换用占位符格式示例 |
| 8 | **示例没有覆盖信息不足** | 只有正常输入的示例，没有信息不足的处理示例 | 信息不足是最有价值的示例类型之一 |
| 9 | **示例没有覆盖边界情况** | 模板有「不适用场景」定义，但示例全是正常输入 | 每个不适用场景至少 1 个对应边界示例 |
| 10 | **应该放案例库却塞进模板正文** | 把 5 个真实案例全部写进模板的示例章节 | 超过 3 个示例时迁移到 `06-case-studies/` |
