## 1. 规范目标

本规范解决以下问题：

| 问题 | 说明 |
|------|------|
| **占位符写法混乱** | 有的模板用 `{变量}`，有的用 `{{变量}}`，有的用 `[变量]`，有的用 `<变量>`，复制使用时需要重新理解 |
| **用户不知道该替换哪里** | 占位符太模糊（如"这里写内容"），或占位符和说明文字混在一起，用户复制后容易遗漏 |
| **输入区边界不清** | 原始需求、背景信息、参考资料、限制条件没有明确分隔，AI 容易混淆来源 |
| **格式描述不一致** | 同样要求"表格输出"，有的模板用文字描述，有的用占位符示例，有的干脆不写 |
| **Markdown / 表格 / JSON / YAML 规则缺失** | 没有统一规定每种输出格式适合什么场景、推荐什么写法 |
| **模板复制后残留说明文字** | 占位符内嵌了大段说明，用户填完内容后说明文字也留在了最终 prompt 里 |

**核心定位**：格式描述的目标是「让 AI 知道输出长什么样，让用户知道该填什么」，用占位符示例替代文字描述，用结构化输入区替代自由填写。

## 3. 与现有规范的关系

Prompt-KB 的配置规范构成一个分层体系，各规范职责清晰、互不重叠：

```
T-CONFIG-001  通用模板结构规范
    │         → 回答「模板整体长什么样」
    │         → 定义 19 个标准章节、分隔符、元数据、版本记录
    │
    ├── T-CONFIG-003  模型类型与提示策略判断规范
    │       → 回答「用什么策略」（Zero-Shot / Few-shot / CoT / Chaining / 多 Agent）
    │
    ├── T-CONFIG-004  Few-shot 适用条件判断规范
    │       → 回答「要不要加示例」
    │
    ├── T-CONFIG-002  Few-shot 示例规范
    │       → 回答「示例怎么写」（数量 / 类型 / 格式 / 验收）
    │
    └── T-CONFIG-005  格式描述与占位符规范  ← 本规范
            → 回答「输入区 / 输出格式 / 占位符怎么写」
```

**关键区分**：

| 规范 | 负责内容 | 不负责内容 |
|------|----------|-----------|
| T-CONFIG-001 | 模板整体结构（19 个章节） | 具体占位符写法、输出格式细节 |
| T-CONFIG-002 | 示例怎么写（输入输出对、三类示例） | 占位符本身怎么命名和设计 |
| T-CONFIG-003 | 选什么策略 | 格式和占位符细节 |
| T-CONFIG-004 | 是否需要 Few-shot | 具体格式怎么描述 |
| T-CONFIG-005 | 占位符格式、输入区结构、输出格式描述 | 示例内容和数量、策略选择 |

**与 T-CONFIG-001 §3.10（输出格式）的关系**：T-CONFIG-001 §3.10 定义了「输出格式」章节的存在和基本写法（推荐用占位符格式示例），本规范进一步细化——占位符用什么符号、怎么命名、输入区怎么组织、JSON / YAML / Markdown / 表格各自怎么写。

**与 T-CONFIG-002 §10（占位符格式示例关系）的关系**：T-CONFIG-002 §10 定义了占位符格式示例和 Few-shot 示例的分工（格式骨架 vs 完整输入输出），本规范进一步定义占位符本身的格式规范。

## 4. 占位符基础规范

### 4.1 统一格式

Prompt-KB 使用**中文方括号** `[中文描述]` 作为标准占位符格式。

| 规则 | 推荐写法 | 不推荐写法 | 原因 |
|------|----------|-----------|------|
| **需要用户替换** | `[主题]` | `{主题}`、`{{主题}}`、`<主题>`、`$主题` | 方括号中文书写最自然，不与 JSON / XML / 模板引擎冲突 |
| **不确定信息** | `[待确认]` | `?`、`TODO`、`（未知）` | 与 T-CONFIG-001 §6 标记规范一致 |
| **合理假设** | `[假设]` | `（瞎猜）`、`default` | 语义明确，与 T-CONFIG-001 §6 对齐 |
| **推断信息** | `[推断]` | `（推的）`、`infer` | 语义明确 |
| **默认值** | `[默认]` | `（随便）`、`fallback` | 语义明确 |

### 4.2 符号选用原则

| 符号 | 是否作为占位符 | 原因 |
|------|-------------|------|
| `[中文]` | ✅ 标准占位符 | 中文书写自然，无歧义 |
| `{英文}` | ⚠️ 仅限 JSON / 代码块内 | JSON 字段名用英文花括号是行业惯例，但在普通模板正文中不使用 |
| `<标签>` | ⚠️ 仅限 XML 标签结构 | 用于 Anthropic API 的 `<example>` 等标签，不作为普通占位符 |
| `{{双花括号}}` | ❌ 不使用 | 与 Mustache / Handlebars 等模板引擎冲突 |
| `$变量` | ❌ 不使用 | 与 Shell / 编程语言变量冲突 |
| `#变量` | ❌ 不使用 | 与 Markdown 标题冲突 |

### 4.3 占位符使用场景

| 场景 | 写法 | 说明 |
|------|------|------|
| 模板输入区 | `[原始需求]` | 用户需要替换的输入内容 |
| 输出格式示例 | `\| [品类] \| [数量] \|` | 展示输出结构，用户不替换 |
| 模板元数据 | `T-[模块]-[序号]` | 模板编号格式 |
| 不确定信息 | `[待确认]` | AI 输出中的不确定标记 |
| 合理假设 | `[假设] [说明假设内容]` | AI 做假设时标注 |
| 参考资料引用 | `[引用来源] [来源名称]` | 引用外部资料时标注 |

## 5. 占位符命名规则

### 5.1 推荐命名

| 推荐写法 | 语义 | 场景示例 |
|----------|------|----------|
| `[主题]` | 一句话可概括 | 学习计划的主题、报告的主题 |
| `[目标用户]` | 明确受众 | 内容的目标读者、产品目标用户 |
| `[时间范围]` | 时间约束 | 上周、Q1、2026 年全年 |
| `[参考资料]` | 外部信息 | 用户提供的文档、笔记、数据 |
| `[限制条件]` | 约束 | 字数限制、风格要求、格式约束 |
| `[输出格式]` | 格式偏好 | 表格、列表、JSON |
| `[数量]` | 数值类 | 销量、预算、人数 |
| `[百分比]` | 比率类 | 环比、同比、转化率 |
| `[名称]` | 命名类 | 品类名称、产品名称 |
| `[位置]` | 地点类 | 区域、城市、渠道 |

### 5.2 不推荐命名

| 不推荐写法 | 问题 | 正确做法 |
|-----------|------|----------|
| `[内容]` | 太模糊，什么内容？ | `[主题]` 或 `[需求描述]` |
| `[东西]` | 太随意，缺乏语义 | `[参考资料]` 或 `[输入数据]` |
| `[随便填]` | 没有约束力 | `[时间范围]` 或 `[目标用户]` |
| `[xxx]` | 占位符本身是占位符 | 直接写 `[具体字段名]` |
| `[这里写很多说明文字]` | 占位符内嵌说明 | 说明文字放占位符外部 |
| `[请填写您的需求，包括主题、时间、限制条件等]` | 复合占位符 | 拆分为多个独立占位符 |

### 5.3 命名原则

| 原则 | 说明 | 正确 ✅ | 错误 ❌ |
|------|------|---------|---------|
| **简短** | 2-6 个字 | `[主题]` | `[请填写您的主题内容]` |
| **中文** | 使用中文，不用英文缩写 | `[品类]` | `[category]` |
| **语义明确** | 一看就知道填什么 | `[时间范围]` | `[日期时间]`（如果只需要日期就说日期） |
| **一个变量** | 一个占位符只表达一个信息 | `[主题]` | `[主题和时间]`（应拆分） |
| **无歧义** | 不会和其他占位符混淆 | `[参考文档]` | `[资料]`（可能指参考资料也可能指参考资料区） |

## 6. 输入区格式规范

### 6.1 标准输入区结构

Prompt-KB 模板的标准输入区由 4 个区块组成，用 `###` 分隔：

```markdown
### 原始需求

```text
[在这里描述你的需求，越具体越好]
```

### 背景信息

```text
[补充说明你的背景、目标或特殊要求。如果没有，写"无"]
```

### 参考资料

```text
[提供相关文档、数据、笔记等内容。如果没有，写"无"]
```

### 限制条件

```text
[列出你的限制要求，如字数、格式、时间等。如果没有，写"无"]
```
```

### 6.2 各区块说明

#### 原始需求（必填）

| 维度 | 说明 |
|------|------|
| **作用** | 用户的核心诉求，模板执行的起点 |
| **为什么用 text 代码块** | 代码块将用户输入与模板指令明确分隔，AI 不会把用户的描述当成指令；同时方便复制粘贴 |
| **推荐写法** | 用户用自然语言描述需求，越具体越好 |
| **常见错误** | ❌ 把需求和背景混在一起；❌ 直接写在代码块外面 |

#### 背景信息（推荐）

| 维度 | 说明 |
|------|------|
| **作用** | 补充上下文，帮助 AI 理解需求的隐含含义 |
| **为什么独立区块** | 背景信息不是核心需求，混在一起会模糊任务焦点 |
| **"无"比留空更好** | 用户不写"无"时，AI 可能不确定是用户忘了填还是确实没有；写"无"明确告知 |
| **常见错误** | ❌ 在背景信息里写具体任务指令 |

#### 参考资料（涉及数据/事实时必填）

| 维度 | 说明 |
|------|------|
| **作用** | 防幻觉机制，限定 AI 只基于给定资料回答（与 T-CONFIG-001 §5 对齐） |
| **为什么独立区块** | 参考资料是 AI 的知识边界，必须和用户需求严格分隔 |
| **输出引用规则** | AI 基于参考资料输出时，须标注 `[引用来源] [来源名称]` |
| **常见错误** | ❌ 参考资料和原始需求混在一起；❌ 参考资料为空时不写"无" |

#### 限制条件（推荐）

| 维度 | 说明 |
|------|------|
| **作用** | 约束 AI 的输出行为（字数、风格、格式、时间等） |
| **为什么单独列出** | 限制条件混在需求里容易被忽略，单独列出确保 AI 重视 |
| **推荐写法** | 每条限制一行，用短句 |
| **常见错误** | ❌ 限制条件太多互相矛盾；❌ 用负面表述（"不要xxx"） |

### 6.3 输入区设计原则

| 原则 | 说明 |
|------|------|
| **代码块包裹** | 所有用户输入放入 `` ```text `` 代码块，分隔用户内容和模板指令 |
| **"无"优于留空** | 空白代码块让 AI 不确定用户是否忘记填写，写"无"明确告知 |
| **独立区块** | 需求、背景、资料、限制各自独立，不混在一起 |
| **有序排列** | 原始需求 → 背景信息 → 参考资料 → 限制条件（从核心到补充） |
| **与 T-CONFIG-001 对齐** | 输入区结构继承 T-CONFIG-001 §4 标准输入区规范 |

## 7. 输出格式描述规范

### 7.1 核心原则

**用占位符格式示例替代文字描述。**

| 方式 | 示例 | 效果 |
|------|------|------|
| ❌ 文字描述 | "请用表格输出，包含品类、销量、环比三列" | AI 可能输出不同结构的表格 |
| ✅ 占位符格式示例 | `\| [品类] \| [数量] \| [百分比] \|` | AI 精确复制结构 |

来源：OpenAI P4（Show output format through examples）。

### 7.2 格式选择总表

| 格式 | 适用场景 | 不适用场景 | 详见章节 |
|------|----------|-----------|----------|
| **Markdown 标题** | 长文档、分节报告、学习计划 | 简单问答、短文本 | §8 |
| **Markdown 表格** | 结构化对比、数据展示、评分表 | 长段落内容、复杂嵌套 | §9 |
| **编号列表** | 步骤说明、排序、清单 | 并列关系、非顺序内容 | §7.4 |
| **JSON** | 机器读取、自动化、API、数据提取 | 面向普通用户阅读、长篇解释 | §10 |
| **YAML** | OpenClaw 配置、工作流参数、Agent 配置 | 长篇正文、非配置类内容 | §11 |
| **自然语言段落** | 简单问答、创意写作、解释说明 | 结构化数据、需要后处理 | §7.5 |

### 7.3 格式描述标准写法

在模板的 `### 输出格式` 章节中，使用以下结构：

```markdown
### 输出格式

[一段话简要说明输出应该包含什么内容，不超过 50 字]

[占位符格式示例]
```

**关键规则**：
- 先用 1-2 句话说明**内容范围**（输出应该包含什么）
- 再用占位符格式示例展示**具体结构**（输出长什么样）
- 占位符格式示例是**骨架**，不是完整内容——用 `[字段名]` 而非具体数据
- 如果内容复杂，分区块展示，每块用 `###` 分隔

### 7.4 编号列表格式规范

| 维度 | 说明 |
|------|------|
| **适用场景** | 步骤说明、排序、清单、流程 |
| **不适用场景** | 并列关系（应用无序列表 `-`）、非顺序内容 |
| **推荐写法** | `1. [步骤名] — [简要说明]` |
| **层级控制** | 最多 3 层嵌套（`1.` → `1.1` → `1.1.1`），超过则改用分节 |
| **常见错误** | ❌ 并列内容用编号列表；❌ 超过 3 层嵌套 |

### 7.5 自然语言段落格式规范

| 维度 | 说明 |
|------|------|
| **适用场景** | 简单问答、创意写作、解释说明、摘要 |
| **不适用场景** | 结构化数据、需要后处理的内容、机器读取 |
| **推荐写法** | 用段落分隔（空行），每段一个要点 |
| **长度控制** | 单段不超过 200 字，超过则分节 |
| **常见错误** | ❌ 把结构化数据写成自然语言（机器无法解析）；❌ 单段过长无分层 |

## 8. Markdown 输出格式规范

### 8.1 标题层级规范

| 规则 | 说明 |
|------|------|
| **不超过 4 级** | `##` → `###` → `####` → `#####`，不要用 `######` |
| **连续递进** | 不要跳级（如 `##` 直接跳到 `####`） |
| **一级标题 `#` 保留给文档标题** | 模板正文从 `##` 开始 |
| **同级标题数量适中** | 每个 `##` 下至少 2 段内容 |

### 8.2 推荐写法

```markdown
## [报告标题]

[一段摘要，不超过 100 字]

### [第一节标题]

[正文内容]

### [第二节标题]

[正文内容]

---
[分节线，用于长文档的分隔]
```

### 8.3 长文档建议

| 建议 | 说明 |
|------|------|
| **包含目录或摘要** | 超过 3 个 `###` 时，在开头加摘要 |
| **分节线 `---`** | 超过 500 字时，用分节线划分逻辑块 |
| **总结收尾** | 长文档末尾用"总结"或"下一步建议"收尾 |

### 8.4 常见错误

| 错误 | 正确做法 |
|------|----------|
| ❌ 标题层级混乱（## 后面直接 ####） | ✅ 连续递进 |
| ❌ 一级标题 `#` 出现在正文 | ✅ `#` 只用于文档标题 |
| ❌ 同级标题下只有一句话 | ✅ 合并到上一节或补充内容 |
| ❌ 全文 7-8 级标题 | ✅ 控制在 4 级以内，超过则拆分文档 |

## 9. 表格输出格式规范

### 9.1 适合表格的场景

| 场景 | 示例 |
|------|------|
| **短字段对比** | 品类销量对比、优缺点对比 |
| **结构化评分** | 多维度评分表、打分矩阵 |
| **清单展示** | 任务清单、检查清单、状态跟踪 |
| **分类汇总** | 按类型/区域/时间的汇总数据 |

### 9.2 不适合表格的场景

| 场景 | 替代方案 |
|------|----------|
| **字段内容很长（> 50 字）** | 改用分节列表或独立段落 |
| **复杂嵌套关系** | 改用层级列表或 JSON |
| **需要解释说明** | 表格只放数据，说明放表格前后 |
| **动态增减字段** | 改用 JSON 或 YAML |

### 9.3 列数控制

| 列数 | 建议 |
|------|------|
| **2-3 列** | 最佳可读性，手机端也能正常显示 |
| **4-5 列** | 可接受，桌面端正常显示 |
| **> 5 列** | 不推荐，水平滚动体验差；应拆分为多表或改用列表 |

### 9.4 推荐写法

```markdown
### 输出格式

按以下表格格式输出：

| [列名 1] | [列名 2] | [列名 3] |
|----------|----------|----------|
| [示例值] | [示例值] | [示例值] |
```

**关键规则**：
- 表头用中括号占位符，示例行用 `[示例值]` 或具体示例数据
- 分隔行 `|---|` 必须有
- 列数不超过 5 列
- 如果内容很长，应改成分节列表

### 9.5 常见错误

| 错误 | 正确做法 |
|------|----------|
| ❌ 文字描述"用表格输出"但不给格式示例 | ✅ 直接给占位符表格骨架 |
| ❌ 表格 8-10 列 | ✅ 控制在 5 列以内 |
| ❌ 表格单元格内放长段落 | ✅ 单元格内容不超过 50 字 |
| ❌ 把复杂报告全部塞进一个表格 | ✅ 按主题拆分为多个小表格 |

## 10. JSON 输出格式规范

### 10.1 适合使用 JSON 的场景

| 场景 | 说明 |
|------|------|
| **机器读取** | 后端程序解析 AI 输出 |
| **自动化流程** | Pipeline 中间步骤传递数据 |
| **API 输入输出** | 作为 API 的请求/响应格式 |
| **数据提取** | 从非结构化文本中提取结构化数据 |
| **结构化标注** | 分类、实体识别、情感分析等标注任务 |

### 10.2 不适合使用 JSON 的场景

| 场景 | 替代方案 |
|------|----------|
| **面向普通用户阅读** | Markdown 表格或自然语言 |
| **长篇解释** | Markdown 分节 |
| **不确定字段很多的任务** | 先用 Markdown 草案，确认字段后再用 JSON |
| **创意写作** | 自然语言段落 |

### 10.3 JSON 输出模板

```markdown
### 输出格式

以 JSON 格式输出，严格遵循以下结构：

```json
{
  "[字段名1]": "[字段说明1]",
  "[字段名2]": "[字段说明2]",
  "[字段名3]": {
    "[子字段名]": "[子字段说明]"
  }
}
```

**不要输出 JSON 代码块以外的任何文字。**
```

### 10.4 JSON 规则

| 规则 | 说明 |
|------|------|
| **字段名用英文** | `category`、`sales_count`、`growth_rate` |
| **字段名下划线风格** | `sales_count` 而非 `salesCount`（与 YAML 配置一致） |
| **值用中文** | `"慢回弹玩具"` 而非 `"slow rebound toy"`（面向中文用户） |
| **不确定信息标记** | 值写 `"[待确认]"` |
| **不要 JSON 注释** | JSON 标准（RFC 8259）不支持注释，`//` 或 `/* */` 会导致解析失败 |
| **纯净输出** | 不输出 JSON 外的多余解释文字，除非用户明确要求 |
| **数组用方括号** | 多值字段使用 `[]` 数组 |

### 10.5 常见错误

| 错误 | 正确做法 |
|------|----------|
| ❌ JSON 中写 `// 这是注释` | ✅ JSON 不支持注释，把说明放在模板正文中 |
| ❌ 字段名用中文 `"品类": "慢回弹"` | ✅ `"category": "慢回弹玩具"` |
| ❌ JSON 外面加"以下是分析结果：" | ✅ 只输出 JSON，不加解释文字 |
| ❌ 不确定字段直接编造值 | ✅ 值写 `"[待确认]"` |
| ❌ 混用单引号 `'value'` | ✅ JSON 标准使用双引号 `"value"` |

## 11. YAML 输出格式规范

### 11.1 适合使用 YAML 的场景

| 场景 | 说明 |
|------|------|
| **OpenClaw 配置** | Agent 定义、工作流参数 |
| **工作流参数** | Pipeline 步骤配置、条件分支 |
| **Agent 配置** | 角色定义、工具列表、权限设置 |
| **规则设置** | 约束条件、边界定义、配置文件 |

### 11.2 YAML 输出模板

```markdown
### 输出格式

以 YAML 格式输出，严格遵循以下结构：

```yaml
[配置名]:
  [字段名1]: "[值说明1]"
  [字段名2]: "[值说明2]"
  [子配置名]:
    [子字段名]: "[子值说明]"
```
```

### 11.3 YAML 规则

| 规则 | 说明 |
|------|------|
| **适合配置，不适合正文** | YAML 是配置语言，不要用 YAML 写长篇正文内容 |
| **缩进必须一致** | 统一使用 2 空格缩进，不要混用 Tab 和空格 |
| **不要混用 Tab 和空格** | YAML 对缩进敏感，混用会导致解析错误 |
| **字段名要稳定** | 不要在同一个模板的不同输出中使用不同字段名 |
| **列表用短横线** | `- [项]` 表示数组项 |
| **布尔值用 true/false** | 不要用 `是/否` 或 `yes/no` |

### 11.4 常见错误

| 错误 | 正确做法 |
|------|----------|
| ❌ 用 YAML 写长篇正文 | ✅ 正文用 Markdown，配置用 YAML |
| ❌ 缩进混乱（Tab 和空格混用） | ✅ 统一 2 空格缩进 |
| ❌ 列表项缩进不一致 | ✅ 所有 `-` 对齐 |
| ❌ 字段名每次输出都变 | ✅ 字段名在模板中固定，输出时保持一致 |

## 16. 常见错误

### 16.1 占位符类错误

| # | 错误 | 正确做法 |
|---|------|----------|
| 1 | 占位符太模糊（`[内容]`、`[东西]`） | 用语义明确的占位符（`[主题]`、`[参考资料]`） |

| 3 | 混用不同占位符符号（`{name}` 和 `[名称]` 混用） | 同一模板内统一使用中文方括号 |
| 4 | 占位符内嵌说明文字（`[时间范围: 写上周/Q1/全年]`） | 说明放占位符外部，占位符内只放字段名 |

### 16.2 输出格式类错误

| # | 错误 | 正确做法 |

| 5 | 只写"结构化输出"但不说明结构 | 给出具体的占位符格式示例（表格/JSON/YAML 骨架） |
| 6 | 表格列太多（8-10 列） | 控制在 3-5 列，超过则拆分 |
| 7 | 把复杂报告全部塞进一个表格 | 按主题拆分为多个小表格或改用分节列表 |
| 8 | 标题层级混乱（`##` 跳到 `####`） | 连续递进，不超过 4 级 |

### 16.3 JSON / YAML 类错误

| # | 错误 | 正确做法 |
|---|------|----------|
| 9 | JSON 中写注释（`// 这是说明`） | JSON 不支持注释，说明放模板正文 |
| 10 | YAML 缩进混乱（Tab 和空格混用） | 统一 2 空格缩进 |

### 16.4 输入区类错误

| # | 错误 | 正确做法 |
|---|------|----------|
| 11 | 图像/视频任务仍然使用纯文本任务格式 | 使用图像/视频专用输入区（见 §12/§13） |
