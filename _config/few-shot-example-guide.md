## 1. 规范目标

本规范解决以下问题：

| 问题 | 说明 |
|------|------|
| **示例随意堆砌** | 模板作者不知道该给几个、给什么样的示例，导致有的模板 0 个示例，有的塞了 10+ 个 |
| **示例污染输出** | 示例过于具体，模型直接复制示例内容而非理解任务规则 |
| **格式锁定失败** | 示例格式与目标输入格式不一致，模型无法学到正确的输出格式 |
| **用户不会填模板** | 示例太完美或太抽象，用户看了仍然不知道该怎么填写占位符 |
| **边界情况缺失** | 示例全是正常情况，模型遇到信息不足、超范围等输入时不会处理 |
| **团队格式不对齐** | 不同模板的示例写法各异，无法横向对比和维护 |

**核心定位**：示例不是「教模型知识」，而是「锁定格式、风格、边界和判断标准」。一份好的示例让模型学会套路，而非背诵答案。

## 2. 适用范围

### 强制适用

本规范强制适用于以下文件中的「示例」章节：

| 类型 | 说明 |
|------|------|
| **文本类提示词模板** | `prompt-kb/02-text-prompts/templates/` 下所有 `.md` 文件中的 `### 示例` 章节 |
| **Prompt Chaining 模板** | 涉及多步骤串联的 Pipeline 模板中各步骤的示例 |
| **带固定输出格式的模板** | 对输出格式有严格要求的模板（如表格、JSON、结构化报告） |
| **带参考资料输入的模板** | 包含防幻觉机制的模板中，示例需展示引用和标记规范 |
| **图像 / 视频提示词模板** | `prompt-kb/03-image-prompts/`、`prompt-kb/04-video-prompts/` 下模板中的输入输出示例 |
| **OpenClaw 工作流模板** | 任何作为 OpenClaw Agent 输入输出样例的示例 |

> **图像 / 视频模板的特化说明**：图像和视频提示词的"输入→输出"逻辑与文本模板不同（如文字描述→生成图片、分镜脚本→视频）。本规范 §7-§9 的通用原则（格式锁定、真实场景、长度控制等）仍然适用，但**输入输出块的具体格式**将在对应模块（`03-image-prompts/`、`04-video-prompts/`）创建时补完特化规则。
>
> 具体而言：文本任务通常是"输入 → 期望输出"，而图像任务更常见的是"画面需求 → 图像提示词"，视频任务更常见的是"视频需求 → 分镜 / 镜头提示词"。因此，**本规范只提供通用示例原则；具体图像 / 视频示例格式应在后续 `03-image-prompts` 和 `04-video-prompts` 模块中单独定义**，不在此强行覆盖。

### 暂不强制适用

以下文件类型不受本规范约束，但参考执行：

| 类型 | 原因 | 说明 |
|------|------|------|
| **普通知识笔记** | 属于知识沉淀，不含执行性示例 | 如 `01-fundamentals/` 下的方法论文档 |
| **案例复盘** | 已归档的实战案例，有独立结构 | 如 `06-case-studies/` 下案例文件 |
| **资源索引** | 纯链接/目录列表，无示例需求 | 如 `00-index/` 下导航文件 |
| **临时草稿** | 尚未定稿，不适合过早规范 | 如 `_drafts/` 目录下的文件 |

## 3. 什么是 Few-shot 示例

### 3.1 概念解释

**Zero-shot（零样本）**：不给任何示例，直接下指令让模型干活。

```
任务：判断以下评论的情感倾向（正面/负面/中性）。
输入：这个产品还不错，性价比很高。
```

**Few-shot（少样本）**：在正式提问前，先给模型看 1-3 个「输入→输出」的范例，让它照着做。

```
任务：判断评论的情感倾向。

示例 1：
输入：这个太棒了！
输出：正面

示例 2：
真差劲，再也不买了。
输出：负面

输入：这个产品还不错，性价比很高。
输出：
```

### 3.2 示例的作用

| 作用 | 说明 |
|------|------|
| **锁定格式** | 让模型知道输出应该长什么样（表格/列表/JSON/纯文字） |
| **锁定风格** | 让模型知道用什么语气、什么详细程度 |
| **锁定边界** | 让模型知道什么该做、什么不该做 |
| **锁定判断标准** | 让模型知道如何对输入做分类或评估 |

### 3.3 示例不是越多越好

DAIR.AI 引用 Min et al. (2022) 的研究发现：

| 发现 | 说明 | 实际意义 |
|------|------|----------|
| **格式比正确性更重要** | 即使示例的标签标错了，只要格式一致，模型仍能学会正确的方向 | 先把格式搞对，再纠结内容是否完美 |
| **随机标签 > 没有标签** | 给乱标的示例都比不给示例好 | 宁可随便给几个示例，也不要纯 Zero-shot |
| **真实分布 > 均匀分布** | 从真实业务数据中取示例比均匀构造更好 | 用真实场景做示例效果最好 |

**一句话总结：示例的作用是「锁定格式和方向」，不是「传授知识」。格式一致性 > 内容准确性。**

## 4. 什么时候需要 Few-shot

### 4.1 推荐使用 Few-shot 的场景

| # | 场景 | 说明 | 示例类型 |
|---|------|------|----------|
| 1 | **输出格式经常不稳定** | 同样的 prompt 多次运行，输出的结构不一致 | 示例 A（正常输入） |
| 2 | **用户不知道怎么填写输入** | 占位符太抽象，用户看了不知道该填什么 | 示例 A（带真实数据的填充示范） |
| 3 | **需要固定风格** | 语气、详细程度、专业度需要保持一致 | 示例 A（正常输入） |
| 4 | **需要固定结构** | 输出必须按特定模板（表格/分节/JSON） | 示例 A（正常输入） |
| 5 | **任务有边界情况** | 信息不足、超范围、矛盾输入等需要特殊处理 | 示例 B + 示例 C |
| 6 | **需要模型学习判断标准** | 分类/评分/评估等需要一致的标准 | 示例 A（覆盖多类别） |
| 7 | **需要减少歧义** | 指令可能有多种理解方式，示例能消除歧义 | 示例 A（正常输入） |
| 8 | **需要对齐团队格式** | 多人协作时，示例统一输出标准 | 示例 A（正常输入） |

### 4.2 判断表

| 情况 | 是否建议 Few-shot | 原因 |
|------|-------------------|------|
| 任务简单，Zero-shot 输出格式已经稳定 | ❌ 不需要 | 加了也是浪费 token |
| 输出格式每次都不一样 | ✅ 强烈建议 | 示例是最直接的格式控制手段 |
| 有明确的表格/JSON/结构化输出要求 | ✅ 建议 | 用示例展示目标格式，比文字描述有效 |
| 用户第一次使用模板，不知道填什么 | ✅ 建议 | 示例是最好的使用说明 |
| 任务涉及分类/评分/判断 | ✅ 建议 | 示例能传达判断标准 |
| 输入可能信息不足或超出范围 | ✅ 建议 | 示例 B/C 展示异常处理方式 |
| 模型是推理模型（GPT-5/Claude Opus） | ⚠️ 按需 | 推理模型 Zero-shot 能力更强，可能不需要示例 |
| 用户希望自由发挥 | ❌ 不需要 | 示例会限制创造性 |

## 5. 什么时候不需要 Few-shot

### 5.1 不推荐使用 Few-shot 的场景

| # | 场景 | 原因 | 替代方案 |
|---|------|------|----------|
| 1 | **任务非常简单** | 如翻译一句话、总结一段文字，Zero-shot 足够 | 直接 Zero-shot |
| 2 | **用户希望自由发挥** | 如创意写作、头脑风暴，示例会限制思路 | Zero-shot + 宽松约束 |
| 3 | **示例容易限制创意** | 如文案创作、设计灵感，固定格式反而降低质量 | 只约束基本结构，内容自由 |
| 4 | **示例内容容易污染答案** | 模型可能直接复制示例中的具体内容 | 不给示例，或给出非常抽象的示例 |
| 5 | **模板指令已经足够清晰** | 分隔符 + 占位符格式示例 + 具体约束已经很完整 | 不需要额外示例 |
| 6 | **输入差异太大，示例难以覆盖** | 如开放式问答、多领域通用任务 | 用约束条件代替示例 |
| 7 | **示例会让 prompt 过长** | 每个 token 都有成本，示例 token 性价比低 | 用占位符格式示例代替完整示例 |

### 5.2 判断表

| 情况 | 是否建议 Few-shot | 原因 |
|------|-------------------|------|
| 任务简单且 Zero-shot 结果稳定 | ❌ 不需要 | 没必要增加 token 消耗 |
| 用户明确说"随便写"或"自由发挥" | ❌ 不需要 | 示例会限制创造性 |
| 示例中的具体内容可能被模型照抄 | ❌ 不建议 | 用抽象占位符代替具体内容 |
| 模板已经有清晰的占位符格式示例 | ❌ 不需要 | T-CONFIG-001 §7.2 的占位符格式示例已经起到示例作用 |
| prompt 总 token 已超过 2000 | ❌ 不建议 | 示例会进一步增加负担，应拆分为多步 Pipeline |
| 涉及创意/发散思维 | ❌ 不建议 | 示例锚定效应过强，限制思维广度 |
| 输入变化极大（如通用翻译） | ⚠️ 谨慎 | 示例可能只覆盖部分情况，反而降低泛化能力 |

## 6. 示例数量规范

### 6.1 Prompt-KB 数量规则

| 数量 | 适用场景 | 说明 |
|------|----------|------|
| **1 个** | 默认 | 绝大多数模板只需要 1 个正常输入示例即可 |
| **2 个** | 需要展示对比 | 一个正常 + 一个边界/异常，或两种不同类别的输入 |
| **3 个** | 复杂模板 | 正常输入 + 信息不足 + 边界输入，三类全覆盖 |
| **> 3 个** | 仅限特殊模板 | 分类训练/多类别模板可适当增加，但不建议超过 5 个 |

### 6.2 各数量适合什么

#### 1 个示例：格式基准

**适合：**
- 模板格式简单清晰（单一表格/列表）
- 任务目标明确（如"提取以下字段"）
- 用户只需要知道"输出长什么样"

**作用：** 建立「输出应该长这样」的基准印象。

**不适合：**
- 有多种可能的输入类型
- 有异常处理需求
- 有分类/评分标准需要传达

#### 2 个示例：对比或分类

**适合：**
- 需要展示两种不同输入类型的处理方式（如"正面评论 vs 负面评论"）
- 需要展示"正常情况 vs 信息不足"的对比
- 任务有 2-3 种可能的输出类别

**作用：** 建立输入差异 → 输出差异的映射关系。

**搭配建议：**
- 示例 A（正常输入）+ 示例 B（信息不足/边界输入）
- 或示例 A（类别 1）+ 示例 B（类别 2）

#### 3 个示例：完整覆盖（Prompt-KB 推荐上限）

**适合：**
- 复杂模板（如 T-TEXT-001 Pipeline）
- 有多种异常处理需求
- 分类任务需要覆盖多个类别
- 团队协作模板需要统一标准

**推荐组合（Prompt-KB 标准三件套）：**
1. 示例 A：正常输入 → 建立格式基准
2. 示例 B：信息不足输入 → 训练异常处理
3. 示例 C：边界/超范围输入 → 训练拒绝能力

**作用：** 让模型同时学会"正常怎么做、信息不够怎么办、不该做的事怎么办"。

#### 超过 3 个：特殊情况处理

**仅限以下情况：**
- 分类任务需要覆盖 4+ 个类别（每个类别至少 1 个示例）
- 专门用于"示例教学"的训练模板
- 多步 Pipeline 中各步骤需要独立示例

**处理原则：**
- 不建议把超过 3 个示例直接塞进模板正文
- 超过 3 个时，应将多余示例移入**案例库**（`06-case-studies/`）
- 在模板正文中只保留最关键的 3 个，并附上「更多示例见案例库」的引用

> **关于与 T-CONFIG-001 的上限差异**：T-CONFIG-001 §8.3 提到"3-5 个最佳，不要超过 10 个"，适用于更宽泛的训练 / 分类 / 评估场景。本规范（T-CONFIG-002）面向 **Prompt-KB 模板正文**，采用更保守的默认规则：正文中建议 1 个示例，复杂模板可放 2-3 个，超过 3 个时优先考虑迁移到案例库。两份规范不冲突——T-CONFIG-001 给出的是上限警戒线，T-CONFIG-002 给出的是模板正文的推荐默认值。

## 7. 三类标准示例

Prompt-KB 推荐所有模板的示例章节按以下三类组织。不是每个模板都需要三类齐全——根据实际需要选择。

### 7.1 示例 A：正常输入示例

**作用：** 展示模板最典型的使用方式，建立输出格式基准。

**适合放在：**
- 几乎所有需要 Few-shot 的模板（必选）
- 格式敏感型模板（如固定表格输出、JSON 输出）

**推荐格式：**

```markdown
#### 示例 1：正常输入

**输入：**
```
{真实或贴近真实的用户输入，内容具体、信息完整}
```

**输出：**
```
{期望的完整输出，严格遵循目标格式}
```
```

**设计原则：**
- 输入内容要**具体真实**，不要用抽象描述（如"一个评论"→改为"这款积木拼装顺滑，零件精度很高"）
- 输出内容要**完整展示目标格式**，包含所有必要字段和结构
- 输入和输出的**格式要与目标问题完全一致**（同样的引导语、同样的分隔符）
- 示例内容优先从**真实业务场景**中提取

**常见错误：**

| 错误 | 正确做法 |
|------|----------|
| ❌ 输入太抽象："一个关于产品的评论" | ✅ 输入具体："这款积木拼装顺滑，零件精度很高，孩子很喜欢" |
| ❌ 输出不完整：只写了部分字段 | ✅ 输出完整：包含所有字段的完整示例 |
| ❌ 输入输出格式不一致 | ✅ 目标问题的呈现方式与示例完全一致 |
| ❌ 示例太完美，不贴近真实 | ✅ 用真实业务数据的格式做示例 |

---

### 7.2 示例 B：信息不足示例

**作用：** 展示当用户输入缺失关键信息时，模型应如何处理——提问澄清、做合理假设并标注、或给出默认值。

**适合放在：**
- 需要用户填写多个占位符的模板
- 涉及 `[待确认]` / `[假设]` / `[推断]` / `[默认]` 标记的模板
- 有「需求澄清」步骤的 Pipeline 模板

**推荐格式：**

```markdown
#### 示例 2：信息不足

**输入：**
```
{故意缺失关键信息的用户输入，模拟真实场景中的模糊需求}
```

**输出：**
```
{展示模型如何识别缺失信息、如何用 [待确认] 标记、
如何提出澄清问题或做合理假设并标注来源}
```
```

**设计原则：**
- 输入应**故意缺失 1-2 个关键信息**（如缺时间、缺目标、缺背景）
- 输出应展示 **`[待确认]` 标记的使用方式**（与 T-CONFIG-001 §6 标记规范对齐）
- 输出应展示 **信息不足时的兜底策略**（提问 / 假设 + 标注 / 给默认值 + 标注）
- 模拟真实用户最常见的「说了一半」场景

**常见错误：**

| 错误 | 正确做法 |
|------|----------|
| ❌ 模型直接编造缺失信息 | ✅ 用 `[待确认]` 标记，或提问澄清 |
| ❌ 标记格式不统一（混用全角半角） | ✅ 统一使用半角 `[待确认]` / `[假设]` / `[推断]` / `[默认]` |
| ❌ 输入缺失太多信息，变成极端场景 | ✅ 只缺失 1-2 个关键信息，保持合理 |
| ❌ 输出只标记不处理 | ✅ 标记 + 给出选项/建议/默认值 |

---

### 7.3 示例 C：边界输入示例

**作用：** 展示当用户输入超出模板适用范围、包含矛盾信息、格式混乱、或属于高风险操作时，模型应如何拒绝或安全处理。

**适合放在：**
- 有明确「不适用场景」定义的模板
- 涉及高风险操作（如数据删除、外部通知）的模板
- 输入类型多样的模板

**推荐格式：**

```markdown
#### 示例 3：边界/超范围输入

**输入：**
```
{超出模板适用范围的输入，如：
- 完全不属于本模板场景的需求
- 包含矛盾信息的需求
- 高风险操作需求
- 格式完全混乱的需求}
```

**输出：**
```
{展示模型如何识别超范围、如何拒绝、如何给出替代建议}
```
```

**设计原则：**
- 每个模板的「不适用场景」（T-CONFIG-001 §3.4）至少对应 1 个边界示例
- 输出应**明确拒绝**而非勉强回答
- 输出应**给出替代方案**而非只说"不适合"（与 T-CONFIG-001 §3.4 规范对齐）
- 展示**安全的兜底行为**——不编造、不过度发挥

**常见错误：**

| 错误 | 正确做法 |
|------|----------|
| ❌ 模型勉强回答超范围需求 | ✅ 明确说明"这超出了本模板的范围"并给出替代方案 |
| ❌ 只拒绝不给替代方案 | ✅ 拒绝 + 推荐替代模板/方法 |
| ❌ 边界示例与「不适用场景」不对应 | ✅ 每个「不适用场景」至少有 1 个对应边界示例 |
| ❌ 拒绝语气生硬 | ✅ 礼貌说明原因 + 建议下一步行动 |

---

### 7.4 三类示例的选择指南

不是每个模板都需要三类齐全。按需选择：

| 模板特征 | 推荐示例组合 | 原因 |
|----------|-------------|------|
| 简单格式锁定模板 | 仅示例 A | 只需要展示输出格式 |
| 带占位符的模板 | 示例 A + 示例 B | 用户需要知道信息不足时怎么处理 |
| 有明确不适用场景的模板 | 示例 A + 示例 C | 需要展示拒绝能力 |
| 完整 Pipeline 模板 | 示例 A + B + C | 全覆盖，三类都要 |
| 创意/发散类模板 | 不加示例或仅示例 A | 示例会限制创造性 |

## 8. Few-shot 示例标准格式

### 8.1 模板内的示例章节标准格式

所有 Prompt-KB 模板的 `### 示例` 章节必须遵循以下结构：

```markdown
### 示例

#### 示例 1：{示例类型标题，如"正常输入" / "信息不足" / "边界输入"}

**输入：**
```text
这里放用户输入的内容。格式必须与模板的「原始需求」区块一致。
```

**输出：**
```text
这里放期望的模型输出。格式必须与模板的「输出格式」区块一致。
```

---

#### 示例 2：{示例类型标题}

**输入：**
```text
...
```

**输出：**
```text
...
```
```

### 8.2 格式要求

| 要求 | 说明 |
|------|------|
| **标题层级** | 用 `####` 作为示例标题层级（在 `### 示例` 之下） |
| **输入输出标记** | 用 `**输入：**` 和 `**输出：**` 加粗标注 |
| **内容包裹** | 用 `` ```text `` 代码块包裹输入输出内容 |
| **示例间分隔** | 用 `---` 分隔不同示例 |
| **编号** | 用"示例 1"、"示例 2"编号，不用中文序号 |
| **输入格式一致性** | 示例输入的格式必须与模板的「原始需求」占位符格式一致 |
| **输出格式一致性** | 示例输出的格式必须与模板的「输出格式」区块完全一致 |

### 8.3 API 场景的可选格式

API 调用场景下，可使用 XML `<example>` 标签包裹（与 Anthropic 规范对齐）：

```xml
<example>
  <input>用户输入内容</input>
  <output>期望输出内容</output>
</example>
```

**Prompt-KB 默认选择**：Markdown 格式（`**输入：**` + 代码块）。理由：中文手写友好度高，与 T-CONFIG-001 §4.2 的 Markdown `###` 策略一致。

## 9. 示例设计原则

### 9.1 格式锁定优先

**核心原则：示例的第一目标是让模型学会「输出长什么样」，而不是学会「答案是什么」。**

| 维度 | 说明 |
|------|------|
| 格式一致性 | 所有示例的输出格式必须完全一致——同样的表头、同样的分隔符、同样的缩进 |
| 结构一致性 | 所有示例的输出结构必须完全一致——同样的字段顺序、同样的嵌套层级 |
| 引导语一致性 | 示例与目标问题使用同样的引导语和呈现方式 |

**反模式：**
- ❌ 示例 1 用表格输出，示例 2 用列表输出
- ❌ 示例的输入用 `Q: xxx? A: yyy` 格式，目标问题用 `请判断以下文本：`

### 9.2 真实场景优先

**核心原则：示例内容应从真实业务场景中提取，而非刻意构造「完美示例」。**

| 维度 | 说明 |
|------|------|
| 内容真实 | 用实际工作/学习中的真实输入，不要为了示例编造 |
| 长度真实 | 示例长度应接近真实输入的平均长度，不要太短也不要太长 |
| 不完美 | 真实输入通常有口语化、略带模糊的特征，保持这些特征 |

**反模式：**
- ❌ 示例输入完美无缺："请分析2026年Q1华东区域慢回弹玩具品类的销量环比变化"（太书面化）
- ✅ 示例输入贴近真实："帮我看看上周慢回弹卖得怎么样，环比有没有跌"（更贴近实际）

### 9.3 边界覆盖优先

**核心原则：如果只能选 2 个示例，选「1 个正常 + 1 个边界」比「2 个正常」更有价值。**

原因：
- 正常情况模型通常能处理（Zero-shot 就行）
- 边界情况才是 Few-shot 真正发挥价值的地方
- 信息不足和超范围输入的处理方式无法从指令中自然学到

### 9.4 示例长度控制

| 示例部分 | 推荐长度 | 说明 |
|----------|----------|------|
| 输入 | 20-100 字 | 接近真实输入的平均长度 |
| 输出 | 50-200 字 | 展示完整格式即可，不要长篇大论 |
| 单个示例总计 | 不超过 300 字 | 超过则应精简，避免消耗过多 token |

### 9.5 示例放置位置

遵循 T-CONFIG-001 §10.1 的 System Prompt / User Message 分工原则：

| 内容类型 | 放置位置 | 原因 |
|----------|----------|------|
| 示例（静态、不频繁变更） | 可放在 System Prompt | 减少每次调用的动态内容 |
| 示例（动态、按需调整） | 放在 User Message | 便于根据不同输入类型切换示例 |
| Prompt-KB 模板中的示例 | 放在 `### 示例` 章节，位于 `### 输出格式` 之后 | 位置靠近输出格式，强化格式锁定效果 |

## 10. 示例与占位符格式示例的关系

T-CONFIG-001 §7.2 定义了「占位符格式示例」（如 `\| 品类 \| 销量 \| 环比 \|`），这是一种轻量级的格式展示方式。

两者不冲突，但有明确分工：

| 维度 | 占位符格式示例 | Few-shot 示例 |
|------|---------------|---------------|
| **位置** | `### 输出格式` 章节 | `### 示例` 章节 |
| **内容** | 用 `{占位符}` 展示格式骨架 | 用真实/接近真实的数据展示完整效果 |
| **作用** | 告诉模型"长什么样" | 告诉模型"怎么做到这样" |
| **token 消耗** | 低（只有格式骨架） | 中-高（包含完整输入输出） |
| **是否必须** | ⭐⭐⭐ 推荐 | ⭐ 可选 |
| **优先级** | 先有占位符格式示例，再考虑加 Few-shot 示例 | 占位符格式示例不足时，用 Few-shot 补充 |

**推荐策略：**
1. 先写占位符格式示例（T-CONFIG-001 §7.2）——这是最低成本
2. 如果 Zero-shot 输出仍然不稳定，再加 Few-shot 示例补充
3. Few-shot 示例中应与占位符格式示例保持一致的格式

## 11. 示例验收标准

创建或修改示例时，使用以下清单验收：

### 完整性检查

- [ ] 每个示例都有明确的「输入」和「输出」
- [ ] 输入格式与模板的「原始需求」区块一致
- [ ] 输出格式与模板的「输出格式」区块一致
- [ ] 示例数量符合 §6 的数量规范（默认 1 个，最多 3 个）

### 质量检查

- [ ] 示例内容贴近真实场景，非刻意构造
- [ ] 示例长度合理（单示例 ≤ 300 字）
- [ ] 各示例间格式完全一致
- [ ] 示例与目标问题的呈现方式一致（引导语、分隔符）
- [ ] 如有 `[待确认]` 等标记，使用半角格式且与 T-CONFIG-001 §6 一致

### 边界覆盖检查

- [ ] 模板的「不适用场景」至少有 1 个对应的边界示例（如有示例 C）
- [ ] 信息不足示例展示了正确的标记和兜底策略（如有示例 B）
- [ ] 正常输入示例展示了完整的期望输出格式（如有示例 A）

### 功能验证

- [ ] 用未出现在示例中的新输入测试，确认模型能泛化
- [ ] 多次运行验证输出格式稳定性
- [ ] 确认模型不会直接复制示例中的具体内容

## 12. 常见错误速查

### 12.1 设计类错误

| # | 错误 | 正确做法 |
|---|------|----------|
| 1 | 示例全是正常情况，不覆盖边界 | 至少 1 个示例展示异常处理 |
| 2 | 示例内容太抽象（如"一个评论"） | 用具体真实内容（如"这款积木拼装顺滑..."） |
| 3 | 示例与目标输入格式不一致 | 目标问题与示例用完全相同的呈现方式 |
| 4 | 示例过多（> 5 个），token 爆炸 | 控制在 1-3 个，多余示例移入案例库 |
| 5 | 示例过于具体，模型照抄答案 | 示例展示格式套路，而非具体答案 |

### 12.2 格式类错误

| # | 错误 | 正确做法 |
|---|------|----------|
| 1 | 不用代码块包裹输入输出内容 | 用 `` ```text `` 代码块包裹 |
| 2 | 示例间没有分隔 | 用 `---` 分隔不同示例 |
| 3 | 不标注"输入"和"输出" | 用 `**输入：**` 和 `**输出：**` 加粗标注 |
| 4 | 混用 XML 和 Markdown 格式 | 单一模板只选一种风格 |
| 5 | 标记格式不统一 | 统一使用半角 `[待确认]` / `[假设]` / `[推断]` / `[默认]` |

### 12.3 逻辑类错误

| # | 错误 | 正确做法 |
|---|------|----------|
| 1 | 信息不足示例中模型编造答案 | 用 `[待确认]` 标记或提问澄清 |
| 2 | 边界示例中模型勉强回答超范围需求 | 明确拒绝 + 给出替代方案 |
| 3 | 示例输入过于极端（全空或全错） | 保持合理的信息缺失程度 |
| 4 | 不验证就固化示例 | 用未出现在示例中的新输入验证泛化能力 |

```

### B.1.5 带参考资料输入的标准示例格式

当模板包含「参考资料」输入块时，示例 1 应同时展示参考资料区块与引用标注方式：

````markdown
#### 示例 1：正常输入（含参考资料）

**参考资料：**
```text
在这里放用户提供的资料、笔记、文档摘要或会议记录。
如果没有参考资料，写"无"。
```

**输入：**
```text
在这里放用户的原始需求。
```

**输出：**
```text
在这里放基于参考资料生成的期望输出。
[引用来源] 数据/结论来自上方参考资料中的 [来源名称]。
不确定信息统一标记为 [待确认]。
```
````

**设计原则（带参考资料示例的 4 条必须遵守）：**
- 示例必须展示"基于参考资料回答"——输出中须有 `[引用来源]` 标注；
- 不能把参考资料中没有的信息写成事实——缺口必须标记 `[待确认]` 或说明信息不足；
- 参考资料不足时，要说明缺口，而非凭空补全；
- 不确定内容统一标记为 `[待确认]`，与 T-CONFIG-001 §6 标记规范对齐。
