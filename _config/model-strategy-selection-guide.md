## 1. 规范目标

本规范解决以下问题：

| 问题 | 说明 |
|------|------|
| **策略选择盲目** | 所有任务都套用复杂 Prompt Chaining，简单任务也拆三步 |
| **CoT 滥用** | 为推理模型手动加「让我们一步步思考」，导致输出冗余 |
| **Few-shot 过度使用** | 输出格式已经稳定仍加示例，浪费 token |
| **多 Agent 过早引入** | 单 Agent 顺序执行就能搞定，却引入了编排复杂度 |
| **模型类型混淆** | 不清楚什么时候用推理模型、什么时候用普通模型 |
| **工具调用边界不清** | 不知道哪些操作必须人工确认，哪些可以自动执行 |
| **图像/视频任务沿用文本逻辑** | 把文本提示词结构照搬到多模态任务，效果差 |

**核心定位**：在写提示词之前，先判断「应该用哪种策略」。本规范是 T-CONFIG-001（写模板结构）的前置决策层。

---

## 2. 适用范围

### 强制适用

本规范强制适用于以下决策场景：

| 类型 | 说明 |
|------|------|
| **新建模板前的策略选择** | 在写 `### 技术选型` 章节之前，先用本规范判断应该用什么技术 |
| **OpenClaw 工作流设计** | 决定用单 Agent 还是多 Agent、是否启用工具调用 |
| **现有模板的策略审查** | 检查是否有过度工程化（如简单模板用了 Prompt Chaining） |
| **模型选型决策** | 适用于普通对话模型、高级推理模型、长上下文模型、多模态模型、工具调用 / Agent 模型、图像生成模型和视频生成模型的策略选择 |

### 暂不强制适用

以下场景参考本规范，但不强制：

| 类型 | 原因 |
|------|------|
| **纯知识笔记** | 不属于提示词工程决策范围 |
| **案例复盘** | 已固化的最优策略，不需要重新判断 |
| **临时草稿** | 未到策略选择阶段 |

## 3. 任务复杂度分级

将任务分为 5 个复杂度等级，每个等级对应不同的推荐策略。

| 等级 | 名称 | 任务特征 | 推荐策略 | 不推荐策略 | 示例 |
|------|------|----------|----------|-------------|------|
| **L1** | 简单直接任务 | 输入清楚、输出明确、一步完成 | Zero-Shot | Few-Shot、CoT、Chaining | 翻译一句话、总结一段文字、判断情感 |
| **L2** | 格式明确任务 | 输出格式要求严格，但逻辑不复杂 | Zero-Shot + 占位符格式示例，不满意再加 Few-Shot | CoT、Chaining | 销售数据转表格、提取字段、格式转换 |
| **L3** | 模糊需求任务 | 用户输入不完整，需要先澄清再执行 | Prompt Chaining（先澄清 → 再执行） | 直接 Zero-Shot | 「帮我做个学习计划」但没说学什么、有多少时间 |
| **L4** | 多步骤复杂任务 | 任务可拆成多个阶段，上一步输出是下一步输入 | Prompt Chaining + 人工确认门 | 单次 Zero-Shot | 周报自动化（数据→分析→报告）、项目计划 |
| **L5** | 高风险/高价值任务 | 涉及删除操作、外部通知、代码执行、长期自动化 | 单/多 Agent + 工具调用 + human-in-the-loop | 纯 Prompt Chaining 不带确认 | 数据库操作、邮件群发、自动化 Pipeline |

## 4. 提示策略选择总表

| 任务情况 | 推荐策略 | 不推荐策略 | 原因 |
|----------|----------|-------------|------|
| 输入清楚、任务简单 | Zero-Shot | Few-Shot、CoT | 简单任务 Zero-Shot 已足够，加策略只会增加 token |
| 输出格式经常不稳定 | Few-Shot（1-3 个示例） | 直接改模板结构 | Few-Shot 是最直接的格式锁定手段 |
| 需要固定风格 | Few-Shot（展示风格示例） | CoT | Few-Shot 能同时锁定格式+风格，CoT 不负责风格 |
| 用户需求模糊 | Prompt Chaining（Step 1 澄清） | 直接 Zero-Shot | 模糊需求直接生成会得到泛泛而谈的结果 |
| 任务包含多个阶段 | Prompt Chaining | 单次 Zero-Shot | 拆成多步每步更可控，且支持中间检查 |
| 任务需要参考资料 | Zero-Shot + 参考资料区（T-CONFIG-001 §5） | 纯 Few-Shot | 参考资料机制比示例更能防止幻觉 |
| 需要比较多个方案 | 结构化分析（先内部分析，只输出结论） | 展示完整 CoT | 用户不需要看推理过程，只需要结论 |
| 需要工具调用 | ReAct 模式（Thought → Action → Observation） | 纯文本生成 | 工具调用需要模型主动决定「调什么 API」 |
| 需要多角色审查 | 多 Agent（各角色独立 Agent） | 单 Agent 模拟多角色 | 单 Agent 模拟多角色容易混淆立场 |
| 涉及文件/邮箱/日历等高权限操作 | 单 Agent + human-in-the-loop | 全自动多 Agent | 高权限操作必须人工确认 |
| 需要长期自动化 | 多 Agent + 消息队列 | 单次 Prompt Chaining | 长期自动化需要容错、状态管理、断点续跑 |
| 图像生成任务 | 专用图像提示词结构（主体+风格+构图+光线） | 文本任务结构照抄 | 图像提示词的核心是视觉描述，不是逻辑推理 |
| 视频生成任务 | 专用视频提示词结构（分镜+镜头运动+时长） | 文本任务结构照抄 | 视频提示词需要时间维度，文本结构不适用 |

## 5. Zero-Shot 使用规范

### 什么时候使用 Zero-Shot

**适合：**
- 任务简单，模型在训练中见过类似任务
- 用户目标明确，输入信息完整
- 输出格式不复杂（或已用占位符格式示例锁定）
- 风险低，出错后果不严重
- 不需要示例来锁定格式

**不适合：**
- 输出格式不稳定（同样的 prompt 多次运行结果不一致）
- 用户需求模糊（不知道要什么、没说清约束）
- 多步骤任务（一步做不完）
- 需要固定风格（如特定语气、专业术语体系）
- 需要严谨处理参考资料（Zero-Shot 容易忽视参考资料边界）

### Zero-Shot 基础模板（可复制）

```markdown
### 任务
{动词开头的一句话描述，如"总结以下客户评价的要点"}

### 输入
{需要 AI 处理的内容}

### 输出格式
{用占位符格式示例展示期望格式，不要用文字描述}
```

**关键点**：Zero-Shot 不是「完全无结构」，而是「不用示例」。占位符格式示例（T-CONFIG-001 §7.2）是 Zero-Shot 场景的最佳实践。

## 6. Few-Shot 使用规范

### 什么时候使用 Few-Shot

**适合：**
- 输出格式经常不稳定（同样的 prompt 多次运行，输出结构不一致）
- 用户不知道怎么填写模板（占位符太抽象）
- 需要固定风格（语气、详细程度、专业度）
- 需要锁定判断标准（分类/评分/评估类任务）
- 需要覆盖边界情况（信息不足、超范围输入）

**引用 T-CONFIG-002 的核心原则：**
- 默认 1 个示例；复杂模板 2-3 个；超过 3 个迁移到案例库
- 示例必须区分输入和期望输出
- 示例用于格式锁定，不是教模型知识
- 示例内容要贴近真实场景，不要刻意构造完美示例

### Few-Shot 基础模板（可复制）

```markdown
### 任务
{任务描述}

### 示例
#### 示例 1：正常输入
**输入：**
```
{具体、完整的用户输入示例}
```
**输出：**
```
{严格遵循目标格式的期望输出}
```

### 输出格式
{占位符格式示例}

### 原始需求
{用户的实际输入}
```

**关键点**：Few-Shot 示例放在 `### 示例` 章节，位于 `### 输出格式` 之后、`### 原始需求` 之前（T-CONFIG-001 §4.2 区块顺序）。

## 7. Prompt Chaining 使用规范

### 什么时候使用 Prompt Chaining

**适合：**
- 任务可以拆成多个阶段，上一步输出会影响下一步
- 需要在中间步骤插入人工确认（human-in-the-loop）
- 需要先澄清需求再生成方案（模糊需求类任务）
- 需要生成计划、报告、分析等结构化输出

**不适合：**
- 简单问答（如「这个单词什么意思」）
- 一步就能完成的改写/翻译/总结
- 没有必要拆分的小任务（拆分反而增加延迟和 token 消耗）

### 三步通用结构

```
Step 1：需求澄清
  └─ 把用户的模糊输入变成结构化需求文档
  └─ 输出：已知信息 + 待确认问题清单 + 初步方向

Step 2：框架/方案设计
  └─ 基于 Step 1 的结果，设计阶段化框架
  └─ 输出：分阶段表格（阶段名/目标/关键动作/时长/完成标志）

Step 3：详细生成/执行
  └─ 基于 Step 1 + Step 2，填充完整内容
  └─ 输出：最终可执行的计划/报告/分析
```

### T-TEXT-001 就是 Prompt Chaining 的稳定示例

T-TEXT-001 v0.4（模糊需求转计划 Pipeline）是 Prompt Chaining 在 Prompt-KB 中的最佳实践：
- 三步结构清晰（需求澄清 → 计划框架 → 详细生成）
- 每步独立可验证
- Step 1 → Step 2 之间设计了人工确认门
- 参考资料机制和 `[待确认]` 标记贯穿三步

**引用方式**：在新建模板的 `### 技术选型` 章节，可以写：「参考 T-TEXT-001 的 Prompt Chaining 结构」。

## 8. Thinking / CoT 使用规范

### CoT / Thinking 的边界

**原则：**
- 不默认要求模型展示完整思考过程
- 优先使用「请先在内部完成必要分析，然后只输出结构化结果」
- 只有在以下情况才展示分析步骤：
  - 教学场景（需要看模型的推理逻辑）
  - 方案比较（需要看模型为什么推荐 A 而非 B）
  - 审查场景（需要验证模型的判断依据）
  - 用户明确要求「展示思考过程」
- 对支持推理强度参数的模型，优先使用平台能力，而不是手写「让我们一步一步思考」

### 推荐写法 vs 不推荐写法

**✅ 推荐（对非推理模型）：**
```
请先在内部完成必要分析，然后只输出结构化结果。
如果需要展示分析过程，在输出中用 ### 分析过程 区块单独呈现。
```

**✅ 推荐（对推理模型）：**
```
请完成分析，只输出结论和结构化结果。
（不需要加「让我们一步步思考」——模型已内置推理能力）
```

**❌ 不推荐（对所有模型）：**
```
让我们一步一步地思考。
{任务描述}
```
> 对内置推理能力的模型多余，且可能导致输出冗余；
> 对非推理模型可以保留，但应放在提示词末尾，而非开头。

### 推理强度参数替代 CoT（重要）

当使用支持 `reasoning_effort` / `extended thinking` / `thinking budget` 等参数的模型时：
- **不要**在手写提示词里加 CoT 引导
- **改为**在 API 调用或 OpenClaw 配置中设置推理强度参数

| 模型类型 | 参数类型 | 使用说明 |
|----------|----------|----------|
| 支持推理强度参数的模型 | `reasoning_effort` 或平台等效参数 | 根据任务复杂度选择推理强度，例如平衡 / 高强度；不要手写要求模型展示完整 CoT |
| 支持扩展思考的模型 | `thinking_budget` 或平台等效参数 | 根据任务价值和复杂度设置思考预算；不要手写要求模型展示完整 CoT |
| 内置推理能力的模型 | 无，模型内部处理 | 直接描述任务、约束和输出格式，不需要额外 CoT 引导 |
| 普通对话模型 | 无专门推理参数 | 使用结构化分析提示，但只要求输出结论、依据和步骤摘要 |

> ⚠️ **注意：长期规范中不要写死具体模型版本号。** 模型名称、版本和参数接口会变化，应优先使用「模型类型」和「平台能力」来描述。具体模型参数以当前平台文档为准。

## 9. 工具调用使用规范

### 什么时候需要工具调用

**适合：**
- 需要读取文件（如 Excel、PDF、Markdown）
- 需要搜索资料（如网页搜索、知识库检索）
- 需要调用 API（如天气、股票、地图）
- 需要执行代码（如数据分析、格式转换）
- 需要处理表格、文档、图片（多模态工具）
- 需要访问邮箱、日历、任务系统（高权限操作）

### 必须 human-in-the-loop 的情况

以下操作在执行前**必须**获得用户确认：

| 操作类型 | 原因 |
|----------|------|
| **删除文件** | 不可恢复，误删后果严重 |
| **发送邮件/消息** | 可能发送给错误对象，内容可能不当 |
| **修改日历** | 可能影响他人行程 |
| **执行系统命令** | 可能破坏系统环境 |
| **访问敏感数据** | 隐私和合规风险 |
| **安装插件或 skill** | 可能引入安全问题 |
| **外部系统写入操作** | 数据写入后难以撤回 |

### OpenClaw 工具调用前的确认模板（可复制）

```yaml
human_confirmation:
  required_when:
    - file_deletion
    - email_sending
    - calendar_modification
    - command_execution
    - sensitive_data_access
    - external_write_operation
  confirmation_format: |
    以下操作即将执行，请确认：
    {操作描述}
    输入「确认」继续，输入「取消」中止。
```

## 10. 单 Agent / 多 Agent 判断规范

### 默认策略

**普通任务优先单 Agent；多 Agent 只在有明确收益时使用。**

| 情况 | 单 Agent | 多 Agent | 原因 |
|------|----------|-----------|------|
| 简单总结/翻译/格式化 | ✅ 推荐 | ❌ 不需要 | 单 Agent 延迟更低，成本更小 |
| 计划生成（如 T-TEXT-001） | ✅ 推荐 | ❌ 不需要 | 三步强依赖串行，多 Agent 无收益 |
| 市场调研（需多角度分析） | ⚠️ 可用 | ✅ 推荐 | 可并行调研多个维度，最后汇总 |
| 代码审查（需多视角） | ⚠️ 可用 | ✅ 推荐 | 安全审查、性能审查、规范审查可并行 |
| 长文档分析（需多维度） | ⚠️ 可用 | ✅ 推荐 | 摘要、关键词、行动项可并行提取 |
| 内容生产流水线（采集→编辑→审核→发布） | ❌ 不适合 | ✅ 推荐 | 各阶段职责明确，可并行处理不同任务 |
| 高风险决策（如数据库操作） | ✅ 推荐 | ⚠️ 可用 | 单 Agent + 人工确认门更可控 |
| 多工具自动化（如周报全自动） | ❌ 不适合 | ✅ 推荐 | 需要状态管理、错误恢复、断点续跑 |

### 判断原则

1. **有可并行子任务吗？** → 有 → 考虑多 Agent
2. **各步骤强依赖串行吗？** → 是 → 用单 Agent 顺序执行
3. **需要多角色审查吗？** → 是 → 考虑多 Agent
4. **需要长期运行吗？** → 是 → 考虑多 Agent + 状态管理
5. **以上都不满足？** → 用单 Agent

## 11. 模型类型判断

⚠️ **本规范不写死具体模型版本号。** 模型名称和能力会变化，应优先使用「模型类型」来描述。

### 11.1 普通对话模型

| 维度 | 说明 |
|------|------|
| **适合任务** | L1 简单任务、L2 格式明确任务 |
| **提示词重点** | 具体描述任务、提供占位符格式示例 |
| **不推荐做法** | 要求展示完整 CoT（模型不具备强推理能力） |
| **是否需要参考资料** | 可选（防幻觉推荐加） |
| **是否需要结构化输出** | 推荐（用占位符格式示例锁定） |
| **是否需要人工确认** | L1 不需要，L2 可选 |

### 11.2 高级推理模型

| 维度 | 说明 |
|------|------|
| **适合任务** | L4 多步骤复杂任务、L5 高风险任务、需要深度推理的任务 |
| **提示词重点** | 描述任务即可，不需要 CoT 引导；通过 `reasoning_effort` 参数控制推理深度 |
| **不推荐做法** | 手写「让我们一步步思考」；过度约束推理过程 |
| **是否需要参考资料** | 推荐（推理模型更容易遵守参考资料边界） |
| **是否需要结构化输出** | 推荐（推理模型格式稳定性更好） |
| **是否需要人工确认** | L5 任务必须在关键节点确认 |

### 11.3 长上下文模型

| 维度 | 说明 |
|------|------|
| **适合任务** | 长文档分析、多轮对话、需要引用原文的任务 |
| **提示词重点** | 文档放在顶部、问题放在末尾（Anthropic 原则）；要求先引用后回答 |
| **不推荐做法** | 把 10+ 页文档直接塞进 prompt（应先摘要） |
| **是否需要参考资料** | 必须（长上下文模型的核心价值就是处理参考资料） |
| **是否需要结构化输出** | 推荐（用 `<relevant_quotes>` + `<answer>` 结构） |
| **是否需要人工确认** | 可选（视任务风险等级而定） |

### 11.4 多模态模型

| 维度 | 说明 |
|------|------|
| **适合任务** | 图像理解、视频理解、图文混合输入 |
| **提示词重点** | 用自然语言描述视觉任务；图像直接传入，不需要 base64 描述 |
| **不推荐做法** | 用文本任务的逻辑处理多模态输入（如要求图像任务输出纯文本推理链） |
| **是否需要参考资料** | 可选 |
| **是否需要结构化输出** | 视任务而定（图像描述可以自由文本，图像分析推荐结构化） |
| **是否需要人工确认** | 涉及生成/编辑操作时推荐确认 |

### 11.5 工具调用 / Agent 模型

| 维度 | 说明 |
|------|------|
| **适合任务** | ReAct 模式（思考→行动→观察）、多步骤工具编排 |
| **提示词重点** | 明确描述可用工具列表、工具调用格式、观察结果处理方式 |
| **不推荐做法** | 在提示词里硬编码工具调用逻辑（应在 OpenClaw 配置中声明工具） |
| **是否需要参考资料** | 可选（工具返回结果可作为参考资料） |
| **是否需要结构化输出** | 推荐（工具调用结果需要结构化解析） |
| **是否需要人工确认** | 高权限工具调用前必须确认 |

### 11.6 图像生成模型

| 维度 | 说明 |
|------|------|
| **适合任务** | 文生图、图生图、图像编辑 |
| **提示词重点** | 视觉主体描述 + 风格 + 构图 + 光线 + 色彩；负面提示词 |
| **不推荐做法** | 沿用文本任务结构（如「先分析再生成」对图像生成不适用） |
| **是否需要参考资料** | 可选（参考图用 `image` 传入，不放在文本里描述） |
| **是否需要结构化输出** | 不适用（输出是图像，不是文本） |
| **是否需要人工确认** | 生成后推荐确认（图像生成成本高，避免浪费） |

### 11.7 视频生成模型

| 维度 | 说明 |
|------|------|
| **适合任务** | 文生视频、图生视频、视频编辑 |
| **提示词重点** | 时间顺序 + 镜头运动 + 动作变化 + 分镜脚本 + 时长和节奏 |
| **不推荐做法** | 用文本任务的「段落结构」描述视频（视频需要镜头语言） |
| **是否需要参考资料** | 可选（参考视频用文件传入） |
| **是否需要结构化输出** | 推荐（分镜脚本用表格结构） |
| **是否需要人工确认** | 生成前推荐确认（视频生成成本极高） |

## 12. 图像 / 视频任务的特殊判断

⚠️ **本规范只制定判断原则，不创建具体图像/视频提示词模板。**

### 图像任务判断

在决定图像提示词策略前，先回答以下问题：

| 问题 | 如果是 → 策略建议 |
|------|-------------------|
| 是否重点在视觉主体？ | 是 → 提示词以主体描述为核心，风格/构图为辅 |
| 是否需要风格、构图、光线、色彩？ | 是 → 在提示词中明确声明这些维度（不用「美观」「高级」等模糊词） |
| 是否需要负面提示词？ | 是 → 单独列出「不要什么」（如「不要文字」「不要水印」） |
| 是否需要参考图？ | 是 → 用 `image` 参数传入参考图，提示词中描述「与参考图的关系」（如「保持构图」「保持风格」） |

### 视频任务判断

| 问题 | 如果是 → 策略建议 |
|------|-------------------|
| 是否需要时间顺序？ | 是 → 提示词用「第 X 秒：描述」的时间轴结构 |
| 是否需要镜头运动？ | 是 → 明确声明镜头类型（如「缓慢推进」「俯拍」「跟随」） |
| 是否需要动作变化？ | 是 → 描述主体在时间段内的动作变化，而非静态画面 |
| 是否需要分镜？ | 是 → 用表格结构：`分镜编号 | 时长 | 画面描述 | 镜头运动` |
| 是否需要时长和节奏控制？ | 是 → 明确总时长和节奏感（如「前 3 秒慢，后 5 秒快切」） |

**说明**：
- 图像/视频模块后续会单独建设（计划在 `03-image-prompts/` 和 `04-video-prompts/` 目录）
- 本规范只负责策略选择，不定义具体提示词格式
- 图像/视频提示词的核心差异：**文本任务是逻辑推理，图像/视频任务是视觉描述**

## 13. 决策树

从用户需求开始，逐步判断应该用哪种提示策略。

```
用户提出需求
  │
  ├─ 任务是否清楚？
  │   ├─ 否 → 用 Prompt Chaining（先澄清再执行）
  │   └─ 是 → 继续判断
  │
  ├─ 是否需要固定格式？
  │   ├─ 是 → Zero-Shot 先试，不满意加 Few-Shot
  │   └─ 否 → 继续判断
  │
  ├─ 是否需要多步骤？
  │   ├─ 是 → 用 Prompt Chaining
  │   └─ 否 → 继续判断
  │
  ├─ 是否需要参考资料？
  │   ├─ 是 → Zero-Shot + 参考资料区（防幻觉）
  │   └─ 否 → 继续判断
  │
  ├─ 是否需要工具调用？
  │   ├─ 是 → 用 ReAct 模式（Thought → Action → Observation）
  │   └─ 否 → 继续判断
  │
  ├─ 是否需要人工确认？
  │   ├─ 是 → 单 Agent + human-in-the-loop（高权限操作）
  │   └─ 否 → 继续判断
  │
  └─ 是否需要多 Agent？
      ├─ 是 → 有可并行子任务 + 多角色审查 + 长期自动化
      └─ 否 → 单 Agent（默认）
```

**最终输出推荐策略**：根据决策树的路径，输出对应的策略组合。

## 14. 可复制判断提示词

以下是一个可以直接复制使用的「任务策略判断提示词」。

**用途**：当你有一个新任务时，可以先让 AI 判断应该用哪种提示策略。

```markdown
### 任务
帮我判断以下需求应该用哪种提示策略。

### 用户需求
{粘贴用户的原始需求}

### 判断维度
请逐一回答以下问题，并给出推荐策略：

1. **任务复杂度等级**（L1 简单直接 / L2 格式明确 / L3 模糊需求 / L4 多步骤 / L5 高风险）
2. **推荐策略**（Zero-Shot / Few-Shot / Prompt Chaining / CoT / 工具调用 / 单 Agent / 多 Agent）
3. **不推荐策略**（容易过度使用的策略）
4. **是否需要参考资料**（是/否 + 原因）
5. **是否需要 Few-Shot**（是/否 + 需要几个示例）
6. **是否需要 Prompt Chaining**（是/否 + 需要几步）
7. **是否需要工具调用**（是/否 + 需要哪些工具）
8. **是否需要单 Agent / 多 Agent**（推荐方案 + 原因）
9. **是否需要人工确认**（是/否 + 哪些节点需要确认）

### 输出格式
| 维度 | 判断结果 | 原因 |
|------|----------|------|
| 复杂度等级 | {L1-L5} | {原因} |
| 推荐策略 | {策略名} | {原因} |
| 不推荐策略 | {策略名} | {原因} |
| 是否需要参考资料 | {是/否} | {原因} |
| 是否需要 Few-Shot | {是/否} | {原因} |
| 是否需要 Prompt Chaining | {是/否} | {原因} |
| 是否需要工具调用 | {是/否} | {原因} |
| 单 Agent / 多 Agent | {推荐} | {原因} |
| 是否需要人工确认 | {是/否} | {原因} |
```

## 15. 常见误判

| # | 误判模式 | 典型表现 | 修正建议 |
| ---|------------|----------|----------|
| 1 | **简单任务过度工程化** | L1 任务用了 Prompt Chaining + CoT + Few-Shot | 先试 Zero-Shot，满意就停 |
| 2 | **模糊任务直接生成最终答案** | 用户说「帮我做个计划」但没说任何约束，AI 直接给了泛泛的计划 | 用 Prompt Chaining Step 1 先澄清 |
| 3 | **所有任务都加 Few-Shot** | 输出格式已经稳定仍加 3 个示例 | Few-Shot 是格式锁定手段，不是默认必选 |
| 4 | **所有任务都要求 CoT** | 翻译一句话也要求展示思考过程 | CoT 仅用于复杂推理任务；推理模型用 effort 参数替代 |
| 5 | **过早使用多 Agent** | 单 Agent 顺序执行就能搞定，却引入了 3 个 Agent | 默认单 Agent；多 Agent 只在有明确并行收益时使用 |
| 6 | **忽略参考资料** | 需要事实准确性的任务没加参考资料区 | 数据查询/分析/报告类任务必须加参考资料区（T-CONFIG-001 §5） |
| 7 | **忽略 human-in-the-loop** | 高权限操作（删除/发送/修改日历）没有确认环节 | 参考 T-CONFIG-001 §10.2 的确认位置表 |
| 8 | **图像/视频任务仍用文本任务结构** | 图像提示词写了「先分析再生成」 | 图像/视频提示词核心是视觉描述，不是逻辑推理链 |
| 9 | **长上下文任务不做分块** | 把 50 页 PDF 直接塞进 prompt | 长文档先摘要，再用参考资料（T-CONFIG-001 §5.3） |
