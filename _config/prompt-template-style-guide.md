## 1. 规范目标

本规范解决以下问题：

| 问题 | 说明 |
|------|------|
| **结构不一致** | 每个模板结构各异，复制使用时需要重新理解成本高 |
| **防幻觉能力缺失** | 模板缺少参考资料机制，AI 输出时容易胡编乱造 |
| **分隔符混乱** | 有的模板用 `###`，有的用 `---`，有的用 `"""`，有的干脆没有 |
| **不兼容现代模型** | 为 GPT-4 设计的模板，未考虑推理模型的特殊性 |
| **无法系统验收** | 没有统一的质量标准，模板改来改去无法判断改好还是改坏了 |
| **中文手写不友好** | XML 标签虽严格，但手写时门槛高，中文用户应优先用 Markdown `###` |

**核心定位**：把提示词模板当作「接口契约」来设计，而不是当作「对话」来随意发挥。

## 2. 适用范围

### 强制适用

本规范强制适用于以下文件：

| 类型 | 说明 |
|------|------|
| **文本类提示词模板** | `prompt-kb/02-text-prompts/templates/` 下所有 `.md` 文件 |
| **OpenClaw 单 Agent 工作流模板** | 任何作为 OpenClaw Agent system prompt 的模板 |
| **Prompt Chaining 类模板** | 涉及多步骤串联的 Pipeline 模板 |
| **带参考资料的任务模板** | 包含防幻觉机制的模板 |
| **后续新增模板** | 从本规范生效后创建的所有新模板 |

### 暂不强制适用

以下文件类型不受本规范约束，但参考执行：

| 类型 | 原因 | 说明 |
|------|------|------|
| **已稳定的历史案例文件** | 已通过验收，不宜频繁改动 | 如 `06-case-studies/` 下已归档案例 |
| **技术学习笔记** | 属于知识沉淀，非提示词执行文件 | 如 DAIR.AI/Anthropic 校准笔记 |
| **原始资源摘要** | 忠实记录来源原文，非二次创作 | 如 `_raw/` 目录下的原始翻译 |
| **特殊工具调用配置文件** | 属于 YAML/JSON 配置，非手写模板 | 如 OpenClaw 的 `.yaml` 工作流配置 |

## 3. 通用模板推荐结构

Prompt-KB 未来所有新模板必须遵循以下 19 个标准章节。按「是否必填」分为三类：

- ⭐⭐⭐ **必须**（缺失则模板不可用）
- ⭐⭐ **推荐**（缺失则模板功能受限）
- ⭐ **可选**（按需添加）

### 3.1 元数据区（文件头，必填）

```markdown
> **模板编号**: T-XXX-000
> **版本**: v0.1
> **创建日期**: YYYY-MM-DD
> **更新日期**: YYYY-MM-DD
> **本次更新**: [变更说明]
> **来源案例**: [关联案例文件路径，无则写"无"]
> **推荐技术**: [Prompt Chaining / Zero-Shot / Few-Shot 等]
> **理论依据**: [方法论文档路径]
```

**作用**：版本追踪、关联定位、技术选型说明。

**是否必填**：⭐⭐⭐ **必须**

**推荐写法**：
- 模板编号遵循 `T-{模块}-{序号}` 规则（见 §17 版本记录规范）
- 每次实质性修改递增版本号并记录变更说明
- 来源案例用于追溯模板的实战来源

**常见错误**：
- ❌ 不写模板编号，导致无法关联
- ❌ 版本号长期停留在 v0.1，不更新
- ❌ 变更说明写"修复"而非具体改了哪里

---

### 3.2 模板定位（必填）

```markdown
## 1. 模板定位

**解决什么问题：**
[一句话说清楚本模板的核心价值]

**核心矛盾（可选）：**
[用户的什么输入特征与期望输出之间存在鸿沟]

**不解决什么问题：**
- ❌ [问题 A]
- ❌ [问题 B]
```

**作用**：让使用者一眼判断是否应该使用本模板。

**是否必填**：⭐⭐⭐ **必须**

**推荐写法**：
- 「解决什么问题」：一句话，不要超过 30 字
- 「核心矛盾」：用对比方式说明（如"用户说不清楚要什么格式 vs 高质量输出需要明确格式"）
- 「不解决什么问题」：列出最常见的错误期望，减少滥用

**常见错误**：
- ❌ 写成模板功能描述而非用户价值（如"本模板使用三步 Prompt Chaining"）
- ❌ 不写「不解决什么问题」，导致用户把模板用在错误场景

---

### 3.3 适用场景（必填）

```markdown
## 2. 适用场景

本模板适用于所有符合以下特征的任务：

| 场景类型 | 典型口语需求 | 匹配度 | 说明 |
|----------|-------------|--------|------|
| [类型 A] | [口语示例] | ⭐⭐⭐⭐⭐ | [说明] |
| [类型 B] | [口语示例] | ⭐⭐⭐⭐ | [说明] |
```

**作用**：提供快速场景匹配，帮助用户在 30 秒内判断是否使用本模板。

**是否必填**：⭐⭐⭐ **必须**

**推荐写法**：
- 用表格呈现，匹配度用 ⭐ 数量表示（1-5 星）
- 包含典型口语需求示例（用户实际会说的话）
- 说明该类型与模板的匹配理由

**常见错误**：
- ❌ 只写场景名称，没有口语示例
- ❌ 匹配度全写 5 星，缺乏区分度

---

### 3.4 不适用场景（必填）

```markdown
## 3. 不适用场景

| 场景类型 | 为什么不适合 | 替代方案 |
|----------|-------------|----------|
| [场景 A] | [具体原因] | [替代模板/方法] |
| [场景 B] | [具体原因] | [替代模板/方法] |
```

**作用**：明确边界，减少模板滥用。

**是否必填**：⭐⭐⭐ **必须**

**推荐写法**：
- 每条都给出替代方案，不要只说"不适合"
- 至少 3 条，覆盖最常见的错误使用场景

**常见错误**：
- ❌ 照搬适用场景的否定形式，缺乏独立思考
- ❌ 不给替代方案，使用者仍然不知道该用什么

---

### 3.5 使用前提（推荐）

```markdown
## 4. 使用前提

使用本模板前，请确认以下条件已满足：

- ✅ [前提条件 A]
- ✅ [前提条件 B]
- ⚠️ [可选条件，如有则效果更好]
```

**作用**：避免在条件不满足时强行使用模板。

**是否必填**：⭐⭐ **推荐**

**常见前提类型**：
- 数据格式前提（如"需要品类维度的销量数据"）
- 用户配合度前提（如"用户至少能回答 3 个核心问题"）
- 技术环境前提（如"需要支持 3 次 API 调用的对话长度"）

### 3.6 技术选型（推荐）

```markdown
## 5. 技术选型

### 为什么用 [技术名] 而不用其他？

| 技术 | 为什么不适合 | 为什么 [选定的技术] 更合适 |
|------|-------------|--------------------------|
| Zero-Shot | [原因] | — |
| Few-Shot | [原因] | — |
| CoT | [原因] | — |
| [选定技术] | — | [原因] |
```

**作用**：说明技术决策的理由，帮助使用者理解模板设计意图。

**是否必填**：⭐⭐ **推荐**（涉及 Prompt Chaining 或高级技术时必须）

**推荐写法**：
- 用对比表格说明为什么选这个技术而非其他
- 包含一个简单的决策流程图（ASCII）

**常见错误**：
- ❌ 直接写技术名称，不说明选择理由
- ❌ 过度分析，把技术选型写成论文

### 3.7 标准输入区（必填）

详见 §4「标准输入区规范」。

**作用**：统一用户/AI 交互的输入格式，防幻觉、可复用。

### 3.8 参考资料区（推荐）

详见 §5「参考资料区规范」。

**作用**：防止 AI 胡编乱造，提供知识依据。

**是否必填**：⭐⭐ **推荐**（涉及数据分析、事实查询时必须）

### 3.9 任务区（必填）

```markdown
### 任务
{具体要做什么，一次只做一件事}
```

**作用**：明确告诉 AI 要完成的核心任务。

**是否必填**：⭐⭐⭐ **必须**

**推荐写法**：
- 用动词开头（分析/提取/生成/转换/分类）
- 一句话，不要超过 50 字
- 只写「做什么」，不写「怎么做」

**常见错误**：
- ❌ 任务描述里夹带多个子任务（如"分析数据、判断趋势、生成报告"）
- ❌ 任务描述太抽象（如"处理一下"）

---

### 3.10 输出格式（推荐）

```markdown
### 输出格式

| 品类 | 销量 | 环比 |
|------|------|------|
| {名称} | {数字} | {百分比} |
```

**作用**：控制输出结构，减少后处理。

**是否必填**：⭐⭐ **推荐**

**推荐写法**：
- 优先用**占位符格式示例**而非文字描述
- 用 `|---|` 表格展示目标格式，不用文字说"用表格输出"
- 包含完整的表头和至少一行示例行

**常见错误**：
- ❌ 用文字描述格式（如"用表格，包含品类、销量、环比"）
- ❌ 只写"输出格式不限"，导致输出不可控
- ✅ 见 OpenAI P4：Show output format through examples

---

### 3.11 约束条件（可选）

```markdown
### 约束条件
- 必须：{不可妥协的条件}
- 禁止：{绝对不能出现的内容}
- 如无法完成：{告知 AI 不确定时该怎么回答}
```

**作用**：设定边界，防止 AI 自由发挥。

**是否必填**：⭐ **可选**

**推荐写法**：
- 用正面表述（"必须"而非"不能"）
- 包含「如无法完成」的兜底处理
- 不确定的信息必须标记为 `[待确认]`

**常见错误**：
- ❌ 大量使用负面约束（"不要 xxx"），OpenAI P7 证明效果差
- ❌ 不给兜底处理，AI 遇到不确定情况时容易乱答

---

### 3.12 示例（可选）

```markdown
### 示例

示例 1：
输入：{示例输入 1}
输出：{示例输出 1}

示例 2：
输入：{示例输入 2}
输出：{示例输出 2}
```

**作用**：通过 Few-Shot 锁定格式和边界。

**是否必填**：⭐ **可选**（格式敏感任务推荐使用）

**推荐写法**：
- 数量控制在 **3-5 个**（Anthropic 建议）
- 示例用于**格式锁定**，不是「教知识」
- 覆盖**边界情况**而非正常情况
- 用 `<example>` 标签包裹（API 场景）

**常见错误**：
- ❌ 示例过多（>10 个）导致模型模仿而非理解
- ❌ 示例与目标输入格式不一致
- ❌ 示例太完美（全是正常情况），不覆盖边界

### 3.14 单 Agent / 多 Agent 判断（可选）

```markdown
## 7. 单 Agent / 多 Agent 判断

### 默认：[单 Agent / 多 Agent]

**原因：**
[为什么默认这样选择]

### 什么时候才需要切换到另一种？

| 条件 | 说明 | 分工方式 |
|------|------|----------|

**作用**：帮助使用者判断是否需要多 Agent。

### 3.15 常见失败（必填）

```markdown
## 8. 常见失败

| # | 失败模式 | 典型表现 | 根本原因 |
|---|----------|----------|----------|
| 1 | [模式 A] | [表现] | [原因] |
| 2 | [模式 B] | [表现] | [原因] |
```

**作用**：提前预警，帮助使用者避免常见错误。

**是否必填**：⭐⭐⭐ **必须**

**推荐写法**：
- 至少 5 条，覆盖本模板最常见的失败场景
- 每条包含「典型表现」，让使用者能对号入座
- 每条包含「根本原因」，帮助定位而非只描述现象

**常见错误**：
- ❌ 只写失败模式，不写典型表现
- ❌ 失败原因泛泛而谈，不切中要害
- ❌ 从其他模板照搬，不结合本模板的实际问题

## 4. 标准输入区规范

### 4.1 通用标准输入区结构

所有 Prompt-KB 模板的输入区块必须包含以下标准组成部分，按顺序排列：

```markdown
### 原始需求
{在此粘贴用户的原始口语化需求。}

### 输入数据
{需要 AI 处理的具体内容。}
```

#### 原始需求

**作用**：保留用户的原始口语输入，作为任务的起点。

**是否必填**：⭐⭐⭐ **必须**

**推荐写法**：
```markdown
### 原始需求
{在此粘贴用户的原始想法。如果用户已经提供了结构化信息，
则将原始口语描述放在此处。}
```

**常见错误**：
- ❌ 把「原始需求」当成「任务描述」，让用户在这里填任务
- ❌ 不提供占位符说明，用户不知道该填什么

---

### 4.2 分隔符使用规范

#### 推荐分隔符层级

Prompt-KB 采用两级分隔符策略：

| 层级 | 符号 | 用途 | 示例 |
|------|------|------|------|
| **一级分隔** | `###` 标题 | 划分主要区块（角色/任务/参考资料/输入/输出格式） | `### 任务` |
| **二级分隔** | `---` | 划分区块内的子区块（仅在需要细分时使用） | `---` |
| **禁止使用** | 连续 3 个以上的 `===` 或 `---` | 仅作装饰性分隔 | `-------` |

#### 一级区块推荐顺序

按「模型越靠前影响越大」的原理排列：

```markdown
### 角色 [可选]
{角色设定，放在开头能早生效}

### 背景信息 [推荐]
{任务背景、受众、目的}

### 任务
{具体要做什么，一次只做一件事}

### 参考资料 [推荐]
{在此粘贴参考资料；如果没有请写"无"}
AI 必须优先基于参考资料。不确定的信息标记为 [待确认]。

### 约束条件 [可选]
{硬性限制}

### 输出格式 [推荐]
{格式要求，尽量用占位符格式示例}

### 示例 [可选/慎用]
{3~5 个结构化示例}

### 原始需求 [必须]
{在此粘贴用户的原始口语化输入}
```

**为什么「原始需求」放末尾**：
- Anthropic 研究表明：模型是自回归生成的，越靠近生成位置的 token 对输出影响越大
- 将用户输入放在末尾，确保模型优先关注指令而非被用户内容带偏
- 对应 Anthropic 的「文档放在顶部、问题放在末尾」原则

#### Markdown `###` vs XML 标签的选择

| 场景 | 推荐分隔方式 | 原因 |
|------|------------|------|
| **中文手写模板** | Markdown `###` | 对中文用户最友好，手写可读性高 |
| **API 调用模板** | XML 或 Markdown 均可 | API 场景对严格性要求更高 |
| **长上下文（10+ 页文档）** | XML `<documents>` | 明确文档边界，支持嵌套元数据 |
| **Few-shot 示例** | `<example>` 标签（API 场景） | 明确输入-输出对的边界 |
| **快速单 prompt** | 不需要分隔符 | 简单任务不需要额外结构 |

**Prompt-KB 默认选择**：Markdown `###`

理由：
- Claude 对 `### ` 和 `<tag>` 都能正确解析
- 中文用户手写友好度高
- 与 Anthropic 的「区块化思想」一致
- T-TEXT-001 v0.4 验证通过

### 4.3 占位符书写规范

#### 占位符语法

| 类型 | 语法 | 示例 |
|------|------|------|
| 必填占位符 | `{名称}` | `{品类名称}` |
| 可选占位符 | `[名称]` 或 `{名称 [可选]}` | `{参考资料 [可选]}` |
| 示例值 | `（示例值）` 跟在占位符后 | `{品类名称（如慢回弹玩具）}` |

#### 占位符命名规范

- 使用中文或拼音，避免英文歧义
- 占位符名称要自解释，不依赖上下文
- 多个相关占位符用同一前缀（如 `{日期_开始}` 和 `{日期_结束}`）

**推荐写法**：
```markdown
### 输入数据
品类：{品类名称（如慢回弹玩具）}
销量：{销量数值（整数）}
环比：{环比百分比（如 +8% 或 -15%）}
```

**常见错误**：
- ❌ 占位符过多（>15 个），增加用户填写负担
- ❌ 占位符名称歧义（如 `{数据}` 不说清什么数据）
- ❌ 不提供示例值，用户不知道该填什么格式

## 5. 参考资料区规范

### 5.1 标准参考资料区结构

```markdown
### 参考资料
{在此粘贴参考资料；如果没有请写"无"}

AI 必须优先基于参考资料生成计划/回答/分析。
不确定的信息标记为 [待确认]，不允许把资料中没有的信息伪装成事实。
如需引用参考资料中的内容，请在回答中标注 [引用来源]。
```

### 5.2 防幻觉机制

**必须包含的三句话**：

1. **来源约束**：`必须优先基于参考资料`
2. **不确定性标记**：`不确定的信息标记为 [待确认]`
3. **禁止编造**：`不允许把资料中没有的信息伪装成事实`

### 5.3 长参考资料处理

当参考资料超过 2000 字时：

```markdown
### 参考资料摘要 [长文档专用]
{在此粘贴参考资料摘要（由人工或 AI 预先提炼）}

### 参考资料原文 [可选]
{完整参考资料，如有需要可附}
```

**原则**：长文档先摘要再用，减少上下文消耗，提升引用准确性。

## 6. 标记规范

### 6.1 统一标记格式

Prompt-KB 所有模板统一使用以下标记：

| 标记 | 含义 | 示例 |
|------|------|------|
| `[待确认]` | 信息不确定，需要用户确认后才能使用 | `目标：[待确认]` |
| `[假设]` | AI 基于上下文做的合理假设 | `训练频率：[假设] 每周 3 次` |
| `[推断]` | AI 从用户描述中推断出的信息 | `学习目标：[推断] 工作中应用` |
| `[默认]` | 使用了行业通用默认值 | `每日时长：[默认] 30 分钟` |
| `[引用来源]` | 在回答中引用了参考资料 | `根据 [CS-001 周报案例]...` |

**重要**：所有标记**统一使用半角方括号**，不要混用全角 `【待确认】`。

### 6.2 格式标记优先级

当同一信息同时有多个标记可能时，按以下优先级使用：

```
[待确认] > [假设] > [推断] > [默认]
```

即：最不确定的标记优先使用。

## 7. 格式输出规范

### 7.1 格式规范优先级

| 优先级 | 方式 | 适用场景 |
|--------|------|----------|
| 1 | **占位符格式示例**（推荐） | 所有需要格式控制的输出 |
| 2 | 表格结构 | 多维度对比、有明确列的数据 |
| 3 | Markdown 列表 | 步骤/要点/检查项 |
| 4 | JSON | 结构化数据交换（API 场景） |
| 5 | 纯文字 | 开放性回答、解释性内容 |

### 7.2 占位符格式示例规范

**❌ 错误（文字描述）：**
```
输出格式：表格，包含品类、销量、环比三列
```

**✅ 正确（占位符格式示例）：**
```
输出格式：

| 品类 | 销量 | 环比 |
|------|------|------|
| {名称} | {数字} | {百分比} |
```

**原则**：给模型看「长什么样」，而不是告诉模型「怎么写」。

## 8. 技术选型规范

### 8.1 默认策略：先简单后复杂

```
你的任务
  │
  ├─ 简单明确的任务（翻译/改写/简单分类）
  │   └─ 先试 Zero-Shot → 够用就别折腾
  │
  ├─ Zero-Shot 结果不理想？
  │   └─ 加上 2-3 个 Few-Shot 范例（用于格式锁定）
  │
  └─ 还是不行？
      └─ 考虑 Prompt Chaining（拆成多步）
          └─ 复杂推理任务 → 加 CoT（仅对非推理模型）

### 8.1.1 技术选择决策表

| 情况 | 推荐策略 | 说明 |
|------|---------|------|
| 任务简单、输入清楚 | Zero-Shot | 直接指令即可，不必加额外复杂度 |
| 输出格式经常不稳定 | Few-Shot | 加 2-3 个格式示例锁定输出结构 |
| 需要固定风格或固定结构 | Few-Shot | 用示例传达格式+风格双重要求 |
| 任务包含多个阶段 | Prompt Chaining | 拆成串行 Pipeline，各阶段独立验证 |
| 需要比较多个方案 | 结构化分析 | 不默认展示完整 CoT，按需触发 |
| 高价值复杂任务 | 标准版或进阶版 | 加入中间检查步骤和验证节点 |

**判断原则**：先让 Zero-Shot 跑通，再按需升级。不要在一开始就上满所有技术。

### 8.2 推理模型 vs 非推理模型

| 模型类型 | 适用写法 | 说明 |
|---------|---------|------|
| 普通对话模型 | 请输出结构化结果 | 不要求展示完整思考过程 |
| 高级推理模型 | 请先在内部完成必要分析，然后只输出结论和结构化结果 | 避免手动要求完整 CoT |
| 支持推理强度参数的模型 | 使用 reasoning_effort / extended thinking / thinking budget 等平台参数 | 优先使用模型或平台提供的推理控制能力 |
| 工具调用 / Agent 模型 | 将推理拆成任务步骤、工具调用和中间结果 | 不要求暴露完整隐性推理 |

> **注意**：不要在长期规范中写死具体模型版本号。模型名称和能力会变化，应优先使用「模型类型」和「平台能力」来描述。

### 8.3 Few-Shot 使用规范

| 维度 | 规范 |
|------|------|
| **数量** | 3-5 个最佳，不要超过 10 个 |
| **作用** | 格式锁定，不是教知识 |
| **选择标准** | 覆盖边界情况，不是正常情况 |
| **格式一致性** | 示例格式与目标问题格式必须一致 |
| **放置位置** | 放在 User Message 中，不放在 System Prompt |

#### 示例类型：至少区分三类

| 类型 | 作用 | 示例场景 |
|------|------|---------|
| **正常输入示例** | 建立基准格式 | 用户输入完整、清晰时的期望输出 |
| **信息不足示例** | 训练不确定性处理 | 用户输入缺失关键信息时如何响应（用 `[待确认]` 标记） |
| **边界输入示例** | 训练异常处理能力 | 用户输入模糊、矛盾、格式混乱时的处理方式 |

**写作原则**：

- 示例用于**锁定格式**，而不是限制内容——模型应学会格式套路，而非背诵示例答案
- 示例**不宜过长**，每条示例尽量控制在 100 字以内
- 示例**数量一般 1-3 个**，能说明格式即可，不必覆盖所有场景
- 示例要**贴近真实任务**，避免刻意构造"完美示例"

## 10. OpenClaw 模板嵌入规范

### 10.1 System Prompt vs User Message 的分工

| 内容类型 | 放置位置 | 原因 |
|---------|---------|------|
| 角色设定 | System Prompt | 持久生效，不需要每次传递 |
| 核心指令 | System Prompt | 持久生效 |
| 输出格式要求 | System Prompt | 持久生效 |
| 参考资料 | User Message（动态） | 按需加载，减少 token 消耗 |
| Few-Shot 示例 | User Message（动态） | 按需加载，便于迭代 |
| 用户当前输入 | User Message | 每次不同 |

### 10.2 Human-in-the-Loop 插入位置

| 场景 | 建议插入位置 | 理由 |
|------|-------------|------|
| 计划类任务 | Step 1 → Step 2 之间 | 方向确认后后续才有意义 |
| 高风险操作（删除/发送） | 操作执行前 | 必须人工确认 |
| 内容生成初稿 | 初稿生成后 | 减少返工 |
| 简单格式化/翻译 | 不需要 | 性价比低 |

#### 最小 OpenClaw 配置示例

```yaml
execution_mode: single_agent_sequential
human_confirmation:
  required_when:
    - requirements_unclear
    - external_tool_use
    - file_modification
    - email_or_calendar_action
save_intermediate_outputs: true
reference_text_required: optional
knowledge_base_update: after_validation
```

**配置说明**：

- `execution_mode`：默认单 Agent 顺序执行，复杂任务再升级
- `human_confirmation`：在关键节点（需求不清、外部工具调用、文件修改、外部通知）插入人工确认
- `save_intermediate_outputs`：Pipeline 各步骤的中间结果需要持久化，供下一步使用
- `reference_text_required`：参考资料可按需加载，不必每次都传
- `knowledge_base_update`：知识库更新必须等最终验证通过后才写入

## 11. 常见错误速查

### 11.1 结构类错误

| # | 错误 | 正确做法 |
|---|------|---------|
| 1 | 模板缺少「不适用场景」章节 | 至少列出 3 条，并给出替代方案 |
| 2 | 「适用场景」不包含口语示例 | 让用户能对照自己的话判断是否适合 |
| 3 | 版本记录长期停留在 v0.1 | 每次实质性修改必须更新版本号 |
| 4 | 参考资料区没有防幻觉三句话 | 必须包含：来源约束 + 标记规范 + 禁止编造 |
| 5 | 分隔符混用 `###` 和 `---` | 同一模板内只选一种风格 |
| 6 | 标记混用全角和半角 | 统一用 `[待确认]` 半角格式 |

### 11.2 内容类错误

| # | 错误 | 正确做法 |
|---|------|---------|
| 1 | 任务描述包含多个子任务 | 拆成多个 prompt 或明确标注主次 |
| 2 | 用文字描述输出格式 | 改为占位符格式示例 |
| 3 | 约束条件大量使用负面表述 | 改为正面表述（"要什么"而非"不要什么"） |
| 4 | Few-Shot 示例超过 10 个 | 控制在 3-5 个，覆盖边界情况 |
| 5 | 为推理模型加手动 CoT 引导 | 用 effort 参数替代 |
| 6 | 模板 token 超过 2000 | 考虑拆分为多步 Pipeline |
| 7 | 占位符超过 15 个 | 精简或拆分为子模板 |
