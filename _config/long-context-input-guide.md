# Prompt-KB 长上下文输入规范

> **规范编号**: T-CONFIG-006
> **版本**: v0.1
> **创建日期**: 2026-05-16
> **状态**: 正式版
> **依据来源**: DAIR.AI + OpenAI（S2 Provide Reference Text / S3 Split Complex Tasks）+ Anthropic（文档靠前问题靠后 / XML 结构化 / 先引用后回答）+ T-CONFIG-001~005
> **用途**: 统一 Prompt-KB 模板中长文档、多来源资料、参考资料、历史记录等输入内容的组织方式
> **适用对象**:
> - 文本提示词模板（长文档分析、多来源资料整理、带参考资料的写作任务）
> - 会议纪要总结、网页 / 论文 / 报告摘要、用户笔记整理
> - OpenClaw 长流程任务、多 Agent 协作中的资料交接
> - 后续图像 / 视频模块中的参考资料或参考图说明

---

## 1. 规范目标

本规范解决以下问题：

| # | 问题 | 影响 |
|---|------|------|
| 1 | 长资料直接堆进 prompt 导致模型混乱 | 输出质量下降、遗漏关键信息、幻觉增加 |
| 2 | 多来源资料边界不清 | 模型混淆资料来源、张冠李戴 |
| 3 | AI 把资料中没有的信息说成事实 | 幻觉风险、信任度下降 |
| 4 | 资料冲突时不说明 | 输出矛盾、用户无法判断 |
| 5 | 长上下文任务一次性生成低质量结果 | 资料越多质量越差的"倒 U 形"现象 |
| 6 | 缺乏统一的输入组织标准 | 各模板结构不一致、难以维护 |

**不解决的问题**：

- 具体任务模板的设计（由 T-CONFIG-001 负责）
- 输出格式的具体写法（由 T-CONFIG-005 负责）
- 示例怎么写（由 T-CONFIG-002 负责）
- 是否需要示例（由 T-CONFIG-004 负责）
- 用什么策略（由 T-CONFIG-003 负责）

## 2. 适用范围

### 2.1 适用的任务类型

| 任务类型 | 典型场景 | 输入特征 |
|----------|----------|----------|
| 长文档分析 | 报告分析、论文解读、合同审查 | 单一长文档（1000+ 字） |
| 多来源资料整理 | 竞品分析、市场调研、技术选型 | 2 个以上不同来源 |
| 会议纪要总结 | 周会、项目复盘、客户访谈 | 聊天记录 / 转写文本 |
| 网页 / 论文 / 报告摘要 | 信息收集、文献综述 | 网页内容 / PDF / 报告 |
| 用户笔记整理 | 学习笔记、读书笔记、工作日志 | 多条零散笔记 |
| 带参考资料的写作 | 深度文章、分析报告、方案建议 | 用户需求 + 参考资料 |
| OpenClaw 长流程任务 | 多步骤自动化流程 | 中间结果需要传递 |
| 多 Agent 协作资料交接 | 审查 + 生成并行 | Agent 间需要共享资料上下文 |

### 2.2 不强制适用的场景

以下场景可参考本规范，但不强制遵守：

- 简单问答（单轮、短输入）
- 短文本改写（翻译、润色、格式化）
- 无资料输入的普通模板（纯生成任务）
- 临时草稿
- 资源索引

### 2.3 判断是否需要应用本规范

```
输入资料是否超过 1000 字？
  ├─ 否 → 本规范仅供参考，不强制
  └─ 是 →
       是否有多个来源？
         ├─ 否 → 是否需要引用来源或说明依据？
         │        ├─ 否 → 参考本规范 §5 即可
         │        └─ 是 → 建议完整应用本规范
         └─ 是 → 必须应用本规范
```

## 3. 与现有规范的关系

Prompt-KB 的六层配置规范形成完整的规范链：

```
T-CONFIG-001  通用模板结构规范
     ↓ 决定模板整体骨架
T-CONFIG-003  模型类型与提示策略判断规范
     ↓ 决定用什么策略执行任务
T-CONFIG-004  Few-shot 适用条件判断规范
     ↓ 判断是否需要示例
T-CONFIG-002  Few-shot 示例规范
     ↓ 如果需要示例，指导怎么写
T-CONFIG-005  格式描述与占位符规范
     ↓ 指导输入区、输出格式和占位符怎么写
T-CONFIG-006  长上下文输入规范（本规范）
     ↓ 指导长资料、多来源资料和参考资料怎么组织
```

**关系说明**：

| 规范 | 负责什么 | 与 T-CONFIG-006 的关系 |
|------|----------|----------------------|
| T-CONFIG-001 | 模板整体结构（元数据、输入区、输出区） | T-CONFIG-006 在 T-CONFIG-001 的"标准输入区"基础上，对参考资料区块做细化规范 |
| T-CONFIG-002 | Few-shot 示例怎么写 | T-CONFIG-006 的参考资料组织方式不影响 Few-shot 示例的编写规则 |
| T-CONFIG-003 | 选策略 | T-CONFIG-006 不涉及策略选择，但补充了"长上下文任务"的判断标准 |
| T-CONFIG-004 | 判断是否需要示例 | T-CONFIG-006 不改变 Few-shot 启用条件 |
| T-CONFIG-005 | 格式和占位符怎么写 | T-CONFIG-006 遵循 T-CONFIG-005 的占位符规则（`[中文描述]`）和输出格式规则 |

**核心原则**：T-CONFIG-006 是 T-CONFIG-005 中"标准输入区"的扩展规范，专注于**资料怎么放进 prompt**，而非模板的整体结构或格式细节。

## 4. 长上下文任务判断

### 4.1 判断标准

| # | 判断条件 | 说明 |
|---|---------|------|
| 1 | 输入资料超过 1000 字 | 超过此阈值后，模型对中间位置的信息关注度下降 |
| 2 | 有 2 个以上来源 | 多来源需要编号和来源说明，避免混淆 |
| 3 | 资料类型多样 | 文档 + 网页 + 表格 + 聊天记录 + 图片说明等混合 |
| 4 | 需要基于资料回答 | 非自由生成，而是"读后回答"或"读后分析" |
| 5 | 需要引用来源或说明依据 | 输出中需要标注"信息来自哪里" |
| 6 | 需要分阶段处理 | 一个 prompt 做不完，需要 Prompt Chaining |
| 7 | 需要先摘要再分析 | 资料太多，直接分析会遗漏关键信息 |
| 8 | 需要处理资料冲突 | 不同来源的信息有矛盾 |

### 4.2 判断表

| 任务情况 | 是否属于长上下文 | 推荐处理方式 |
|----------|-----------------|-------------|
| 100 字以内的问答 | 否 | Zero-Shot 即可 |
| 单篇 500 字文章改写 | 否 | Zero-Shot 或 Few-shot |
| 单篇 1500 字文章摘要 | 是（轻度） | 参考 §5 输入结构即可 |
| 3 篇文章对比分析 | 是（中度） | 参考 §5 + §6 多来源组织 |
| 10 页报告深度解读 | 是（重度） | 参考 §11 先摘要，再分块 |
| 5 个来源的市场调研 | 是（重度） | 参考 §6 + §7 + §11 |
| 会议记录（5000+ 字）总结 | 是（重度） | 参考 §7 + §11 + §12 |
| 带资料的方案设计 | 是（中度） | 参考 §5 + §13 引用规范 |
| 多 Agent 协作审查 | 是（重度） | 参考 §15 + §16 |
| 图像生成 + 风格参考 | 视情况 | 参考 §17 |

## 5. 长上下文输入总结构

### 5.1 推荐输入结构

```markdown
### 任务目标
[一句话说明要做什么]

### 背景信息
[任务背景、受众、最终目的]
[如无背景信息，写"无"]

### 参考资料
资料 1：[来源名称] / [类型] / [日期] / [可信度]
[资料内容]

资料 2：[来源名称] / [类型] / [日期] / [可信度]
[资料内容]

资料 3：[来源名称] / [类型] / [日期] / [可信度]
[资料内容]

[如无参考资料，写"无"]

### 资料来源说明
[补充说明资料的可靠程度、时效性、覆盖范围]
[如无需说明，写"无"]

### 限制条件
[硬性限制、可接受范围、安全注意事项]
[不确定的限制标记为 [待确认]]

### 输出格式
[期望的输出结构和格式]
[参考 T-CONFIG-005 的输出格式规范]

### 原始需求
[在此粘贴用户的原始输入]
```

### 5.2 各区块作用

| 区块 | 作用 | 是否必选 | 说明 |
|------|------|----------|------|
| **任务目标** | 让模型明确知道要做什么 | 必选 | 一句话，不要超过 3 句 |
| **背景信息** | 提供任务上下文 | 推荐 | 缺少背景时写"无" |
| **参考资料** | 提供分析依据，防止幻觉 | 资料任务必选 | 没有资料时写"无"，不要留空 |
| **资料来源说明** | 补充资料的可靠性信息 | 推荐 | 当资料可信度不明确时必选 |
| **限制条件** | 明确边界，避免自由发挥 | 推荐 | 不确定时标记 [待确认] |
| **输出格式** | 控制输出结构 | 推荐 | 参考 T-CONFIG-005 |
| **原始需求** | 用户原始输入 | 必选 | **放在末尾**（Anthropic 原则：文档靠前，问题靠后） |

### 5.3 核心设计原则

1. **用户输入和参考资料必须分开**：不要把用户需求混在参考资料中
2. **多来源资料必须编号**：`资料 1`、`资料 2`、`资料 3`... 依次编号
3. **没有资料时写"无"**：不要留空，不要省略该区块
4. **不确定信息标记为 [待确认]**：遵循 T-CONFIG-005 的占位符规则
5. **合理假设标记为 [假设]**：模型可以做假设，但必须标注
6. **资料中没有的信息不能伪装成事实**：没有依据时必须标注来源缺失

## 6. 多来源资料组织规范

### 6.1 推荐格式

```
资料 1：[来源名称] / [类型] / [日期] / [可信度]
[资料内容]

资料 2：[来源名称] / [类型] / [日期] / [可信度]
[资料内容]

资料 3：[来源名称] / [类型] / [日期] / [可信度]
[资料内容]
```

**示例**：

```
资料 1：2025 年度财务报告 / 内部文档 / 2026-01-15 / 高
（报告正文...）

资料 2：行业趋势分析 - 玩具行业 / 网页摘要 / 2026-03-20 / 中
（摘要正文...）

资料 3：客户访谈记录 - 华南区域 / 会议记录 / 2026-05-10 / 高
（访谈正文...）
```

### 6.2 设计原则

| 原则 | 原因 |
|------|------|
| **编号**（资料 1、资料 2...） | 输出时可精确引用"来源：资料 2"，避免模糊的"资料显示" |
| **标注来源类型** | 不同类型的资料有不同的处理重点（如会议记录注意决策、网页注意时效性） |
| **标注日期** | 时效性判断依据；新旧资料冲突时优先新资料（但不能只看日期） |
| **区分事实、观点、推测** | 避免模型把推测当成事实传播 |
| **不要混在一起** | 多个来源混在一个段落中，模型无法区分信息边界 |

### 6.3 资料编号引用规则

输出中引用资料时，使用统一格式：

- **单来源引用**：`（来源：资料 1）`
- **多来源引用**：`（来源：资料 1、资料 3）`
- **不确定来源**：`（来源：[待确认]）`
- **模型自身推断**：`（来源：[假设]）`
- **禁止模糊引用**：不要写"根据资料显示"、"据某报告"，必须指明具体编号

## 7. 资料来源标注规范

### 7.1 来源类型定义

| # | 来源类型 | 典型形式 | 处理重点 |
|---|---------|----------|----------|
| 1 | 用户直接提供 | 用户粘贴的文本、手写笔记 | 优先级最高，用于个性化任务 |
| 2 | 内部文档 | 公司报告、内部邮件、项目文档 | 注意版本和时效性，标注是否为最终版 |
| 3 | 网页摘要 | 新闻、博客、行业资讯 | 注意时效性和来源可信度，区分一手和二手 |
| 4 | 论文 / 报告 | 学术论文、研究报告、白皮书 | 注意结论、方法、样本量和研究限制 |
| 5 | 会议记录 | 周会、项目会、客户访谈 | 注意发言人、决策、待办、口语化表达 |
| 6 | 聊天记录 | IM 对话、邮件往来 | 注意上下文缺失、省略和口语化，标注参与者 |
| 7 | 表格数据 | Excel、CSV、数据库导出 | 注意字段定义、时间范围、指标计算口径 |
| 8 | 代码 / 日志 | 源码、错误日志、系统日志 | 注意版本、运行环境、错误上下文 |
| 9 | 图片说明 | 参考图描述、设计稿说明 | 用文字准确描述视觉元素，不确定细节标记 [待确认] |
| 10 | 视频说明 | 分镜描述、镜头参考、剧本 | 注明时长、节奏和转场要求 |

### 7.2 各来源类型的特殊处理

**会议记录**：
- 标注发言人身份
- 提取决策点和待办事项
- 口语化表达需注明"此为口语转写"
- 如有录音，标注录音时长和完整性

**表格数据**：
- 注明字段定义（如"销量"是指出库量还是订单量）
- 注明时间范围
- 注明数据来源和计算口径
- 如有缺失值，明确标注

**聊天记录**：
- 标注参与者和角色
- 注意上下文可能缺失（聊天记录常省略已知信息）
- 口语化表达需要理解隐含含义
- 如有截断，标注"以下为部分记录"

**网页摘要**：
- 注明原始 URL
- 注明抓取日期
- 区分一手新闻和二手转载
- 标注来源可信度（官方 > 自媒体 > 匿名来源）

**论文 / 报告**：
- 提取核心结论和方法
- 注意样本量和适用范围
- 注意研究限制和作者声明
- 区分结论和推测

## 8. 资料可信度和时效性规范

### 8.1 基本原则

1. **不要默认所有资料都同等可信**——必须评估每个来源的可靠程度
2. **新资料通常优先于旧资料**——但不能只看日期，要结合来源类型
3. **用户提供的背景优先用于个性化任务**——但事实性判断仍需客观来源
4. **官方文档优先于二手摘要**——有条件时追溯一手来源
5. **内部文档优先于公开猜测**——但也要注意内部文档可能有偏差
6. **冲突资料必须标记**——不能自行选择一个当作绝对事实
7. **无法判断时标记为 [待确认]**——宁可不判断，不要误判

### 8.2 可信度判断表

| 资料类型 | 默认可信度 | 注意事项 |
|----------|-----------|----------|
| 用户直接提供 | 高（个人任务） / 中（事实任务） | 个人任务中尊重用户说法；事实任务仍需验证 |
| 内部文档（正式发布） | 高 | 注意版本是否为最终版 |
| 内部文档（草稿） | 中 | 可能有未修正的错误 |
| 官方公告 / 官方文档 | 高 | 注意公告日期和适用范围 |
| 论文（同行评审） | 高 | 注意样本量和研究限制 |
| 论文（预印本） | 中 | 未经验证，结论可能有偏差 |
| 行业报告（知名机构） | 中-高 | 注意赞助方和利益冲突 |
| 新闻报道（主流媒体） | 中 | 注意是否为二手转载 |
| 网页摘要（自媒体） | 低-中 | 需要追溯原始来源 |
| 匿名来源 | 低 | 仅作参考，不能作为事实依据 |
| 会议记录 | 中 | 口语化，可能有记忆偏差 |
| 聊天记录 | 中 | 上下文缺失，可能有误解 |
| AI 生成的内容 | 低 | 可能包含幻觉，需人工验证 |
| 数据过时（超过 2 年） | 降低 1 级 | 需注明时效性风险 |

### 8.3 时效性判断

| 时效情况 | 处理方式 |
|----------|----------|
| 资料日期在 6 个月内 | 可直接使用 |
| 资料日期在 6 个月 ~ 2 年 | 标注"资料可能已过时"，评估是否仍适用 |
| 资料日期超过 2 年 | 标注"资料已过时"，寻找更新来源；找不到时标注 [待确认] |
| 无日期的资料 | 默认视为"时效性未知"，标注 [待确认] |
| 新旧资料冲突 | 优先新资料，但需标注旧资料的存在和差异 |

## 9. 资料冲突处理规范

### 9.1 常见冲突类型

| # | 冲突类型 | 示例 | 处理优先级 |
|---|---------|------|-----------|
| 1 | 两个来源数字不同 | 资料 1 说销售额 500 万，资料 2 说 450 万 | 列出差异，标注来源，标记 [待确认] |
| 2 | 新旧版本描述不一致 | 旧版说功能 A 支持中英文，新版只支持英文 | 优先新版，注明旧版差异 |
| 3 | 用户说法和资料不一致 | 用户说"去年增长了 30%"，资料说"增长 15%" | 列出双方数据，不自行判断谁对 |
| 4 | 官方资料和第三方资料不一致 | 官方报告说性能提升 20%，第三方测试说 12% | 列出双方，说明可能原因 |
| 5 | 同一文档不同章节不一致 | 第一章说"覆盖全球"，第三章说"仅限亚太" | 标注内部矛盾 |

### 9.2 冲突处理规则

1. **不要自行选择一个当作绝对事实**——即使某个来源看起来更可信
2. **先列出冲突点**——明确说"哪里有矛盾"
3. **标注冲突来源**——"资料 1（来源 X）vs 资料 2（来源 Y）"
4. **给出可能解释**——如"可能是统计口径不同"、"可能是版本差异"
5. **标记 [待确认]**——冲突必须由用户或人工判断
6. **必要时建议用户确认**——高风险冲突应暂停并要求确认

### 9.3 冲突处理模板

```markdown
## 资料冲突

### 冲突 1：[冲突主题]
- **资料 1**（[来源名称]，[日期]）：[具体内容]
- **资料 2**（[来源名称]，[日期]）：[具体内容]
- **可能原因**：[分析可能的原因]
- **建议**：[待确认] / 建议用户提供更权威来源 / 以下分析基于资料 1
```

## 10. 资料不足处理规范

### 10.1 基本原则

1. **明确说明缺少什么**——不要假装资料完整
2. **不要编造不存在的信息**——这是本规范最重要的规则
3. **可以给出合理假设**——但必须标记 [假设]
4. **可以输出"基于现有资料的初版"**——让用户知道这不完整
5. **可以列出需要补充的问题**——帮助用户补充资料
6. **高风险任务应停止并要求补充资料**——不要在信息不足时硬输出

### 10.2 风险等级

| 风险等级 | 场景 | 处理方式 |
|----------|------|----------|
| 低 | 常规摘要、格式整理 | 标注不足之处，继续输出 |
| 中 | 分析报告、方案建议 | 标注不足之处 + 给出 [假设]，输出初版 |
| 高 | 法律审查、医疗分析、投资决策 | 停止输出，列出缺失信息，要求补充 |
| 极高 | 涉及人身安全、重大财务决策 | 必须停止，不能输出任何结论 |

### 10.3 资料不足处理模板

```markdown
## 资料完整性说明

### 已有资料
- 资料 1：[类型] — [简述内容]
- 资料 2：[类型] — [简述内容]

### 缺失信息
1. [缺失的具体信息] — 影响：[对输出的影响]
2. [缺失的具体信息] — 影响：[对输出的影响]

### 合理假设
以下分析基于以下假设（已标记 [假设]）：
1. [假设 1] — 依据：[为什么这样假设]
2. [假设 2] — 依据：[为什么这样假设]

### 输出说明
以下为**基于现有资料的初版**，标记 [假设] 的内容需要用户确认。
```

## 11. 长资料摘要规范

### 11.1 什么时候需要先摘要

| 适合先摘要 | 不需要先摘要 |
|-----------|-------------|
| 单份资料超过 3000 字 | 单份资料在 1000 字以内 |
| 来源数量 3 个以上 | 来源数量 1-2 个 |
| 用户目标不明确，需要先了解资料全貌 | 用户目标明确，只需要提取特定信息 |
| 后续还要进行分析 / 写作 / 生成方案 | 只需要简单摘录 |
| OpenClaw 需要分步骤执行 | 单 prompt 可完成 |
| 资料包含大量无关信息 | 资料高度相关 |

### 11.2 摘要应包含的内容

| # | 内容 | 说明 |
|---|------|------|
| 1 | 核心事实 | 资料中的关键事实和数据 |
| 2 | 关键数据 | 具体数字、百分比、金额等 |
| 3 | 重要观点 | 作者或发言人的主要立场 |
| 4 | 冲突信息 | 资料内部的矛盾或与其他资料的冲突 |
| 5 | 不确定信息 | 资料本身标注为"待定"、"预估"的内容 |
| 6 | 与任务相关的内容 | 对当前任务有直接帮助的信息 |
| 7 | 可忽略内容 | 明确标注哪些内容与任务无关 |

### 11.3 摘要模板

```markdown

### 核心事实

2. [事实 2]
3. [事实 3]

- [数据 1]（来源：资料 [编号] 第 X 节）

### 重要观点
- [观点 1]
- [观点 2]

## 12. 分块处理规范

### 12.1 什么时候需要分块

| 场景 | 是否需要分块 |
|------|------------|
| 单份资料超过 5000 字 | 建议 |
| 单份资料超过 10000 字 | 必须 |
| 资料总量超过模型上下文的 50% | 建议 |
| 资料总量超过模型上下文的 80% | 必须 |
| 不同来源需要独立分析 | 建议 |
| 需要保留原始细节进行引用 | 建议 |

### 12.2 分块原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | 按来源分块 | 不同来源各自独立处理，避免交叉引用混乱 |
| 2 | 按主题分块 | 单一来源内，按主题切分（如"财务数据"、"市场数据"） |
| 3 | 按时间顺序分块 | 时间序列数据（如年报、日志）按时间分段 |
| 4 | 按任务阶段分块 | 不同处理阶段使用不同资料子集 |
| 5 | 每块保留编号 | `资料 1-A`、`资料 1-B` 表示同一来源的不同块 |
| 6 | 每块输出小结 | 每块处理后输出该块的关键发现 |
| 7 | 最后合并全局结论 | 汇总各块小结，形成最终输出 |

### 12.3 分块注意事项

| # | 注意事项 | 原因 |
|---|---------|------|
| 1 | 不要按固定字数切断语义 | 切断语义会丢失关键信息 |
| 2 | 每块要有标题 | 方便引用和追溯 |
| 3 | 每块要标注来源编号 | 避免合并后混淆来源 |
| 4 | 每块要说明与任务的关系 | 帮助模型理解该块的重要性 |
| 5 | 合并时避免重复 | 不同块可能包含相同信息 |
| 6 | 保留块间引用关系 | 某块可能依赖另一块的信息 |

## 13. 引用和依据说明规范

### 13.1 什么时候需要引用

| 适合引用 | 不需要引用 |
|----------|-----------|
| 基于资料回答问题 | 通用知识 |
| 总结报告 | 简单格式转换 |
| 决策建议 | 用户原始需求复述 |
| 对比分析 | 模板标准文本 |
| 高风险判断 | 纯创意生成 |
| 涉及具体数字或事实 | 格式化输出 |

### 13.2 引用格式

| 场景 | 格式 | 示例 |
|------|------|------|
| 单来源引用 | `（来源：资料 [编号]）` | 该季度销售额增长 15%（来源：资料 2） |
| 多来源引用 | `（来源：资料 [编号 1]、[编号 2]）` | 综合多个来源判断...（来源：资料 1、资料 3） |
| 引用具体段落 | `（来源：资料 [编号]，[位置描述]）` | ...（来源：资料 2，第三章第二节） |
| 不确定来源 | `（来源：[待确认]）` | 据推测...（来源：[待确认]） |
| 模型推断 | `（来源：[假设]）` | 如果按此趋势...（来源：[假设]） |

### 13.3 引用规则

1. **有内部文件引用时**，保留文件路径或来源编号，方便追溯
2. **没有正式引用系统时**，用"来源：资料 1 / 资料 2"标注
3. **不要写无法追溯的引用**——禁止"资料显示"、"据了解"等模糊表述
4. **没有依据时**，必须标记 [待确认] 或 [假设]
5. **引用和观点要分开**——先引用事实，再给出分析或建议

## 15. OpenClaw 长上下文工作流规范

### 15.1 推荐 Step 流程

```
Step 1：资料接收与编号
  → 接收用户提供的资料
  → 为每份资料分配编号（资料 1、资料 2...）
  → 提取元数据（来源、类型、日期、可信度）
  → 输出：资料清单

Step 2：资料摘要
  → 对每份资料进行摘要（参考 §11）
  → 提取核心事实、关键数据、重要观点
  → 标注冲突信息和不确定信息
  → 输出：资料摘要表

Step 3：冲突与缺口检查
  → 对比各资料，列出冲突点
  → 识别资料缺口（缺少什么信息）
  → 评估资料充分性
  → 输出：冲突清单 + 缺口清单

         ──── 人工确认（如需要） ────

Step 4：任务相关信息提取
  → 基于任务目标，从资料中提取相关信息
  → 过滤无关信息
  → 输出：任务相关信息摘要

Step 5：生成初版输出
  → 基于提取的信息，生成最终输出
  → 遵循 §14 的输出格式
  → 标注所有引用、[待确认] 和 [假设]

         ──── 人工确认 ────

Step 6：修订与入库
  → 根据反馈修订
  → 确认所有 [待确认] 事项
  → 输出终版
```

### 15.2 关键规则

| # | 规则 | 说明 |
|---|------|------|
| 1 | 什么时候必须 human-in-the-loop | 涉及高风险决策、资料有严重冲突、资料严重不足时 |
| 2 | 中间结果如何保存 | 每步输出独立保存，方便回溯和调试 |
| 3 | 资料过长时如何拆任务 | 参考 §12 分块规范，每块独立处理后再合并 |
| 4 | 多 Agent 是否必要 | 参考 §16 判断表，默认单 Agent |
| 5 | 默认优先单 Agent 顺序执行 | 除非有明确的多 Agent 需求（§16） |

## 16. 多 Agent 长上下文协作边界

### 16.1 适合多 Agent 的场景

| # | 场景 | 说明 |
|---|------|------|
| 1 | 来源很多（5+ 个）且类型不同 | 不同来源需要不同处理策略 |
| 2 | 需要独立审查 | 一个 Agent 生成，另一个 Agent 审查 |
| 3 | 需要事实核查 | 一个 Agent 提取事实，另一个验证 |
| 4 | 需要多个角色并行处理 | 如"分析师"和"写作者"同时工作 |
| 5 | 长期自动化流程 | 多步骤需要独立监控和容错 |

### 16.2 不适合多 Agent 的场景

| # | 场景 | 说明 |
|---|------|------|
| 1 | 资料不多（1-3 个来源） | 单 Agent 足够，多 Agent 增加复杂度 |
| 2 | 任务目标简单 | 如简单摘要，不需要拆分 |
| 3 | 只需要摘要 | 摘要任务通常不需要并行 |
| 4 | 用户还没确认需求 | 需求不明确时先澄清，再决定是否多 Agent |

### 16.3 单 Agent / 多 Agent 判断表

| 判断条件 | 推荐 | 原因 |
|----------|------|------|
| 1-3 个来源，任务明确 | 单 Agent | 资料量可控，单 Agent 效率更高 |
| 4-6 个来源，需要对比 | 单 Agent 或简单拆分 | 可按来源分块，顺序处理 |
| 7+ 个来源，类型多样 | 多 Agent | 不同类型来源需要不同处理逻辑 |
| 需要事实核查 | 双 Agent（生成 + 审查） | 审查 Agent 独立验证，减少幻觉 |
| 涉及高风险决策 | 多 Agent + human-in-the-loop | 交叉验证 + 人工确认 |
| 长期自动化流程 | 多 Agent | 需要 Agent 间独立监控和容错 |

[对每份资料的摘要]

## 关键信息
[从所有资料中提取的关键信息，按主题分组]

## 资料冲突
[列出不同资料之间的矛盾或不一致之处]

## 缺失信息
[列出缺少什么关键信息，以及对任务的影响]

## 与任务相关的内容
[基于任务目标，筛选出最相关的信息]

## 待确认事项
[列出所有不确定、需要用户确认的信息]

## 下一步建议
[建议接下来怎么做：补充资料、直接分析、调整目标等]

### 规则
- 只基于提供的资料回答，不要编造信息
- 不确定的信息标记为 [待确认]
- 合理推断标记为 [假设]
- 引用具体资料时使用"来源：资料 [编号]"格式
- 资料之间有冲突时，不要自行选择一个当作事实，要列出冲突
```

## 20. 常见错误

| # | 错误 | 问题 | 修正 |
|---|------|------|------|
| 1 | 把所有资料混在一起 | 模型无法区分来源 | 编号 + 分开放置 |
| 2 | 不标来源 | 输出无法追溯 | 每份资料标注来源名称和类型 |
| 3 | 不标日期 | 无法判断时效性 | 每份资料标注日期 |
| 4 | 不区分事实和观点 | 模型可能把推测当事实 | 资料中明确标注"事实/观点/推测" |
| 5 | 资料不足时编造 | 幻觉风险 | 明确说明缺失，标记 [待确认]，给出 [假设] |
| 6 | 冲突资料不处理 | 输出矛盾 | 列出冲突、标注来源、标记 [待确认] |
| 7 | 摘要丢失关键数字 | 信息损失 | 摘要模板中要求"关键数据"单独列出 |
| 8 | 长文档一次性要求最终输出 | 质量下降 | 先摘要 → 再分析 → 最后输出 |
| 9 | 没有中间确认 | 方向偏差 | OpenClaw 中在关键节点设置 human-in-the-loop |
| 10 | 没有标记 [待确认] | 用户不知道哪些不可靠 | 强制标记所有不确定信息 |
| 11 | 把视觉参考和事实资料混在一起 | 维度混乱 | 视觉参考和事实资料分开展示 |
| 12 | 多 Agent 过度使用 | 复杂度增加、成本增加 | 参考 §16 判断表，默认单 Agent |
