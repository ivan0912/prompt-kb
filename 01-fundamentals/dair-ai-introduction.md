## 4. 核心概念

### 4.1 什么是提示工程？

**一句话：设计有效的输入，让 AI 给出你想要的输出。**

提示工程不是玄学，而是一个可迭代的工程过程。它的本质是在和语言模型（LLM）沟通时，通过精心设计的输入来引导模型的行为。

**为什么这对你有用？**
- 你不需要懂模型内部原理，只需要学会怎么「说话」它就能听懂
- 提示词质量直接决定输出质量——同样的模型，好的提示词和差的提示词结果天差地别
- 这是一项可以系统学习和复用的技能，不是靠运气

### 4.2 提示词的四大组成元素

一个提示词不一定包含全部四个元素，但知道它们的存在能帮你更有意识地构建提示词：

| 元素 | 是什么 | 举例 |
|------|--------|------|
| **指令 (Instruction)** | 你想让模型做什么 | "分类这段文本的情感倾向" |
| **上下文 (Context)** | 背景信息，帮助模型理解场景 | "你是一个数据分析助手，用户是电商运营" |
| **输入数据 (Input Data)** | 需要处理的具体内容 | "我觉得这个产品还行" |
| **输出指示 (Output Indicator)** | 期望的格式或类型 | "Sentiment: " 或 "以 JSON 格式输出" |

**实际运用时的思路：** 写提示词之前先过一遍这四项——我给了明确的指令吗？背景信息够吗？要处理的输入是什么？希望输出长什么样？

### 4.3 Zero-Shot vs Few-Shot

这是两种最基础的提示模式：

**Zero-Shot（零样本）**：直接下命令，不给例子。
```
Q: 这句话是正面还是负面？"今天天气真好"
A:
```
适合：简单任务、模型本身就擅长的领域、快速测试。

**Few-Shot（少样本）**：在提问前先给几个范例。
```
Q: "太棒了！" → 正面
Q: "真差劲" → 负面
Q: "今天天气真好" → 
```
适合：需要控制输出格式、任务有一定复杂度、模型表现不稳定时。

**核心机制叫「上下文学习」（In-Context Learning）**：模型通过你给的范例自动理解任务规律，不需要重新训练。这就是为什么给 2-3 个例子往往能大幅提升效果。

### 4.4 提示词的标准格式

不同任务需要不同的格式结构。格式不是死的——核心原则是**让模型一眼看懂你想要什么**：

| 任务类型 | 推荐格式 |
|----------|----------|
| 问答 | `Q: <问题>? \n A:` 或直接问 |
| 带 Few-Shot 的问答 | 先给 2-3 组 Q/A 示例，再给目标 Q |
| 分类 | 先给 `<文本> // <标签>` 示例，再给目标文本 |
| 生成/写作 | 直接用指令动词开头："写一篇""总结一下""翻译成" |

**关键认知：** 格式的目的是降低模型的「理解负担」，不是走形式。

### 4.5 设计提示词的五个核心原则

| # | 原则 | 一句话解释 |
|---|------|-----------|
| 1 | **从简单开始** | 先写最基本的版本，逐步加元素，别一上来就搞复杂的 |
| 2 | **明确指令** | 用"写""分类""总结""翻译"这类动词开头，告诉模型具体干什么 |
| 3 | **越具体越好** | 不要说"简短说明"，要说"用 2-3 句话向高中生解释" |
| 4 | **避免模糊** | 模糊 = 不可控。直接说你要什么，不要绕弯子 |
| 5 | **说"要什么"而非"不要什么"** | 别说"不要问用户偏好"，要说"直接推荐热门榜单" |

### 4.6 LLM 参数基础认知（Settings）

通过 API 调用时，这些参数会影响输出：

| 参数 | 干什么的 | 怎么调 |
|------|----------|--------|
| **Temperature** | 控制输出的随机性/创造性 | 低=精准事实，高=创意发散（ factual QA 用 0~0.3，写诗用 0.7~1） |
| **Top P** | 和 Temperature 二选一调，不要同时调 | 低=保守确定，高=更多样化 |
| **Max Length** | 限制生成长度 | 控制成本，防止啰嗦 |
| **Stop Sequences** | 遇到指定文本就停止生成 | 控制结构，比如列表到第 11 项就停 |
| **Frequency Penalty** | 减少重复用词 | 和 Presence Penalty 二选一 |
| **Presence Penalty** | 鼓励话题多样性 | 同上 |

**实用建议：** 大多数日常任务默认参数就够用了。只有在你发现输出总是重复、太发散、或者长度不对的时候才需要调参。

## 5. 适用场景

- ✅ **日常问答** — 基础的 Zero-Shot 提示即可满足大多数信息查询需求
- ✅ **写作辅助** — 通过角色设定（Role Prompting）和明确指令控制文风和篇幅
- ✅ **学习新概念** — 利用"向 XX 解释"的模式让 AI 当私人讲师
- ✅ **资料整理 / 信息提取** — 结合上下文 + 输入数据 + 格式指示的结构化提示
- ✅ **任务拆解** — 从简单提示开始迭代，自然形成任务分解思维
- ✅ **文本分类 / 情感分析** — Few-Shot 模式的经典应用场景
- ✅ **代码生成（简单到中等）** — 给定清晰的描述和上下文，LLM 能生成可用代码
- ✅ **图片 / 视频提示词前置规划** — 在生成多媒体内容前，先用文字提示词理清需求和结构
- ✅ **OpenClaw 工作流的基础单元** — 每个 Agent 的核心 prompt 都应遵循这些原则
- ✅ **多 Agent 协作的通信规范** — Agent 之间的消息传递本质上是结构化的提示词

---

## 6. 不适用场景

- ❌ **复杂工具调用 / Function Calling** — 需要 Agents 章节的高级技术
- ❌ **RAG（检索增强生成）** — 需要专门的 RAG 技术和向量数据库知识
- ❌ **多 Agent 编排与协作** — 需要Agents 章节的 ReAct、Reflexion 等框架
- ❌ **长文档深度分析** — 基础提示词受上下文窗口限制，复杂分析需要分段 + 汇总策略
- ❌ **自动化执行工作流** — 需要Prompt Chaining、ART 等链式技术
- ❌ **图像生成的细节提示词** — 文字提示词的基础原则适用，但图像有专属语法（如 Midjourney 参数）
- ❌ **视频生成的细节提示词** — 同上，视频提示有时序、镜头等额外维度
- ❌ **复杂推理任务（数学证明、多步逻辑）** — 需要 Chain-of-Thought 等高级推理技术
- ❌ **对抗性安全防护** — 需要Risks & Misuses 章节的知识

## 7. 中文提示词模板

### 模板 A：口语需求转结构化提示词

> **使用场景：** 你有一个模糊的想法，想把它变成 AI 能执行的清晰指令。

```markdown
# 角色
你是一个{专业领域}专家助手。

# 任务
{用一句话说清楚你要 AI 做什么}

# 上下文
- 我是谁：{你的身份/角色}
- 背景：{为什么做这件事}
- 已有资料：{你已经有什么信息或材料}

# 输入
{需要 AI 处理的具体内容}

# 输出要求
- 格式：{表格 / 列表 / 段落 / JSON / Markdown}
- 篇幅：{大概多少字 / 多少条}
- 语言风格：{正式 / 口语化 / 学术 / 商务}
- 必须包含：{关键要素清单}
- 不要包含：{排除项}

# 示例（可选）
输入示例：{一个输入样例}
期望输出：{对应的输出样例}
```

**使用示范——填空后：**
```markdown
# 角色
你是一个电商运营数据分析助手。

# 任务
分析上周品类销售数据，找出 Top 5 畅销品和 Top 5 滞销品

# 上下文
- 我是谁：玩具品类运营
- 背景：需要做周报，给老板看
- 已有资料：上周销售明细 Excel

# 输入
[粘贴销售数据或上传文件]

# 输出要求
- 格式：Markdown 表格
- 篇幅：各 Top 5，附带简要分析
- 语言风格：商务简洁
- 必须包含：SKU 名称、销量、环比变化、一句话原因
- 不要包含：技术术语堆砌
```

---

### 模板 B：模糊任务转清晰任务说明

> **使用场景：** 你知道大概要做什么，但不知道怎么精确描述需求。

```markdown
请帮我完成以下任务：

## 任务目标
{把"我想..."转化为"请输出..."}

## 具体要求
1. {要求 1，用数字编号}
2. {要求 2}
3. {要求 3}

## 约束条件
- 必须：{不可妥协的条件}
- 禁止：{绝对不能出现的内容}
- 如果无法完成：{告知 AI 不确定时该怎么回答}

## 输出格式
{精确描述输出长什么样，最好给个模板}

## 参考标准
好的输出应该满足：{判断好坏的标准}
```

**使用示范——填空后：**
```markdown
请帮我完成以下任务：

## 任务目标
将一段产品描述翻译成英文，用于亚马逊 Listing

## 具体要求
1. 保留所有产品特性和卖点
2. 使用地道的英文表达，不要翻译腔
3. 突出卖点关键词，便于搜索优化

## 约束条件
- 必须：保持原文的信息完整性
- 禁止：添加原文中没有的产品功能
- 如果无法完成：标注出不确定的部分并给出建议

## 输出格式
- Title: {标题}
- Bullet Points: {5 个卖点要点}
- Description: {产品描述段落}

## 参考标准
好的输出应该像母语者写的，客户读一遍就想下单。
```

**备选使用示范——数据分析场景：**
```markdown
请帮我完成以下任务：

## 任务目标
将本周 Essaone 淘宝店铺的销售原始数据转化为周报可用的分析结果

## 具体要求
1. 计算各三级品类的销量和销售额
2. 对比上周数据，标注环比变化
3. 找出异常波动的 SKU（涨幅或跌幅超过 30%）

## 约束条件
- 必须：基于提供的数据计算，不编造数字
- 禁止：输出 SQL 或 Python 代码，只输出分析结论
- 如果无法完成：说明缺少哪些字段

## 输出格式
| 品类 | 销量 | 销售额 | 环比 | 备注 |

## 参考标准
老板看一眼就能知道这周生意怎么样、哪里出了问题。
```

### 模板 C：学习新概念时的提示词模板

> **使用场景：** 你遇到了不懂的概念，想让 AI 教你。

```markdown
我想学习{概念名称}。

## 我的背景
{你的领域/年级/经验水平}，请不要假设我有任何前置知识。

## 请按以下结构教我：

### 1. 一句话说清楚
用最通俗的话解释这个概念是什么（打个比方更好）。

### 2. 为什么重要
这个概念解决了什么问题？不会它会有什么后果？

### 3. 核心要素
列出 3-5 个必须掌握的关键点，每个点用一句话解释。

### 4. 举个具体例子
给我一个我生活中能遇到的实例。

### 5. 常见误区
初学者最容易犯的错误是什么？

### 6. 动手试试
出一个练习题让我检验是否理解了。

## 额外要求
- 用中文回答
- 如果涉及专业术语，首次出现时括号注释英文原文
- 复杂的地方多举个例子，少用公式
```

## 8. OpenClaw 使用方式

| 维度 | 说明 |
|------|------|
| **适合单 Agent 吗？** | ✅ **非常适合**。这些基础知识就是为单 Agent 设计的——每个 Agent 的 System Prompt 都应该遵循四大元素 + 五大原则 |
| **适合多 Agent 吗？** | ⚠️ **部分适合**。作为 Agent 间通信的消息格式规范有用，但多Agent 编排本身需要更高级的技术（ReAct 等） |
| **适合放入 system prompt 吗？** | ✅ **强烈推荐**。将角色设定、输出规范、约束条件写入 system prompt，是 OpenClaw 单 Agent 的最佳实践 |
| **适合作为工作流前置步骤吗？** | ✅ **适合**。在任何复杂工作流中，第一步都应该是用这些基础方法把"用户口语需求"转为"结构化任务描述"，然后再分发给下游 Agent |
| **OpenClaw 中应该如何调用？** | **建议模式：** 用户输入 → [结构化提示词预处理 Agent（用本知识库方法）] → 分发给专业 Agent 执行 |

### OpenClaw 调用示例

```
工作流：周报自动化

Step 1 - 需求预处理 Agent（使用本知识库）
├── System Prompt: 包含角色设定 + 输出格式规范
├── 输入: "帮我整理这周的销售数据"
├── 处理: 将口语转为结构化任务（模板 A）
└── 输出: 标准化的任务描述 JSON

Step 2 - 数据分析 Agent
├── 输入: Step 1 的结构化任务 + 数据文件
└── 执行: 计算指标、生成表格

Step 3 - 报告生成 Agent
├── 输入: Step 2 的分析结果
└── 执行: 按照格式要求生成周报文档
```

## 9. 单 Agent 适配度

# ★★★★★ (5/5)

**原因：**
- 这些基础概念本质上就是为单 Agent 交互设计的
- 四大元素（指令、上下文、输入、输出）完美对应单 Agent 的 System/User/Assistant 结构
- Five-Shot / Few-Shot 在单 Agent 场景下效果立竿见影
- 角色设定（Role Prompting）是单 Agent 最强大的技巧之一
- 五大设计原则可以直接写入 System Prompt 作为持久行为指导

---

## 10. 多 Agent 适配度

# ★★☆☆☆ (2/5)

**原因：**
- 基础提示词原则适用于**每个单独的 Agent**（每个 Agent 都需要好的 Prompt），但不解决 Agent 之间的协作问题
- 不涉及：任务分发、结果汇总、冲突解决、上下文传递等多人协作核心问题
- **可以用在：** 统一所有 Agent 的消息格式规范（相当于团队「沟通协议」）
- **不够用在：** Agent 编排、依赖管理、错误恢复等工作流层面的设计
- 建议：先用本知识库搞定每个 Agent 自身的提示词质量，再学 Agents 章节的编排技术

## 11. 常见失败

| # | 失败模式 | 典型表现 | 根本原因 |
|---|----------|----------|----------|
| 1 | **目标太模糊** | "帮我想想办法""写个好的文案" | 缺乏具体的任务指令和成功标准 |
| 2 | **缺少上下文** | AI 回答的方向完全偏离你的意图 | 没提供背景信息，模型只能猜 |
| 3 | **输出格式不清** | 返回一大段文字，但你想要表格 | 没指定 Output Indicator |
| 4 | **约束太少** | 回答太长/太短/太深奥/太浅显 | 没设定边界条件 |
| 5 | **一次塞太多任务** | 部分完成、遗漏、互相矛盾 | 把本该拆分的步骤合成一个 Prompt |
| 6 | **说了"不要什么"** | 模型偏偏做了你不要的事 | 负面指令的效果远差于正面指令 |
| 7 | **不给范例** | 输出格式和你预期的不一致 | Few-Shot 缺位，模型只能猜测格式 |
| 8 | **忽略了角色设定** | 回答语气、深度不适合你的场景 | 没有 Role Prompting，模型用默认模式回复 |
| 9 | **温度参数不当** | 创意任务太死板 / 事实任务太发散 | 不了解 Temperature 对任务类型的影响 |

## 12. 修正提示

针对上面的常见失败，一一给出修正版提示词：

### 修正 1：目标太模糊 → 加上明确任务指令

**❌ 错误：** "帮我想个文案"

**✅ 修正：**
```
请为我的一款慢回弹玩具撰写淘宝商品标题和主图文案。
- 目标客户：25-35 岁的办公室白领
- 核心卖点：减压、静音、桌面摆件
- 标题要求：30 字以内，包含关键词"解压""桌面""礼物"
- 主图文案：10 字以内，突出情绪价值
- 输出格式：
  ## 标题
  ## 主图文案（3 个备选）
```

### 修正 2：缺少上下文 → 补充背景信息

**❌ 错误：** "分析这组数据"

**✅ 修正：**
```
你是一位玩具品类运营分析师。请分析以下销售数据：

【背景】
- 数据来源：Essaone 品牌淘宝店铺上周（5.6-5.12）订单明细
- 分析目的：为周报准备，需要汇报给品牌负责人
- 关注重点：哪些品类的增长或下滑最值得关注

【数据】
[粘贴数据]

【输出要求】
按品类分组，列出销量 Top 5 和 Bottom 5，附带环比变化率。
```

### 修正 3：输出格式不清 → 加上 Output Indicator

**❌ 错误：** "提取里面的地点"

**✅ 修正：**
```
请从以下文本中提取所有地点名称。

文本：{粘贴文本}

输出格式（严格遵循）：
Place: <地点1>, <地点2>, <地点3>
```

### 修正 4：约束太少 → 设定边界

**❌ 错误：** "介绍一下 Prompt Engineering"

**✅ 修正：**
```
用 2-3 句话向一位有编程经验但没接触过 AI 的开发者介绍 Prompt Engineering。
- 不要超过 100 字
- 不要使用"大语言模型""神经网络"等技术术语
- 如果必须提到专业概念，用生活化的比喻替代
- 结尾加一句说明"这对我的日常工作有什么用"
```

### 修正 5：一次塞太多 → 拆分任务

**❌ 错误：** "帮我把这份报告翻译成英文，然后总结要点，再做成 PPT 大纲，最后发邮件给老板"

**✅ 修正（拆成 4 步）：**
```
## 第一步：翻译
请将以下中文报告翻译为商务英文：[报告内容]

## 第二步：总结
基于以上译文，提炼 5 个核心要点

## 第三步：PPT 大纲
基于 5 个要点，生成 10 页 PPT 的标题页大纲

## 第四步：邮件草稿
基于以上内容，起草一封发给老板的工作汇报邮件
```

### 修正 6："不要什么" → 改为"要什么"

**❌ 错误：** "不要用专业术语，不要太长，不要跑题"

**✅ 修正：**
```
请用高中生能听懂的通俗语言解释。
控制在 200 字以内。
紧扣主题：只解释什么是 API，不展开讲网络协议。
如果我不确定能否回答，请说"这个我不太确定"而不是编造答案。
```

### 修正 7：不给范例 → 加上 Few-Shot

**❌ 错误：** "把这些评论分类"

**✅ 修正：**
```
请将每条评论分类为"质量""物流""服务""其他"之一。

示例：
评论："发货太快了！" → 分类：物流
评论："东西坏了" → 分类：质量
评论："客服态度好" → 分类：服务

待分类：
1. "{评论 1}"
2. "{评论 2}"
3. "{评论 3}"

请按以下格式输出：
1. 分类：{类别}
2. 分类：{类别}
3. 分类：{类别}
```

### 修正 8：忽略角色 → 加上 Role Prompting

**❌ 错误：** 直接丢问题

**✅ 修正：**
```
你是一位有 10 年经验的玩具品类运营经理，擅长数据分析和竞品研究。
你的回答风格：数据驱动、言简意赅、给 actionable 的建议。

我的问题是：{问题}
```

### 修正 9：温度参数不当 → 匹配任务类型

**❌ 错误：** 所有任务都用 temperature=1

**✅ 修正：**
```
根据任务类型选择参数：
- 事实查询 / 数据提取 / 代码生成 → temperature: 0 ~ 0.3
- 一般对话 / 写作辅助 / 翻译 → temperature: 0.4 ~ 0.7
- 创意写作 / 头脑风暴 / 文案变体 → temperature: 0.8 ~ 1.0

当前任务是：{任务描述}
推荐设置：temperature: {对应值}
```

## 13. 示例

### 原始口语需求

> "我想让 AI 帮我整理一个学习计划，但是我不知道怎么说。"

### 问题诊断

对照常见失败清单，这个需求命中了：
- #1 目标太模糊 ——"学习计划"范围无限大
- #2 缺少上下文 —— 学什么、谁学、多久都不清楚
- #4 约束太少 —— 没有时间、难度、形式的要求
- #3 输出格式不清 —— 想要表格？日历？清单？

### 优化后的提示词

```markdown
# 角色
你是一个高效的学习规划顾问，擅长将复杂的学习目标拆解为可执行的计划。

# 任务
为我制定一份关于"提示工程（Prompt Engineering）"的学习计划

# 学习者画像
- 身份：品类运营从业者
- 技术水平：能看懂代码、会操作命令行，但非专业开发者
- 可用时间：每天 30-60 分钟
- 学习目的：能在工作中用 AI 提升效率，特别是周报自动化和多 Agent 工作流
- 已有基础：用过 ChatGPT，写过基本提示词，但缺乏系统性知识

# 学习计划要求
- 总周期：2 周（14 天）
- 每天 1 个学习模块，约 30-45 分钟
- 难度递进：从基础概念 → 实战模板 → 高级应用
- 每个模块包含：
  * 🎯 学习目标（1 句话）
  * 📚 学习内容（2-3 个知识点）
  * 🔨 动手练习（1 个具体任务）
  * ✅ 完成标准（怎么判断学会了）

# 输出格式
## 第一周：打好基础
| Day | 主题 | 目标 | 练习 | 预计时长 |

## 第二周：实战进阶
| Day | 主题 | 目标 | 练习 | 预计时长 |

## 参考资料
推荐 3-5 个优质资源（教程/工具/社区），附链接和推荐理由。
```

### OpenClaw 使用建议

**这是一个典型的「需求预处理 → 专业执行」场景：**

| 步骤 | Agent 类型 | 说明 |
|------|-----------|------|
| **1** | **需求理解 Agent** | 使用本知识库模板 A，将用户的"我想学 X"转化为上述结构化提示词 |
| **2** | **教学设计 Agent** | 接收结构化需求，生成学习计划（可以使用 RAG 检索最新的提示工程教程） |
| **3** | **进度跟踪 Agent**（可选） | 每日检查学习进度，根据掌握情况动态调整后续计划 |

**在 OpenClaw 中的配置建议：**
- Step 1 的 System Prompt 应固化本知识库的四大元素 + 五大原则
- Agent 之间传递的消息遵循"输入数据 + 输出指示"的统一格式
- 最终输出可直接保存为 Markdown 文件供用户查阅
