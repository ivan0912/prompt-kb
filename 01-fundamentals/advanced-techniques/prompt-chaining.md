# Prompt Chaining (PC) — 提示词链式调用

> 🟢 **立即掌握** | DAIR.AI Advanced Prompting #4 | [返回总览](../dair-ai-advanced-prompting.md)

---

## 1. 一句话解释

**把一个复杂任务拆成多个子步骤，每个步骤用一个独立的 prompt，上一步的输出作为下一步的输入。**

```
传统方式（一个 prompt 干所有事）：
用户文档 + 问题 → [巨型 prompt] → 最终答案 ❌ 可能混乱/遗漏

Prompt Chaining 方式：
Step 1: 文档 + 问题 → [提取引文 prompt] → 相关引文列表
Step 2: 文档 + 引文列表 + 问题 → [合成回答 prompt] → 最终答案 ✅ 结构化且可追溯
```

---

## 2. 适合什么时候用

- ✅ **复杂文档处理** — 长文章摘要、合同审查、报告生成
- ✅ **多步业务流程** — 周报自动化（数据提取→分析→报告）、客户分析 pipeline
- ✅ **需要可调试/可追溯的处理流程** — 每步输入输出独立可检查
- ✅ **OpenClaw 工作流设计** — **这是你在 OpenClaw 中最常用到的高级模式之一**
- ✅ **需要高质量输出的复杂任务** — 每步专注一件事，比一个大 prompt 干所有事更可靠

---

## 3. 不适合什么时候用

- ❌ **简单问答** — 一个 prompt 就够了，拆分反而是过度工程
- ❌ **步骤过多（>6 步）** — 累积误差和信息损失会抵消收益
- ❌ **步骤间依赖度低的任务** — 独立子任务不需要 chaining
- ❌ **Token 预算极紧** — 每步都要传递上一步的完整输出
- ❌ **需要实时响应的场景** — 多步骤串行执行增加延迟

---

## 4. 核心优势

| 优势 | 说明 |
|------|------|
| **任务分解** | 大任务拆成小任务，每个小任务更容易做好 |
| **可调试** | 每一步的输入输出都可以独立检查 |
| **可优化** | 单独调整某一步的 prompt 不影响其他步骤 |
| **错误隔离** | 出错了知道是哪一步的问题 |
| **透明度** | 整个处理流程清晰可见 |

**这是你在 OpenClaw 工作流中最常用到的高级模式之一。**

## 5. 中文提示词模板

### 模板：Prompt Chaining 多步 Pipeline ⭐ 工作流核心

> **推荐等级：** ⭐⭐⭐⭐⭐（搭建任何 AI 工作流的基础模式）

**通用 Step 模板：**
```markdown
## Step {N}: {步骤名称}

**角色：** {该步骤 AI 扮演的角色}
**输入：** {来自上一步的输出变量}
**任务：** {该步骤的具体任务}

**输出要求：** {该步骤的输出格式}

---
{该步骤的具体 prompt 内容}
```

**完整示例——周报异常分析 Pipeline：**

**Step 1：数据摘要提取**
```markdown
你是一个销售数据摘要助手。

**角色：** 从原始 Excel 数据中提取本周关键指标
**输入：** {本周原始销售数据}
**任务：** 提取各品类销量、环比、销售额 Top5/Bottom5

**输出要求：** JSON 格式
{
  "summary": {"total_sales": ..., "total_qty": ..., "wow_change": ...},
  "top5": [...],
  "bottom5": [...],
  "category_details": [...]
}
```

**Step 2：异常标记（CoT）**
```markdown
你是一个销售异常检测分析师。

**角色：** 基于 Step 1 的摘要数据，识别异常品类
**输入：** {Step 1 的 JSON 输出}
**任务：** 逐一判断每个品类的表现状态，说明理由

**输出要求：** 对每个异常品类给出：
- 品类名 | 异常类型 | 严重程度 | 推理过程 | 建议行动

请对每个异常品类逐步分析推理过程，不要只给结论。
```

**Step 3：报告生成**
```markdown
你是一个专业的周报撰写助手。

**角色：** 将 Step 1（数据）+ Step 2（分析）整合为正式报告
**输入：**
- 数据摘要：{Step 1 输出}
- 异常分析：{Step 2 输出}
**任务：** 生成面向管理层的周报正文

**输出要求：** Markdown 格式，包含执行摘要 + 详细分析 + 行动建议
```

## 6. OpenClaw 使用方式

### 配置方案：Prompt Chaining Pipeline（多 Agent 协作）

适用于：复杂业务流程（如周报自动化、客户分析 pipeline）。

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ Step 1   │───▶│ Step 2   │───▶│ Step 3   │───▶│ Step 4   │
│ 数据提取  │    │ 分析判断  │    │ 报告生成  │    │ 格式转换  │
│ Agent    │    │ CoT Agent│    │ Agent    │    │ Agent    │
└──────────┘    └──────────┘    └──────────┘    └──────────┘
                   ↑ CoT
                   增强
```

**关键设计原则：**
1. 每个 Agent 有**单一职责**（Single Responsibility）
2. Agent 之间通过**结构化数据传递**（JSON/XML/Markdown 表格）
3. 每个 step 可以**独立测试和替换**
4. 中间步骤出问题时容易**定位和修复**

**Prompt Chaining 天然就是多 Agent 的组织形式——每个 step 就是一个 Agent。**

---

## 7. 单 Agent 适配度

# ★★★☆☆ (3/5)

**原因：**
- Prompt Chaining 的本质是**多步骤/多调用**，即使叫"单 Agent"也需要多次调用
- 单 Agent 可以顺序执行各步骤（同一 Agent，多次调用），但失去了并行化的好处
- **更适合多 Agent 架构**

---

## 8. 多 Agent 适配度

# ★★★★★ (5/5)

**原因：**
- **Prompt Chaining 天然就是多 Agent 的组织形式**——每个 step 就是一个 Agent
- **这是构建多 Agent 工作流的最基础、最重要的模式**
- 掌握 Prompt Chaining 后就可以开始搭建真正的多 Agent 工作流了
- 比 Basic Prompting（★★★☆☆）高很多，因为高级技术本身就是围绕"复杂任务拆解与协作"设计的

---

## 9. 常见失败

| # | 失败模式 | 典型表现 | 根本原因 |
|---|----------|----------|----------|
| 1 | **步骤过多** | 10 步 chain 每步都有信息损失，最终输出质量下降 | 步骤越多累积误差越大。一般 **2-4 步为最佳区间** |
| 2 | **步骤间格式不兼容** | Step 1 输出自由文字，Step 2 期望 JSON，解析失败 | 必须严格约定每步的输入输出格式，最好用结构化数据 |
| 3 | **信息瓶颈** | Step 1 总结过度，Step 2 丢失了关键细节 | 每步输出要保留足够的上下文，不要过度压缩 |
| 4 | **错误传播** | Step 1 出错，后续所有步骤都基于错误数据继续 | 需要校验门（validation gate）拦截错误传播 |
| 5 | **过度拆分** | 3 步能做完的事拆成了 8 步 | 拆分的粒度应该是"逻辑边界"而不是"越细越好" |

## 10. 修正提示

### 修正：Prompt Chain 信息丢失 → 结构化传递 + 校验门

**❌ 错误：** Step 1 输出一大段文字，Step 2 丢失关键信息

**✅ 修正——强制结构化输出 + 门控校验：**
```
Step 1 Prompt（强制 JSON 输出）：
  ... 请严格按以下 JSON 格式输出，不要添加任何额外文字 ...

Step 1 ↔ Step 2 之间加入校验门：
  if output.json_parseable() and output.has_required_fields():
      pass_to_step2(output)
  else:
      retry_step1(max_retries=3)
      or fallback_to_manual()

每个 step 的 prompt 里明确写出期望的输入格式：
  "你的输入将是上一步产生的 JSON，包含以下字段：..."
```

**最佳实践 checklist：**
- [ ] 每 step 的输出格式明确定义（JSON schema 最好）
- [ ] step 间传递的数据结构一致
- [ ] 有错误重试机制（至少 1-2 次重试）
- [ ] 关键步骤有校验门
- [ ] 总步骤数控制在 2-6 步

## 11. 示例

### 场景：周报自动化完整 Pipeline

详见 [cot.md](cot.md) §11 中的完整示例。以下是 Prompt Chaining 的架构视角：

| 步骤 | 技术 | Agent 类型 | 输入 | 输出 |
|------|------|-----------|------|------|
| **Step 1: 数据准备** | Python 脚本 | 非 Agent | 原始 Excel | JSON 结构化数据 |
| **Step 2: 异常分析** | **CoT** | 单 Agent（增强） | Step 1 JSON | 异常列表 + 归因分析 |
| **Step 3: 报告整合** | Few-Shot | 单 Agent | Step 1 + Step 2 | 正式 Markdown 报告 |

**为什么不用 ReAct？**
- 当前任务的数据已经由 Python 准备好了，不需要实时搜索
- 分析所需的信息都在数据里，不需要调用外部工具
- CoT 已经足够处理这类"数据 → 见解"的纯推理任务

**什么时候应该升级到 ReAct？**
- 如果你希望 AI 能主动去查竞品价格、查行业趋势、查天气等因素来做归因
- 那就是 ReAct 的典型场景了（Thought: 查一下竞品 → Action: Search[...]）

## 12. 与其他技术的组合方式

| 组合 | 方式 | 效果 |
|------|------|------|
| **Chaining + CoT** | Chaining 的某个/多个步骤内部使用 CoT | **最常用组合**——几乎所有的 Chaining pipeline 都会在分析步骤加 CoT |
| **Chaining + ReAct** | 某个步骤用 ReAct Agent（需要外部信息时） | 混合 pipeline——大部分步骤普通 chaining，特定步骤升级为 ReAct |
| **Chaining + GK** | Step 1 用 GK 生成领域知识，后续步骤引用 | 适用于需要领域上下文的完整 workflow |
| **Chaining + SC** | Chaining 的关键步骤用 SC 增强精度 | 仅对容易出错的步骤加 SC，控制成本 |

**Chaining 是"骨架"，其他技术是"肌肉"。** 先搭 Chaining 骨架，再在需要的步骤上填充 CoT/GK/ReAct 等技术。
