## 4. 核心概念

### 4.1 Zero-Shot Prompting（零样本提示）

**定义：不给任何示例，直接下指令让模型干活。**

```
Prompt: 把这段话分类为正面、负面或中性。
文本：我觉得这个产品还行。

输出：中性
```

**为什么能用？**
现代大模型（GPT-4、Claude 3 等）经过两个关键训练阶段：
1. **指令微调（Instruction Tuning）**：在大量「指令→回答」数据对上训练，让模型学会理解并执行自然语言指令
2. **RLHF（人类反馈强化学习）**：让模型的输出更符合人类的期望和行为规范

这两个阶段使得模型具备了「听懂人话直接干活」的能力，不需要额外的示例。

**适合 Zero-Shot 的任务特征：**
- 任务定义清晰，模型在训练中见过类似任务
- 不需要特殊输出格式（或格式要求简单）
- 对准确性要求不是极高，容错空间大

**不适合 Zero-Shot 的信号：**
- 模型输出的格式和你预期的不一致
- 同样的 prompt 多次运行结果不稳定
- 任务涉及多步推理或复杂判断

---

### 4.2 Few-Shot Prompting（少样本提示）

**定义：在正式提问前，先给模型看 2-5 个「输入→输出」的范例，让它照着做。**

```
Prompt:
这个太棒了！ → 正面
真差劲！ → 负面
哇这电影太酷了！ → 正面
这节目真烂！ →

输出：负面
```

**核心机制：上下文学习（In-Context Learning）**

> 模型不需要重新训练权重。它通过你提供的几个范例，在当前对话的上下文中自动学会任务的规律，然后应用到新问题上。

这是一个非常强大的能力——意味着你不需要任何机器学习背景，只要会写例子就能「教」模型新技能。

**Few-Shot 为什么比 Zero-Shot 更强？**
| 维度 | Zero-Shot | Few-Shot |
|------|-----------|----------|
| 输出格式的控制力 | 弱 — 模型自由发挥 | 强 — 范例锁定期望格式 |
| 任务边界的明确性 | 模糊 — 靠模型猜测 | 清晰 — 范例划定范围 |
| 对罕见/定制任务的支持 | 差 | 好 |
| Token 消耗 | 少 | 多（每个范例占 token） |
| 编写难度 | 低 | 中（需要设计好范例） |

---

### 4.3 Few-Shot 的关键研究发现（Min et al., 2022）

这是 DAIR.AI 引用的一个重要研究结论，反直觉但极其实用：

| 发现 | 说明 | 对你的实际意义 |
|------|------|----------------|
| **标签空间分布重要** | 范例中各类别出现的比例影响结果 | 如果你希望模型偏向某个类别，就在范例里多放该类别的样例 |
| **格式比正确性更重要** | 即使范例的标签标错了（如把 Positive 标为 Negative），只要格式一致，模型仍能学会正确的分类方向 | 先把格式搞对，再纠结标签是否完美 |
| **随机标签 > 没有标签** | 给乱标的范例都比不给范例好 | 宁可随便给几个例子也不要纯 Zero-Shot |
| **真实分布的随机标签更好** | 从真实数据分布中随机抽样作为标签，比均匀随机更好 | 用真实业务数据的格式做范例效果最好 |

**一句话总结：范例的作用主要是「锁定格式和方向」，而不是「传授知识」。格式一致性 > 标签准确性。**

### 4.4 选择策略：什么时候用什么？

```
你的任务
  │
  ├─ 简单明确的任务（翻译、改写、简单分类）
  │   └─ 先试 Zero-Shot → 够用就别折腾
  │
  ├─ Zero-Shot 结果不理想？
  │   └─ 加上 2-3 个 Few-Shot 范例
  │       └─ 还是不行？
  │           └─ 加到 5-10 个范例
  │               └─ 还是不行？
  │                   └─ 该换高级技巧了（Chain-of-Thought 等）
  │
  └─ 复杂推理任务（数学、逻辑、多步分析）
      └─ 直接跳过 Few-Shot → 用 Chain-of-Thought（不在本条目范围内）
```

**黄金法则：从最简单的开始，逐步增加复杂度。**

## 5. 适用场景

- ✅ **文本分类 / 情感分析** — Few-Shot 的经典战场，2-3 个范例就能稳定输出格式
- ✅ **信息提取** — 通过范例指定提取的字段名和输出结构
- ✅ **格式转换** — 如 JSON ↔ 表格 ↔ 自然文字，用范例演示目标格式
- ✅ **翻译（带风格约束）** — Zero-Shot 能翻，但 Few-Shot 能锁定术语和语气
- ✅ **内容审核 / 规则判断** — 用范例教会模型你的业务规则
- ✅ **周报自动化中的标准化输出** — 让 AI 按固定模板填数据（模板 A 的实战应用）
- ✅ **OpenClaw 单 Agent 的输入预处理** — 统一用户输入的格式后再分发给下游 Agent
- ✅ **快速原型测试** — Zero-Shot 快速验证想法是否可行
- ✅ **API 成本敏感场景** — Zero-Shot 省 token，适合大批量调用

---

## 6. 不适用场景

- ❌ **复杂多步推理（数学证明、逻辑链推导）** — Few-Shot 在这类任务上的准确率极低，需要 Chain-of-Thought
- ❌ **需要外部知识的任务（实时查询、私有数据检索）** — 需要 RAG 技术
- ❌ **长文档深度分析** — 上下文窗口限制 + 需要分段策略
- ❌ **代码生成复杂功能** — 简单函数可以，但完整模块/系统需要更精细的技术
- ❌ **多 Agent 编排与协作** — 单纯的 Zero/Few-Shot 无法解决 Agent 间的依赖管理
- ❌ **图像生成的细节提示词** — 文字提示原则适用，但有专属语法和参数体系
- ❌ **对抗性安全防护** — 需要专门的安全提示技术
- ❌ **需要高度创造性且格式不确定的任务** — 过多的 Few-Shot 可能限制模型创造力

## 7. 中文提示词模板

### 模板 A：Zero-Shot 快速执行模板

> **使用场景：** 任务简单明确，你想最快速度拿到结果。日常使用频率最高。

```markdown
{指令动词}{任务描述}。

{输入内容}

{输出指示}
```

**填空示范：**
```markdown
总结以下客户评价的核心观点，不超过 50 字。

[粘贴评价内容]

请按以下格式输出：
- 正面反馈要点：...
- 负面反馈要点：...
- 改进建议：...
```

**变体——加角色设定（Zero-Shot + Role Prompting）：**
```markdown
你是一个{角色}。

{任务描述}。

{输入内容}

{输出要求}
```

**填空示范：**
```markdown
你是一个有经验的电商客服主管。

请将以下客户投诉归类为「物流问题」「质量问题」「服务态度」「其他」，并给出优先级（高/中/低）。

[粘贴投诉内容]

输出格式：
| 投诉内容摘要 | 分类 | 优先级 | 建议 |
```

---

### 模板 B：Few-Shot 格式锁定模板

> **使用场景：** Zero-Shot 输出格式不对、不稳定，或者你需要严格控制输出格式时使用。

```markdown
{任务指令}

{示例 1 输入}
{输出分隔符}{示例 1 输出}

{示例 2 输入}
{输出分隔符}{示例 2 输出}

{示例 3 输入}
{输出分隔符}{示例 3 输出}

{目标输入}
{输出分隔符}
```

**填空示范——销售数据分析：**
```markdown
请根据以下数据判断每个品类的周表现状态。

示例：
品类：积木玩具 | 销量: 1200 | 环比: +15% | 状态：增长强劲 📈
品类：拼图玩具 | 销量: 300 | 环比: -5% | 状态：平稳 ➡️
品类：遥控车 | 销量: 80 | 环比: -32% | 状态：预警 ⚠️
品类：慢回弹玩具 | 销量: 2100 | 环比: +8% | 状态：

待分析：
品类：陀螺 | 销量: 150 | 环比: -18%
品类：DIY 手工 | 销量: 600 | 环比: +22%
品类：电动宠物 | 销量: 45 | 环比: -41%
```

---

### 模板 C：Few-Shot 渐进优化模板

> **使用场景：** 你不确定该给几个范例、不知道格式是否合理时的迭代流程。

**Step 1 — 先 Zero-Shot 试水：**
```markdown
{任务描述}
{输入}
```
→ 检查输出是否满意？满意就到此为止。

**Step 2 — 不满意？加 1 个范例（1-Shot）：**
```markdown
{任务描述}

示例：
{输入 A}
{期望输出 A}

{真实输入}
```
→ 再检查。好多了？可能 1 个就够了。

**Step 3 — 还是不够？加到 3 个范例（3-Shot）：**
```markdown
{任务描述}

示例 1：
{输入 A} → {输出 A}
示例 2：
{输入 B} → {输出 B}
示例 3：
{输入 C} → {输出 C}

{真实输入} →
```

**Step 4 — 还是不行？考虑以下选项：**
- 范例数量加到 5-10 个
- 检查你的范例本身是否有歧义
- **放弃 Few-Shot，升级到 Chain-of-Thought 或其他高级技巧**

**关键心态：每一步都验证，不要一上来就写 10 个范例。**

## 8. OpenClaw 使用方式

| 维度 | 说明 |
|------|------|
| **适合单 Agent 吗？** | ✅ **非常适合**。Zero-Shot 和 Few-Shot 是单 Agent 最核心的交互方式 |
| **适合多 Agent 吗？** | ⚠️ **部分适合**。Agent 内部执行具体任务时用得到，但不解决编排问题 |
| **适合放入 system prompt 吗？** | ⚠️ **有限适合**。System Prompt 适合放 Zero-Shot 的角色和规则；Few-Shot 范例更适合放在 User Message 中动态传入 |
| **适合作为工作流前置步骤吗？** | ✅ **非常适合**。可以用 Few-Shot Agent 做「格式标准化网关」，统一所有用户输入 |
| **OpenClaw 中应该如何调用？** | 见下方详细配置 |

### OpenClaw 配置方案

#### 方案 1：Zero-Shot Agent（轻量快速）

适用于：简单查询、格式转换、标准分类等高频低复杂度任务。

```
┌─────────────────────────────────────┐
│         Zero-Shot Agent             │
├─────────────────────────────────────┤
│ System Prompt:                      │
│   你是{角色}。                       │
│   你的任务是{任务定义}。              │
│   输出必须遵循以下格式：              │
│   {格式模板}                        │
│                                     │
│ User Message:                       │
│   {用户的原始输入}                   │
└─────────────────────────────────────┘
```

#### 方案 2：Few-Shot Agent（格式标准化网关）

适用于：用户输入五花八门，需要统一格式后才能交给下游 Agent 处理。

```
┌──────────────────────────────────────────┐
│       Few-Shot 格式标准化 Agent           │
├──────────────────────────────────────────┤
│ System Prompt:                           │
│   你是一个输入格式标准化处理器。            │
│   你的任务是将用户的非结构化输入转换为      │
│   标准化的 JSON 格式。                    │
│                                          │
│ User Message（动态生成）：                 │
│   请将以下输入标准化：                    │
│                                          │
│   示例 1：                               │
│   输入："帮我看看上周卖得怎么样"          │
│   输出：{"intent":"sales_analysis",       │
│     "time_range":"last_week",            │
│     "metrics":["sales","qty"],            │
│     "confidence":0.9}                    │
│                                          │
│   示例 2：                               │
│   输入："哪个品类的环比跌最多"            │
│   输出：{"intent":"anomaly_detection",    │
│     "metric":"wow_change",               │
│     "sort_direction":"asc",              │
│     "confidence":0.95}                   │
│                                          │
│   待处理输入：                            │
│   "{用户的实际输入}"                      │
└──────────────────────────────────────────┘
         ↓
    标准化 JSON 输出
         ↓
┌──────────────────────────┐
│   下游专业 Agent 接收     │
└──────────────────────────┘
```

**核心价值：** 这个 Few-Shot 网关 Agent 是整个工作流的「翻译官」，确保不管用户怎么说话，下游 Agent 收到的都是结构化的、可靠的指令。

## 9. 单 Agent 适配度

# ★★★★★ (5/5)

**原因：**
- Zero-Shot 和 Few-Shot 就是**为单 Agent 设计的**最基本交互范式
- 单 Agent 的 System Prompt = 增强版 Zero-Shot（持久化角色 + 规则）
- 单 Agent 的 User Message = 天然的 Few-Shot 承载位置
- 所有主流 AI 应用（ChatGPT、Claude 等）的单轮/多轮对话本质上都是 Zero/Few-Shot 的变种
- 开销最低、实现最快、调试最简单的单 Agent 方案

---

## 10. 多 Agent 适配度

# ★★★☆☆ (3/5)

**原因：**
- **可以用在：** 每个 Agent 内部的具体任务执行（如「分类 Agent」用 Few-Shot 判断意图，「提取 Agent」用 Few-Shot 提取字段）
- **特别适合做：** Agent 之间的「协议转换层」（如上面的格式标准化网关）
- **不够用在：** 不解决 Agent 编排、依赖管理、错误恢复、上下文传递等核心问题
- 比 Introduction 的 ★★☆☆☆ 高一档，因为 Few-Shot 在多 Agent 场景中有明确的实用价值（格式标准化）
- 建议：先用 Few-Shot 搞定单个 Agent 的输入输出质量，再叠加 Agents 章节的编排技术

## 11. 常见失败

| # | 失败模式 | 典型表现 | 根本原因 |
|---|----------|----------|----------|
| 1 | **Zero-Shot 格式失控** | 你要表格，它给你一大段文字；你要 JSON，它给你 Markdown | 没有通过范例或显式格式指示锁定输出结构 |
| 2 | **Few-Shot 范例质量差** | 给了 5 个范例，模型输出还是不对 | 范例本身有歧义、不一致，或没有覆盖边界情况 |
| 3 | **Few-Shot 范例太多** | Prompt 超长、token 爆炸、反而效果下降 | 盲目堆砌范例，没有遵循「从小到大」的渐进策略 |
| 4 | **混淆 Zero-Shot 和 Few-Shot 适用场景** | 简单任务硬加范例浪费 token，复杂任务只用 Zero-Shot 反复失败 | 没有按照选择策略判断该用哪种模式 |
| 5 | **忽略了标签空间分布** | 模型总是偏向某一种分类结果 | 范例中各类别样本数不均衡导致偏差 |
| 6 | **Few-Shot 用于复杂推理** | 数学题、逻辑推理题给了 10 个范例还是答错 | Few-Shot 不能替代 Chain-of-Thought，多步推理需要思路拆解而非范例堆叠 |
| 7 | **输出格式与范例不一致** | 范例用 `A → B` 格式，但目标问题换了格式 | 目标问题的呈现方式和范例不匹配，模型困惑 |
| 8 | **在 System Prompt 里塞 Few-Shot 范例** | 每次对话都重复发送范例，浪费 token 且难以维护 | Few-Shot 范例应该放在 User Message 中按需加载 |

## 12. 修正提示

### 修正 1：Zero-Shot 格式失控 → 加上 Output Indicator 或切换 Few-Shot

**❌ 错误：** "分析这段评论"

**✅ 修正方案 A（加强 Zero-Shot）：**
```
分析以下客户评论，严格按表格格式输出：

| 评论要点 | 情感倾向 | 优先级 | 建议行动 |

[粘贴评论]
```

**✅ 修正方案 B（切 Few-Shot）：**
```
分析以下客户评论的情感和优先级。

示例：
评论："物流太慢了，等了一周才到" | 情感：负面 | 优先级：高 | 行动：联系物流
评论："东西不错，包装很用心" | 情感：正面 | 优先级：低 | 行动：无
评论："客服回复很快但是解决方案不行" | 情感：混合 | 优先级：中 | 行动：跟进

待分析：
[粘贴评论]

输出格式：评论要点 | 情感 | 优先级 | 行动建议
```

### 修正 2：Few-Shot 范例质量差 → 检查三件事

**检查清单：**
```
□ 范例的输入是否清晰无歧义？
□ 范例的输出是否是你真正想要的目标格式？
□ 各个范例之间的格式是否完全一致？

如果以上任一项为「否」，重写范例。
```

**常见错误范例 vs 修正后的范例：**

**❌ 差范例（有歧义）：**
```
这个产品很好 → 正面评价
那个不太行 → 
```
> 问题：「很好」和「不太行」太模糊，模型不知道什么算好什么算不好

**✅ 好范例（清晰具体）：**
```
这款积木拼装顺滑，零件精度很高，孩子很喜欢 → 正面评价 | 推荐
发货晚了两天，盒子有压痕，但里面东西没坏 → 负面评价 | 需改进物流
价格有点贵，不过质量确实比便宜的好 → 混合评价 | 观望
```

### 修正 3：Few-Shot 范例太多 → 遵循渐进策略

**❌ 错误：** 一上来就写 10 个范例

**✅ 修正——逐步递增法：**
```
第 1 次：0 个范例（Zero-Shot）→ 评估结果
第 2 次：1 个范例（1-Shot）→ 评估结果
第 3 次：3 个范例（3-Shot）→ 评估结果
→ 如果 3 个已经够了，就停在这里。不要为了「保险」加到 10 个。
```

### 修正 4：混淆适用场景 → 用决策树判断

**❌ 错误：** 所有任务都用同一种模式

**✅ 修正——每次写提示词前问自己三个问题：
```
1. 这个任务模型之前大概率见过吗？（是 → 先试 Zero-Shot）
2. 我对输出格式有严格要求吗？（是 → 直接上 Few-Shot）
3. 这个任务需要多步推理吗？（是 → Few-Shot 可能不够，准备升级）
```

### 修正 5：标签空间分布不均 → 平衡范例

**❌ 错误：** 5 个范例里 4 个是正面的，1 个负面的

**✅ 修正：**
```
确保每个类别至少有 1-2 个范例。
如果业务中某些类别天然更多见，可以适当加权，
但要意识到这会让模型偏向该类别。

推荐默认配比：均衡分布（各类别样本数相等），
只在有明确理由时才故意偏斜。
```

### 修正 6：Few-Shot 用于复杂推理 → 认清边界

**❌ 错误：** 给了 8 个数学题范例，模型还是算错

**✅ 认知调整：**
```
Few-Shot 的能力边界：
✅ 格式锁定（输出长什么样）
✅ 任务方向（大致要干什么）
✅ 简单模式识别（这个像那个）
✗ 多步推理拆解（第一步做什么→第二步→第三步）
✗ 复杂计算（数学运算、数据统计）

如果你的任务落在 ✗ 区域：
→ 停止增加范例
→ 改用 Chain-of-Thought（让模型展示思考步骤）
→ 或接受：这个任务需要高级技巧 / 微调 / 代码辅助
```

### 修正 7：输出格式与范例不一致 → 统一格式

**❌ 错误：**
```
范例：Q: xxx? A: yyy
目标问题：请判断下面的文本属于哪一类：zzz
```

**✅ 修正：**
```
范例：
问题：xxx?
答案：yyy

问题：aaa?
答案：bbb

问题：zzz?
答案：
```

**原则：目标问题的呈现方式要和范例保持一致——同样的引导语、同样的分隔符、同样的结构。**

### 修正 8：System Prompt 塞范例 → 移到 User Message

**❌ 错误：** 把 5 个 Few-Shot 范例写在 System Prompt 里，每次 API 调用都发送一遍

**✅ 修正：**
```
System Prompt（精简，只放不变的内容）：
  你是一个{角色}。你的任务是{任务定义}。

User Message（动态，按需放入范例）：
  {Few-Shot 范例}
  {当前要处理的输入}
```

**好处：**
- System Prompt 更短更干净
- 范例可以根据不同类型的输入动态调整
- 降低每次调用的 token 消耗（System Prompt 通常会计入缓存，但超长仍然浪费）

## 13. 示例

### 原始口语需求

> "我每周要从 Excel 里整理一堆销售数据做成周报，每次都要手动分类哪些卖得好哪些卖得差，能不能让 AI 自动帮我判？"

### 需求分析

对照 Basic Prompting 的选择策略：
- 任务定义清晰吗？✅ 是的——判断销售表现
- 需要特定输出格式吗？✅ 是的——需要固定的分类和标记
- 需要多步推理吗？❌ 不是——基于规则的判断即可
- **结论：适合 Few-Shot，目标是锁定输出格式**

### 优化后的提示词

```markdown
你是一个玩具品类销售数据分析助手。请根据销量和环比变化率，判断每个品类的周表现状态。

## 判断标准
- 📈 增长强劲：销量 > 500 且 环比 > +10%
- 📊 稳步增长：销量 > 300 或 环比在 0%~+10% 之间
- ➡️ 平稳：环比在 -10%~+10% 之间，无明显趋势
- ⚠️ 预警：环比 < -10% 但销量 > 100
- 🔴 下滑严重：环比 < -20% 或 销量 < 50

## 参考示例

品类：积木套装 | 销量: 1,250 | 环比: +15.2% | 状态：📈 增长强劲
品类：木质拼图 | 销量: 280 | 环比: -3.5% | 状态：➡️ 平稳
品类：遥控赛车 | 销量: 85 | 环比: -31.8% | 状态：⚠️ 预警
品类：慢回弹捏捏乐 | 销量: 2,100 | 环比: +8.3% | 状态：📊 稳步增长
品类：儿童科学实验 | 销量: 32 | 环比: -45.0% | 状态：🔴 下滑严重

## 待分析数据

品类：{品类名称 A} | 销量: {数值} | 环比: {百分比}%
品类：{品类名称 B} | 销量: {数值} | 环比: {百分比}%
品类：{品类名称 C} | 销量: {数值} | 环比: {百分比}%
（... 更多品类 ...）

## 输出格式

严格按以下格式逐行输出，不要添加额外说明：

品类：{名称} | 销量: {数值} | 环比: {百分比}% | 状态：{ emoji } {等级名称}
```

### OpenClaw 使用建议

**这是典型的「单 Agent + Few-Shot」场景，可以直接嵌入现有周报自动化工作流：**

| 步骤 | 角色 | 说明 |
|------|------|------|
| **输入** | Python Pipeline | 从 Excel 读取本周数据，计算各品类销量和环比 |
| **处理** | Few-Shot Analysis Agent | 将数据和上面的提示词一起发送给 LLM |
| **输出** | 结构化文本 | LLM 返回带状态标记的分类结果 |
| **后续** | 报告生成 Agent | 将分类结果写入周报 Markdown/Excel |

**为什么不用多 Agent？**
- 这个任务的核心难点是「判断标准的传达」，Few-Shot 一次搞定
- 不涉及跨 Agent 协作、条件分支、错误恢复等复杂逻辑
- 单 Agent + 好的 Few-Shot = 最简最优解
