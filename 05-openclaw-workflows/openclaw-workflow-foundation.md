# OpenClaw 多 Agent 工作流基础规范

> **规范编号**: T-OPENCLAW-001
> **版本**: v0.1
> **创建日期**: 2026-05-27
> **更新日期**: 2026-05-27
> **本次更新**: 创建 OpenClaw 多 Agent 工作流基础规范，作为 Phase 5 的底层规范
> **依据来源**:
> - T-CONFIG-001 通用模板结构规范（模板骨架与元规范定位）
> - T-CONFIG-003 模型类型与提示策略判断规范（单/多 Agent 判断参考）
> - T-CONFIG-005 格式描述与占位符规范（输出格式标准）
> - T-CONFIG-006 长上下文输入规范（参考资料与长流程处理）
> - T-TEXT-001 模糊需求转计划 Pipeline（需求澄清→结构化执行的方法论）
> - T-IMG-001 / T-IMG-002 图像模块（规范→速查→案例→平台适配→测试闭环参考）
> - T-VIDEO-001 / T-VIDEO-002 视频模块（同上）
> - Phase 3 / Phase 4 阶段性验收经验
> **性质**: 工作流基础规范——本身不是提示词模板、不是图像/视频规范、不是具体案例。定义如何将 Prompt-KB 已有模块组织成可执行的 OpenClaw 工作流

## 1. 规范目标

### 本规范解决什么问题

| # | 问题 | 说明 |
|---|------|------|
| 1 | **复杂需求不知道怎么拆** | 用户说"帮我建一个知识库"，不知道从哪开始、分几步、每步产出什么 |
| 2 | **不知道该用单 Agent 还是多 Agent** | 所有任务都用单 Agent 效率低，所有任务都用多 Agent 过度复杂 |
| 3 | **不知道调用 Prompt-KB 哪个文件** | 有 T-CONFIG、T-TEXT、T-IMG、T-VIDEO、CS/TEST 多层体系，不知道从哪入手 |
| 4 | **执行顺序混乱** | 先写案例再写规范、先登记导航再验收产物、先创建再修改 |
| 5 | **验收标准缺失** | 创建完就结束，不知道质量是否达标 |
| 6 | **范围漂移** | 验收时顺手小修、登记时修改正文、测试时改模板 |
| 7 | **失败后不知道怎么恢复** | 会话中断、路径错误、搜索循环、输出太长 |
| 8 | **产物不登记** | 创建了文件但没更新 README/QUICKSTART，后续找不到 |
| 9 | **没有下一步建议** | 每次执行完不知道接下来该做什么 |

**核心定位**：T-OPENCLAW-001 是 Prompt-KB 的"任务调度层"，负责把已有规范、模板、案例组织成可执行的工作流。它不替代任何具体模块，而是定义如何使用这些模块。

### 本规范不解决

| # | 不解决的问题 | 原因 |
|---|-------------|------|
| 1 | 具体文本/图像/视频提示词模板 | 由 T-TEXT、T-IMG、T-VIDEO 系列负责 |
| 2 | 具体平台参数 | 由各平台官方文档和平台适配模板负责 |
| 3 | Agent 执行一定无误 | AI 执行仍有随机性，本规范只能提高成功率和可追踪性 |
| 4 | 高风险/违法/越权任务 | 涉及安全边界的任务不在本规范范围内 |
| 5 | 替代人工最终判断 | 本规范提供决策框架，最终判断仍需人工 |

## 3. OpenClaw 工作流核心公式

### 核心公式

```
OpenClaw 工作流 = 任务识别 + 范围界定 + 资源定位 + 单/多Agent判断
                + 执行计划 + 产物生成 + 验收检查 + 小修处理
                + 导航登记 + 下一步决策
```

### 各环节说明

| 环节 | 作用 | 简单任务 | 复杂任务 |
|------|------|----------|----------|
| **任务识别** | 判断任务类型 | 快速判断 | 详细分类 |
| **范围界定** | 确定修改/创建/保护范围 | 显式列出 | 分阶段列出 |
| **资源定位** | 找到需要参考的规范/模板/案例 | 直接引用 | 多文件检索 |
| **单/多 Agent 判断** | 决定执行方式 | 默认单 Agent | 评估是否需要多 Agent |
| **执行计划** | 确定执行顺序 | 一步到位 | 分步骤+检查点 |
| **产物生成** | 创建目标文件 | 直接生成 | 分阶段生成 |
| **验收检查** | 检查质量 | 轻量复核 | 完整验收 |
| **小修处理** | 修正问题 | 即时修正 | 独立小修任务 |
| **导航登记** | 更新索引和状态 | 必须执行 | 必须执行 |
| **下一步建议** | 给出后续方向 | 必须输出 | 必须输出 |

### 关键原则

1. **简单任务可以单 Agent 直接执行**：目标明确、范围小、不涉及多模块
2. **复杂任务需要拆分步骤**：分阶段执行，每阶段有明确产出
3. **高价值任务需要验收**：新规范、新模板、新案例必须经过验收
4. **长链路知识库任务必须登记导航**：创建了文件就必须更新索引
5. **不确定任务先澄清，不要直接执行**：参考 T-TEXT-001 的需求澄清方法

## 4. 工作流核心维度

### 维度总表

| # | 维度 | 作用 | 什么时候必填 | 怎么写 | 常见错误 |
|---|------|------|-------------|--------|----------|
| 1 | **任务目标** | 明确本次要做什么 | 每次必填 | 一句话说明目标，如"创建 T-OPENCLAW-001 v0.1" | 目标太模糊（"优化一下"）或太宽泛（"完善整个知识库"） |
| 2 | **任务类型** | 分类以便选择执行方式 | 每次必填 | 从§5任务类型表中选择 | 不分类直接执行，导致流程不匹配 |
| 3 | **输入资料** | 用户提供的原始材料 | 有资料时必填 | 列出文件路径或内容摘要 | 遗漏关键资料或资料路径错误 |
| 4 | **参考文件** | 需要参考的已有产物 | 每次必填 | 列出文件路径+用途说明 | 参考过多导致上下文溢出，或参考不足导致遗漏 |
| 5 | **目标文件** | 本次要创建/修改的文件 | 每次必填 | 列出完整路径 | 路径错误或目标文件不明确 |
| 6 | **产物类型** | 输出什么类型的文件 | 每次必填 | 规范/模板/速查卡/案例/测试记录/报告 | 类型不清导致结构错误 |
| 7 | **复杂度等级** | L1-L5 复杂度判断 | 每次必填 | 从§6复杂度表中判断 | 低估复杂度导致遗漏步骤 |
| 8 | **单 Agent / 多 Agent 判断** | 决定执行方式 | 每次必填 | 参考§7判断规范 | 简单任务用多 Agent（过度复杂），复杂任务用单 Agent（质量不足） |
| 9 | **执行顺序** | 确定步骤和依赖 | L2+ 必填 | 列出有序步骤 | 步骤遗漏或顺序颠倒 |
| 10 | **验收标准** | 判断产物是否合格 | L2+ 必填 | 列出检查项或评分标准 | 无验收标准导致"创建即完成" |
| 11 | **保护文件** | 不应修改的文件 | 每次必填 | 显式列出保护清单 | 未列出保护文件导致误改稳定文件 |
| 12 | **是否需要小修** | 判断是否需要修正 | 验收后判断 | 根据验收结论判断 | 不需要小修时强行小修，或需要小修时跳过 |
| 13 | **是否需要导航登记** | 判断是否更新索引 | 创建新文件时必填 | 创建/验收新产物后必须登记 | 创建了文件但不登记，后续找不到 |
| 14 | **是否需要案例验证** | 判断是否需要案例测试 | 新模板/新规范时 | 参考 TEST-IMG/TEST-VIDEO 经验 | 新模板不验证就投入使用 |
| 15 | **是否需要平台适配** | 判断是否需要多平台版本 | 图像/视频模板时 | 参考 T-IMG-002/T-VIDEO-002 | 文本任务不需要平台适配 |
| 16 | **是否需要人工确认** | 判断哪些环节需要人工 | 高风险/不确定时 | 列出需要确认的问题 | 全自动执行高风险任务，或低风险任务也要求人工确认 |
| 17 | **输出报告** | 执行完成后输出摘要 | 每次必填 | 参考§17报告模板 | 不输出报告或报告不完整 |
| 18 | **下一步建议** | 给出后续方向 | 每次必填 | 从§23候选建议中选择 | 不给下一步建议导致停滞 |

## 5. 任务类型分类

### 任务类型表

| 任务类型 | 适用场景 | 推荐执行方式 | 是否需要验收 | 是否需要登记 |
|----------|----------|-------------|-------------|-------------|
| **创建规范** | 新建基础规范（如 T-OPENCLAW-001） | 单 Agent，参考已有规范结构 | ✅ 完整验收 | ✅ 必须登记 |
| **创建模板** | 新建提示词模板（如 T-TEXT-001） | 单 Agent，遵循 T-CONFIG-001 | ✅ 完整验收 | ✅ 必须登记 |
| **创建速查卡** | 从规范压缩出快速参考 | 单 Agent，对照规范校准 | ✅ 轻量验收 | ✅ 必须登记 |
| **创建案例** | 记录实际使用成功/失败案例 | 单 Agent，参考已有案例格式 | ✅ 轻量验收 | ✅ 必须登记 |
| **创建平台适配模板** | 多平台改写模板（如 T-IMG-002） | 单 Agent，参考已有适配模板 | ✅ 完整验收 | ✅ 必须登记 |
| **创建测试记录** | 用案例测试模板可用性 | 单 Agent，参考 TEST 经验 | ✅ 检查清单验收 | ✅ 必须登记 |
| **质量验收** | 对新产物做完整质量检查 | 只读，不修改文件 | — 本身就是验收 | 验收后登记 |
| **轻量复核** | 对小修后产物做快速检查 | 只读，检查修正点 | — 轻量检查 | 视情况登记 |
| **小修** | 修正已验收产物的小问题 | 限定修改范围，升级版本 | ✅ 轻量复核 | 视情况更新 |
| **导航登记** | 将产物登记到索引 | 不修改正文，只更新索引 | — 不涉及 | ✅ 本身就是登记 |
| **阶段性验收** | 判断模块是否可以收尾 | 只读分析，输出结论 | — 本身就是验收 | 视结论登记 |
| **阶段状态更新** | 更新 Phase 状态（进行中→完成） | 增量更新，不重写全文 | — 不涉及 | ✅ 必须更新 |
| **长上下文资料整理** | 整理大量参考资料 | 分块处理，参考 T-CONFIG-006 | ✅ 轻量验收 | 视情况登记 |
| **多文件索引更新** | 批量更新 README/QUICKSTART | 增量更新，列出所有修改 | — 不涉及 | ✅ 本身就是索引更新 |
| **失败修复** | 修复之前执行失败的任务 | 分析失败原因，限定修复范围 | ✅ 轻量复核 | 视情况更新 |
| **版本升级** | 对已有产物做重大更新 | 参考已有版本，明确变更内容 | ✅ 完整验收 | ✅ 必须登记 |

## 6. 复杂度分级

### L1-L5 复杂度表

| 等级 | 任务特征 | 推荐方式 | 是否需要拆分 | 是否需要验收 | 是否需要人工确认 |
|------|----------|----------|-------------|-------------|-----------------|
| **L1** | 简单单文件修改（错别字、格式修正、一行改动） | 单 Agent 直接执行 | 否 | 轻量复核 | 否 |
| **L2** | 单文件创建或小修（新案例、速查卡小修、版本号升级） | 单 Agent 执行 | 否 | 轻量验收 | 否 |
| **L3** | 多文件导航更新 / 案例创建 / 测试记录 | 单 Agent + 清单驱动 | 建议拆分 | 完整验收 | 视情况 |
| **L4** | 新模块基础规范 / 平台适配模板 / 阶段性验收 | 单 Agent 分阶段执行 | 必须拆分 | 完整验收 | 建议确认 |
| **L5** | 跨模块重构 / 多 Agent 协作 / 长链路知识库建设 | 多 Agent 或多轮人工确认 | 必须拆分 | 多轮验收 | 必须确认 |

### 复杂度判断参考

```
任务来了：
  │
  ├─ 只改一个文件的一小部分？
  │   └─ 是 → L1
  │
  ├─ 创建或修改单个完整文件？
  │   └─ 是 → L2
  │
  ├─ 涉及 2-5 个文件（创建+登记+索引更新）？
  │   └─ 是 → L3
  │
  ├─ 创建新模块/新规范/阶段性验收？
  │   └─ 是 → L4
  │
  └─ 跨多个模块/需要并行/需要重构？
      └─ 是 → L5
```

## 7. 单 Agent / 多 Agent 判断规范

### 判断表

| 判断问题 | 单 Agent 倾向 | 多 Agent 倾向 | 说明 |
|----------|--------------|--------------|------|
| 任务目标是否明确？ | ✅ 明确 | ❌ 模糊或需要探索 | 模糊任务先用单 Agent 澄清 |
| 文件范围是否明确？ | ✅ 1-3 个文件 | ❌ 5+ 个文件 | 大范围文件操作可考虑并行 |
| 修改范围是否小？ | ✅ 局部修改 | ❌ 全文重写 | 大范围修改需要分阶段 |
| 是否需要并行处理？ | ❌ 串行即可 | ✅ 有独立并行分支 | 并行任务适合多 Agent |
| 是否涉及多领域？ | ❌ 单一领域 | ✅ 文本+图像+视频混合 | 跨领域需要不同专业视角 |
| 是否需要独立评审？ | ❌ 自检即可 | ✅ 需要独立审查 | 高价值产物建议独立评审 |
| 是否需要长上下文？ | ✅ 上下文可控 | ❌ 超长上下文需分块 | 长上下文可拆分处理 |
| 是否需要多人协作？ | ❌ 单人可完成 | ✅ 需要不同角色 | 协作场景适合多 Agent |

### 使用建议

1. **默认用单 Agent**：大多数 Prompt-KB 任务（L1-L4）都可以单 Agent 完成
2. **L5 任务评估多 Agent**：跨模块、需要并行、需要独立评审时考虑多 Agent
3. **多 Agent 是职责分离**：不是形式主义，每个 Agent 必须有明确的输入输出
4. **简单任务不要过度多 Agent 化**：拆成 3 个 Agent 做 1 个文件的小修是浪费

## 8. 多 Agent 角色设计

### 可选角色

| 角色 | 职责 | 何时使用 | 输入 | 输出 |
|------|------|----------|------|------|
| **Planner Agent** | 任务拆解与执行计划 | L4+ 复杂任务 | 用户需求+上下文 | 执行计划+步骤清单 |
| **Builder Agent** | 创建规范/模板/案例 | 创建类任务 | 执行计划+参考文件 | 目标文件草稿 |
| **Reviewer Agent** | 质量验收 | 验收类任务 | 目标文件+验收标准 | 评分+问题清单+结论 |
| **Refiner Agent** | 小修与版本升级 | 小修类任务 | 问题清单+目标文件 | 修正后文件+版本记录 |
| **Librarian Agent** | 导航登记与索引维护 | 登记类任务 | 产物信息+目标索引 | 更新后的 README/索引 |
| **Tester Agent** | 案例测试和平台适配测试 | 测试类任务 | 案例+模板+检查清单 | 测试记录+结论 |
| **Risk Agent** | 风险、边界和保护文件检查 | 高风险任务 | 任务范围+保护清单 | 风险报告+保护检查 |
| **Summarizer Agent** | 阶段性总结和下一步建议 | 阶段性验收 | 所有交付物+闭环状态 | 验收报告+下一步建议 |

### 角色使用原则

1. **不是每个任务都需要所有 Agent**：L1-L3 通常只需要 Builder + Librarian
2. **多 Agent 是职责分离**：Planner 不执行，Builder 不评审，Reviewer 不修改
3. **简单任务不要过度多 Agent 化**：创建一个小案例不需要 5 个 Agent
4. **角色可以合并**：Builder + Refiner 可以合并为一个 Agent，Reviewer + Risk 可以合并

### 推荐角色组合

| 任务类型 | 推荐角色组合 | 说明 |
|----------|-------------|------|
| L1 简单修改 | Builder | 单 Agent 直接执行 |

| L4 新规范创建 | Planner + Builder + Reviewer + Librarian | 规划+创建+验收+登记 |
| L5 跨模块重构 | 全角色 | 需要完整流程 |

## 10. 标准工作流：验收类任务

### 适用场景

质量验收（完整检查）和轻量复核（快速检查）。

### 质量验收流程

```
1. 只读目标文件
   → 不修改任何内容
   → 完整阅读文件

2. 核对元数据
   → 编号、名称、版本、路径是否正确
   → 依据来源是否列出

3. 核对章节完整性
   → 是否覆盖所有必要章节
   → 章节顺序是否合理

4. 核对核心内容
   → 核心公式/维度/规则是否完整
   → 示例是否正确
   → 表格是否完整

5. 核对与关联规范的一致性
   → 与 T-CONFIG-001 结构是否一致
   → 与上游规范是否有冲突
   → 与已有案例是否兼容

6. 核对保护文件
   → 确认没有修改不应修改的文件

7. 输出评分或通过结论
   → A/B/C/D 评级
   → 具体评分（如 91/100）
   → 通过/不通过结论

8. 给出是否小修
   → 必须修改（阻塞）
   → 建议修改（不阻塞）
   → 无需修改

9. 给出下一步建议
   → 小修后登记
   → 直接登记
   → 需要重做
```

### 轻量复核流程

```
1. 只读修改部分
   → 不重新阅读全文
   → 只检查修正点

2. 核对修正是否正确
   → 修正内容是否符合预期
   → 是否引入新问题

3. 核对版本号
   → 是否升级了版本
   → 版本记录是否更新

4. 输出通过/不通过结论

5. 给出下一步建议
```

### 验收原则

1. **验收不应修改文件**：Reviewer 不是 Builder
2. **轻量复核只检查小修点**：不要重新做完整验收
3. **大验收适合新规范/新模板**：需要全面检查
4. **案例验收适合检查实际可用性**：重点看案例是否可复用

## 11. 标准工作流：小修类任务

### 适用场景

修正已验收产物的小问题（错别字、格式、补充说明、版本号升级）。

### 标准流程

```
1. 明确修正背景
   → 为什么需要修正
   → 来自验收报告还是用户反馈

2. 明确修正位置
   → 具体哪个文件的哪个章节
   → 具体修正什么内容

3. 限定只修改目标文件
   → 不扩大修改范围
   → 不顺手修改其他文件

4. 不重写全文
   → 只做局部修改
   → 保持已有内容不变

5. 更新版本号
   → 小修通常升级次版本号（v0.1 → v0.2）
   → 重大修正可升级主版本号

6. 更新版本记录
   → 在版本记录章节新增条目
   → 说明本次修正内容

7. 输出保护文件检查
   → 确认没有修改保护文件

8. 轻量复核
   → 检查修正是否正确
   → 确认没有引入新问题

9. 通过后登记或继续下一步
   → 更新导航（如有必要）
   → 给出下一步建议
```

### 小修原则

1. **小修不应扩大范围**：修正 A 问题时不要顺手改 B
2. **小修不应回改稳定文件**：不要修改已通过验收的其他文件
3. **小修应说明是否升级版本**：版本号变化必须明确
4. **小修后建议做轻量复核**：确保修正正确

## 12. 标准工作流：导航登记类任务

### 适用场景

将已验收产物登记到 README、QUICKSTART、模块 README、backlog 等索引文件。

### 标准流程

```
1. 确认产物已通过验收
   → 有明确的验收结论
   → 版本号和状态已确定

2. 确认产物信息
   → 路径、编号、版本、状态
   → 关联文件（上游规范、下游案例）

3. 更新 README.md
   → 在对应模块章节新增条目
   → 更新版本历史
   → 更新下一步路线

4. 更新 QUICKSTART.md
   → 在按需求查找表新增入口
   → 更新版本信息

5. 更新模块 README
   → 在对应模块目录的 README 新增条目
   → 更新模块状态

6. 必要时更新 backlog / 阶段路线
   → 更新 Phase 状态
   → 更新下一步候选

7. 不修改产物正文

   → 不修改已验收的产物

8. 输出修改摘要
   → 列出所有修改的文件
   → 说明每个文件新增/更新了什么

9. 输出保护文件检查
```

1. **登记不修改正文**：只更新索引文件
2. **增量更新**：不要重写全文，只做必要的新增/修改
3. **版本历史必须更新**：README 的版本历史记录每次变更

## 13. 标准工作流：测试记录类任务

### 适用场景

模板需要通过案例验证、平台适配模板需要生成平台版本、规范需要验证实际可用性。

### 标准流程

```
1. 选择已验收案例作为输入
   → 案例必须已通过验收
   → 案例必须包含完整的核心信息

2. 提取核心信息
   → 从案例中提取所有必要字段
   → 用表格输出：信息项｜提取内容｜来源位置

3. 按模板生成测试输出
   → 严格遵循模板结构
   → 不修改模板本身

4. 使用检查清单验收
   → 逐项检查测试输出
   → 输出检查结果表格

5. 判断是否需要修改模板
   → 如果测试发现模板问题，记录但不立即修改
   → 问题汇总后统一处理

6. 写入测试结论
   → 模板是否适用于该案例
   → 是否需要修改模板
   → 是否需要修改案例

7. 登记测试记录
   → 更新 README/QUICKSTART
   → 更新模块 README
   → 更新 backlog
```

### 测试原则

1. **测试不修改模板**：测试记录是独立文件，不改模板本身
2. **测试不修改案例**：案例是输入，不是修改对象
3. **测试结论必须明确**：通过/不通过/需要修改
4. **测试记录必须登记**：创建了文件就必须更新索引

## 14. 标准工作流：阶段性验收类任务

### 适用场景

一个模块完成基础规范、速查卡、案例、平台适配模板、测试记录后，需要决定是否进入下一阶段。

### 阶段性验收结构

```
1. 交付物总览
   → 列出所有交付物
   → 编号、文件路径、版本、状态、作用、是否完成

2. 能力覆盖度
   → 检查模块是否覆盖所有必要能力
   → 用表格输出：能力项｜是否覆盖｜对应文件｜说明

3. 场景覆盖度
   → 检查模块是否覆盖至少一个完整业务场景
   → 判断是否需要更多场景才能收尾

4. 闭环检查
   → 检查是否形成完整闭环
   → 如：规范→速查→案例→平台适配→测试

5. 当前不足
   → 列出已知不足
   → 判断是否严重、是否阻塞收尾

6. 是否需要继续扩展
   → 判断是否必须创建更多产物
   → 判断是否必须修改已有产物

7. 是否可以进入下一阶段
   → 基于以上分析给出结论

8. 阶段性结论
   → A. 已完成阶段性闭环，可以进入下一阶段
   → B. 基本完成，建议先补某项
   → C. 还需要继续完善
   → D. 不建议收尾
   → E. 需要重构

9. 下一步建议
   → 进入下一阶段
   → 补充缺失项
   → 更新状态
```

### 验收原则

1. **阶段性验收只读不写**：分析现有产物，不创建新文件
2. **闭环检查是核心**：判断是否形成可用闭环
3. **不足项要分级**：区分阻塞项和按需扩展项
4. **结论必须明确**：给出 A/B/C/D/E 结论

## 15. 保护文件与范围控制规范

### 核心原则

每个任务必须列出不应修改的文件，任务执行后必须报告保护文件检查。

### 保护规则

| 场景 | 不应做的事 | 应该做的事 |
|------|-----------|-----------|
| **创建任务** | 顺手修改导航 | 创建完成后单独做导航登记 |
| **验收任务** | 顺手小修问题 | 记录问题，由独立小修任务处理 |
| **登记任务** | 修改产物正文 | 只更新索引文件 |
| **测试任务** | 修改模板 | 测试记录是独立文件 |
| **小修任务** | 扩大修改范围 | 限定修正位置 |
| **任何任务** | "优化"稳定文件 | 只在有明确理由时修改 |

### 保护文件检查清单

任务执行后必须输出：

```
保护文件检查：
- ✅ 未修改 [文件A]
- ✅ 未修改 [文件B]
- ✅ 未修改 [文件C]
- ...
```

### 范围控制

1. **明确列出保护文件**：任务开始时列出所有不应修改的文件
2. **不要为了"完善"而改动稳定文件**：已通过验收的文件不要随意修改
3. **修改范围必须可控**：如果修改范围超出预期，停下来重新评估
4. **范围漂移时及时停止**：发现正在修改不该修改的文件，立即停止

## 16. 失败与返工处理规范

### 常见失败类型

| 失败类型 | 表现 | 修正方式 | 预防方式 |
|----------|------|----------|----------|
| **会话中断** | 执行到一半断开 | 重新读取文件，从断点继续 | 分阶段执行，每阶段有明确产出 |
| **指令不可复制** | 用户指令太长或格式混乱 | 重新整理指令，确认关键信息 | 使用结构化指令模板 |
| **输出太长** | 单次输出超过上下文限制 | 分段输出，先写核心章节 | 控制单次输出长度 |
| **文件路径错误** | 写入了错误路径 | 检查路径，修正后重新写入 | 写入前先 ls 确认目录存在 |
| **漏改导航** | 创建了文件但没更新索引 | 补充导航登记 | 导航登记作为独立步骤 |
| **修改范围过大** | 验收时顺手改了正文 | 回退修改，重新限定范围 | 严格遵循保护文件清单 |
| **验收结论不清** | 只说"通过"不说评分 | 补充评分和详细结论 | 使用标准验收报告模板 |
| **搜索循环** | 反复搜索同一内容 | 停止搜索，基于已有信息决策 | 设定搜索次数上限 |
| **重复修改稳定文件** | 反复修改已验收产物 | 回退修改，确认修改理由 | 保护文件清单+范围控制 |
| **没有输出下一步建议** | 执行完就结束 | 补充下一步建议 | 下一步建议作为必要输出 |

### 返工流程

```
1. 分析失败原因
   → 是什么导致了失败
   → 失败发生在哪个环节

2. 确定返工范围
   → 需要重新执行哪些步骤
   → 哪些步骤可以保留

3. 限定返工范围
   → 不要重新执行整个任务
   → 只修复失败的部分

4. 执行返工
   → 按标准流程执行
   → 注意保护已完成的部分

5. 验收返工结果
   → 确认问题已解决
   → 确认没有引入新问题

6. 输出返工报告
   → 说明失败原因
   → 说明修正方式
   → 说明当前状态
```
