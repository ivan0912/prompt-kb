## 1. 原始口语需求

> "我想让 AI 帮我整理一个学习计划，但是我不知道怎么说，也不知道应该让它输出什么格式。"

**需求特征提取（参考 Introduction §4.2 四大元素）：**

| 元素 | 用户提供了什么 | 缺失什么 |
|------|---------------|----------|
| 指令 (Instruction) | "整理一个学习计划" | ❌ 模糊——学什么？多久？什么目的？ |
| 上下文 (Context) | 无 | ❌ 完全缺失——用户背景、当前水平 |
| 输入数据 (Input Data) | 无 | ❌ 无具体学习内容或素材 |
| 输出指示 (Output Indicator) | 无 | ❌ 用户明确说"不知道输出什么格式" |

**诊断**: 四个元素缺失 3 个半。这是典型的「模糊需求」，直接丢给 AI 必然得到泛泛而谈的结果。

## 2. 技术选型判断

### 结论：**Prompt Chaining（链式调用）**

### 判断过程（逐步走决策树）

```
Step 1: 这个任务需要推理还是简单执行？
  → 需要"推理"——AI 需要理解用户意图、拆解学习目标、设计合理路径

Step 2: 走 Advanced 决策树（参考 Advanced 总览 §7）
  │
  ├─ 多步数学/逻辑题？     → 不是
  ├─ 需要外部信息/搜索？    → 不是（不需要查资料）
  ├─ 复杂任务可拆分？      → ✅ 是！
  │   "整理学习计划" 可以拆为：
  │   ① 理解需求 + 补全信息 → ② 设计计划框架 → ③ 生成详细计划
  └─ → 用 Prompt Chaining ✓
```

### 为什么不是 Zero-Shot？

参考 Basic Prompting §4.1 的「不适合 Zero-Shot 的信号」：

| 信号 | 本案例是否命中 |
|------|--------------|
| 输出格式和你预期的不一致 | ✅ 命中——用户明确说"不知道输出格式" |
| 同样的 prompt 多次运行结果不稳定 | ⚠️ 可能命中——"学习计划"太宽泛 |
| 任务涉及多步推理或复杂判断 | ✅ 命中——需要先理解再规划 |

→ **Zero-Shot 不适合**。一个 prompt 试图完成"理解模糊需求 + 设计格式 + 生成内容"三件事，必然每件事都做不好。

### 为什么不是 Few-Shot？

Few-Shot 的核心价值是**锁定输出格式**（参考 Basic §4.3 Min et al. 研究：「格式 > 标签正确性」）。
但本案例的问题不在格式，而在**任务本身没有被清晰定义**。给范例解决不了"不知道要学什么"这个问题。

→ **Few-Shot 不够**。它是 Zero-Shot 的增强，不能替代任务分解。

### 为什么是 Prompt Chaining？

参考 Prompt Chaining §2 适用场景和 §4 核心优势：

| PC 特征 | 本案例匹配度 |
|---------|-------------|
| 复杂任务可拆分 | ✅ 完美匹配——3 步 pipeline |
| 每步专注一件事 | ✅ 需求分析 / 计划设计 / 内容生成 分离 |
| 可调试 | ✅ 第一步可以先和用户确认方向再继续 |
| 错误隔离 | ✅ 如果计划框架不对，只改 Step 2 |

## 3. 优化提示词（可直接复制）

### 推荐版本：Prompt Chaining 三步 Pipeline

这是基于 [Prompt Chaining §5 模板](../01-fundamentals/advanced-techniques/prompt-chaining.md#5-中文提示词模板) 直接改写的实战版本。

#### **Step 1：需求澄清与信息补全**

```markdown
你是一个学习规划顾问。

**角色：** 帮助用户把模糊的学习想法变成清晰的规划需求
**输入：** 用户的原始想法（可能很模糊）
**任务：** 通过提问补全制定学习计划所需的关键信息

请根据用户的描述，生成一份"学习需求问卷"。如果用户没有提供以下信息，请逐一询问：

1. **学习主题**：具体想学什么？（如：Python 编程 / Prompt Engineering / 英语口语）
2. **当前水平**：完全零基础 / 有一些了解 / 已有基础想进阶？
3. **学习目标**：为什么学？（工作需要 / 兴趣爱好 / 考证 / 转行）
4. **时间预算**：每天能投入多少时间？希望多长时间达到目标？
5. **期望成果**：学完后能做什么？（能独立写项目 / 能流利对话 / 通过某考试）
6. **偏好方式**：喜欢看文档 / 看视频 / 动手实践 / 混合？

**输出要求：**
- 先列出你已经知道的信息（基于用户描述）
- 再列出你需要确认的问题（编号列表）
- 最后给一个你初步判断的"学习方向建议"（1-2 句话）

---
用户原始描述：
{在此处粘贴你的想法，例如："我想让 AI 帮我整理一个学习计划"}
```

#### **Step 1 变体：最小回答版**

> 如果用户不想回答太多问题，用这个精简版本——只需 3 个必答题，其余由 AI 做合理假设。

```markdown
你是一个学习规划顾问。

**角色：** 用最少的信息快速生成可用的学习计划初稿
**输入：** 用户的原始想法
**任务：** 只确认 3 个关键信息，其余做合理假设

请向用户确认以下 3 个问题（如果用户描述中已包含则跳过）：

1. **想学什么？** （如：Prompt Engineering / Python / 英语口语）
2. **当前大概什么水平？** （零基础 / 听过概念 / 能简单使用 / 想进阶）
3. **每天或每周能投入多少时间？** （如：每天 30 分钟 / 每周 5 小时）

**对于以下信息，如果用户未提供，请自行做合理假设，并在输出中标注「待确认」：**
- 学习目标 → 默认假设为"能在实际工作/项目中应用"
- 时间周期 → 根据时间预算反推
- 学习方式偏好 → 默认假设为"理论 40% + 实践 60%"
- 期望成果 → 根据学习主题推断

**输出要求：**
1. 三问清单（只列未回答的）
2. 我的假设列表（每条标注 [待确认]）
3. 基于以上信息和假设的初步方向建议（2-3 句）

---
用户原始描述：
{在此处粘贴你的想法}
```

**使用建议**: 最小回答版适合"先快速看效果再迭代"的场景。拿到初稿后，用户可以根据 ` [待确认] ` 标记逐条修正。

#### **Step 2：计划框架设计**

```markdown
你是一个学习路径设计师。

**角色：** 基于已确认的需求，设计阶段化的学习路线图
**输入：** Step 1 的需求澄清结果
**任务：** 设计学习计划的骨架（不含具体内容）

**输入数据（来自 Step 1）：**
{粘贴 Step 1 的输出结果}

**输出要求：** Markdown 表格格式

| 阶段 | 名称 | 目标 | 关键内容 | 预计时长 | 产出物 |
|------|------|------|----------|----------|--------|
| 1 | ... | ... | ... | ... | ... |

设计原则：
- 每个阶段应有明确的"完成标志"（产出物）
- 从易到难，循序渐进
- 每阶段不超过 2 周（保持节奏感）
- 总体符合用户的时间预算
```

#### **Step 3：详细计划生成**

```markdown
你是一个专业的学习计划撰写助手。

**角色：** 将计划骨架填充为可执行的详细学习计划
**输入：**
- 计划骨架：{Step 2 的表格}
- 需求详情：{Step 1 的完整信息}
**任务：** 生成最终版学习计划

**输出要求：** 以下固定结构

# {学习主题} 学习计划

## 一、基本信息
- 学习主题：
- 当前水平：
- 学习目标：
- 时间安排：
- 预计总周期：

## 二、学习路线
（按阶段展开每个阶段的具体学习内容、推荐资源、练习方式）

## 三、每周时间表示例
| 星期 | 内容 | 时长 | 方式 |
|------|------|------|------|
| 周一 | ... | ... | ... |
| ... | ... | ... | ... |

## 四、里程碑检查点
- 第 X 周：[ ] 应该能够...
- 第 Y 周：[ ] 应该能够...

## 五、常见坑提醒
（列出学习这个主题时最容易踩的 3-5 个坑）

---
开始生成：
```

## 4. 更简单的版本

### 场景：你不想跑三步，只想一次搞定

→ 用 **Zero-Shot + 结构化输出指示器**（参考 Introduction §4.2 + Basic 模板 A）

**适用条件**: 你自己心里大概有数，只是需要一个结构化的输出框架

```markdown
帮我制定一个 {学习主题} 的学习计划。

**我的情况：**
- 当前水平：{你的水平}
- 每天可用时间：{X 小时}
- 学习目标：{想达到什么程度}
- 预计周期：{多长时间}

**请按以下格式输出：**

# {主题} 学习计划

## 基本信息
（主题、水平、目标、时间安排概览）

## 分阶段路线（从入门到熟练）
每个阶段包含：阶段名称 | 学习目标 | 核心内容 | 推荐资源 | 练习方式 | 预计时长

## 每周时间表示例
（星期 × 内容 × 时长 × 学习方式）

## 关键里程碑
（第几周应该能达到什么水平）

## 注意事项
（3-5 个最容易踩的坑）
```

**局限（参考 Basic §6 不适用场景）**: 单 prompt 承担了所有任务，如果需求复杂可能会遗漏或泛化。适合需求相对明确的场景。

## 5. 更进阶的版本

### 场景：你需要最高质量的计划，且愿意付出更多调用成本

→ **Prompt Chaining + CoT + Generated Knowledge** 组合（参考 Advanced 总览 §6 学习路径中的组合方式）

**核心升级**: 在 Step 2 加入 CoT 推理（"让我们一步一步地思考"），在 Step 1 之前加入 Generated Knowledge 阶段补充领域知识。

#### **Step 0：领域知识生成（新增）**

```markdown
你是一个 {学习领域} 教育专家。

**任务：** 生成关于"{学习主题}"的核心知识地图，用于指导后续的学习计划设计。

请逐步思考并输出：
1. 这个领域的知识体系是如何组织的？（主要分支和依赖关系）
2. 新手最常见的错误学习路径是什么？
3. 这个领域中哪些资源是最权威的？（教材/课程/工具/社区）
4. 从零基础到熟练，通常需要经历哪些关键阶段？

**输出格式：** 结构化知识图谱（Markdown 嵌套列表）
```

#### **Step 1'：需求澄清（CoT 增强）**

在原 Step 1 末尾追加：

```markdown
在生成问题之前，**让我们一步一步地思考**：
1. 用户的描述中隐含了哪些信息？
2. 根据该领域的常见学习路径，还有哪些关键决策点需要明确？
3. 我应该优先问哪 3 个最重要的问题（按重要性排序）？

请按此推理过程输出问卷。
```

#### **Step 2'：计划框架设计（CoT 增强）**

在原 Step 2 追加：

```markdown
**在设计路线之前，让我们一步一步地思考：**
1. 该领域的知识依赖关系是怎样的？（必须先学 A 才能 学 B）
2. 用户的 {时间预算} 内最多能覆盖多少内容？
3. 哪些内容是"必修"（不学会后面全卡住），哪些是"选修"（可以跳过）？
4. 怎样安排顺序可以让用户最快获得正向反馈（做出东西/解决问题）？

基于以上推理，设计学习路线表。
```

**组合效果**: Step 0 补充领域知识 → Step 1' CoT 深度理解需求 → Step 2' CoT 科学设计路径 → Step 3 生成最终计划

**代价**: 4 次 API 调用，token 消耗约为简单版的 3-4 倍。适用于高价值学习场景（如转行学习、考证准备）。

## 6. OpenClaw 执行方案

### 推荐：单 Agent 顺序执行

| 方案 | 推荐? | 原因 |
|------|-------|------|
| **单 Agent（顺序 Chaining）** | ✅ **推荐** | 任务是串行依赖的（Step 1→2→3），无并行收益；单 Agent 顺序调用最简单可控 |
| 多 Agent 并行 | ❌ 不需要 | 各步骤强依赖，无法并行化 |
| 多 Agent 流水线 | ⚠️ 过度工程 | 除非要把这个流程固化成重复使用的自动化工具 |

### OpenClaw 推荐配置

```yaml
execution_mode: single_agent_sequential    # 单 Agent 顺序执行
multi_agent_required: false                # 不需要多 Agent

pipeline_steps:
  - step: 1
    name: 需求澄清
    prompt_ref: "Step 1（标准版或最小回答版）"
    temperature: 0.7
    requires_human_confirmation: false     # Step 1 本身就是收集信息，无需确认

  - step:2
    name: 计划框架设计
    prompt_ref: "Step 2"
    temperature: 0.7
    requires_human_confirmation: true      # ⭐ 确认需求方向后再进入内容生成

  - step: 3
    name: 详细计划生成
    prompt_ref: "Step 3"
    temperature: 0.3                       # 追求格式稳定
    requires_human_confirmation: false

中间结果保存: true                          # 每步输出都保存，支持断点续跑和逐步审查
自动化复用适合度: 有条件适合                  # ✅ 适合固化为重复模板
                                           # ⚠️ 但应先人工跑通至少 3 次，验证各步骤稳定后再自动化
```

**配置决策说明：**

| 决策项 | 选择 | 原因 |
|--------|------|------|
| 执行模式 | 单 Agent 顺序 | 步骤间强依赖（Step 2 需要 Step 1 输出），无并行化空间 |
| 是否多 Agent | 不需要 | 无并行步骤，多 Agent 只增加编排复杂度 |
| 人工确认位置 | Step 1→2 之间 | 性价比最高的检查点——方向错了后面全白做 |
| 中间结果保存 | 是 | 支持用户在某一步打断修改后只重跑后续步骤 |
| 自动化前提 | 先人工跑通 3 次 | 确认各步骤 prompt 在目标场景下输出质量稳定 |

### 单 Agent 配置（参考 Prompt Chaining §6）

```
┌──────────────────────────────────────────┐
│           LearningPlan Agent              │
│                                          │
│  State: idle → step1 → step2 → step3 → done │
│                                          │
│  step1: 需求澄清 prompt                   │
│    ↓ 输出传递                            │
│  step2: 计划框架 prompt (可选 CoT)        │
│    ↓ ★ 人工确认门                        │
│  step3: 详细计划生成 prompt               │
│    ↓ 最终输出                            │
│  done: 返回完整计划                       │
└──────────────────────────────────────────┘
```

**关键配置要点**:
1. **中间结果保留**: 每步输出都保存，方便用户在某一步打断修改后重新执行后续步骤
2. **人工确认门**: Step 1 → Step 2 之间建议加入人工确认（让用户确认需求理解是否正确）
3. **温度设置**: Step 1 和 Step 2 用 temperature=0.7（需要一定创造性），Step 3 用 temperature=0.3（追求格式稳定）

#### ✅ 适用场景

| **项目计划** | "我想做一个 XX 项目但没规划" | ⭐⭐⭐⭐ 需增加团队/预算/技术栈维度 |
| **考试计划** | "我要准备 XX 考试" | ⭐⭐⭐⭐⭐ 时间刚性、目标清晰，非常适合 |
| **内容创作计划** | "我想做自媒体但不知道做什么方向" | ⭐⭐⭐ 需增加平台/受众/竞品维度 |
| **职业转型计划** | "想转到 XX 行业不知道怎么准备" | ⭐⭐⭐⭐ 高价值场景，值得用进阶版 |

#### ❌ 不适用场景

| 场景 | 原因 | 替代建议 |
|------|------|----------|
| **需要实时数据的任务** | 如"帮我查明天天气做出行计划"，Chaining 不解决数据获取问题 | 用 ReAct + 工具调用 |
| **法律 / 医疗 / 金融等专业建议** | AI 生成的计划不能替代专业判断 | 必须由持证专业人士审核或生成 |
| **必须接入外部工具才能完成** | 如"帮我写代码并部署到服务器"，需要代码执行环境 | 用 ReAct 或 PAL |
| **用户完全不愿提供任何信息** | 连"想学什么"都不说，无法做任何有意义的假设 | 先解决意愿问题，不在提示词范畴 |

- **第 7 天**：[ ] 能口述四大元素并写出合格的 Zero-Shot prompt

- **第 30 天**：[ ] 完成一个完整的「口语需求 → 结构化 prompt」实战案例

## 五、常见坑提醒

1. **只看不练** — Prompt Engineering 是动手技能，每天至少写 3 个 prompt 才有效
2. **一次学太多** — 7 大高级技术不需要全掌握，先精通 CoT + Chaining 就够用
3. **忽略迭代** — 第一次写的 prompt 很少是好的版本，养成"写→测→改"的习惯
4. **照搬模板** — 看到的模板都要根据自己的场景改写，直接复制效果通常不好
5. **不记录复盘** — 每次使用的成功/失败经验是最宝贵的学习材料

### 本次经验沉淀

1. **"我不知道怎么输出格式" = Prompt Chaining 的强信号** — 当用户连输出格式都无法指定时，说明任务本身还未被充分理解，必须先做需求澄清
2. **Step 1 的人工确认门是性价比最高的优化** — 在需求澄清和计划设计之间插入人工确认，能避免后续所有步骤的方向性错误
3. **Zero-Shot 简单版仍有价值** — 对于"心里有数只要结构化输出"的场景，单 prompt + 固定输出模板就够了，不需要过度工程
4. **组合技的使用边界** — CoT + GK + Chaining 的进阶组合 token 消耗是简单版的 3-4 倍，只在"高价值 + 高不确定性"场景下才值得
